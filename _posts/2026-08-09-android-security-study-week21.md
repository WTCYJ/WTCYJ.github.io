> **진행 구간**: 24주 로드맵의 21주차 — 안전한 검증
> **대상**: CVE-2022-20425 / AVD `sec-31-r03`(2022-08-01) · `sec-31-r05`(2022-10-01)
> **이전 글**: [20주차 CVE 재현](/posts/android-security-study-week20/) · [19주차 이미지 쌍 준비](/posts/android-security-study-week19/) · [24주 로드맵](/posts/android-security-study-roadmap/)

20주차에 재현에 성공했습니다. 패치 전 이미지에서는 컴포넌트당 100개, 패치 후에는 패키지당 100개였습니다. 관측은 깔끔했습니다.

그런데 이걸로 "이 CVE 패치의 효과"라고 말할 수 있느냐가 남습니다. 19주차에 두 이미지를 파일 단위로 비교했을 때 **7개 파일이 달랐습니다.** 커널도 램디스크도 함께 바뀝니다. 빌드 컷은 10개월 차이입니다. 동작 차이 하나만 놓고 원인을 특정하기에는 후보가 너무 많습니다.

로드맵의 21주차가 요구하는 것이 정확히 이 지점입니다. "로그·예외·테스트 결과·**코드 경로**로 차이를 검증한다." 이번 회차는 동작이 아니라 코드를 봤습니다.

---

## 배경 개념 - 시스템 코드는 어디에 있는가

앱은 APK 안에 dex 로 들어 있지만, 프레임워크 코드는 다른 곳에 있습니다. 우리가 보려는 `ZenModeHelper` 는 `system_server` 프로세스에서 도는 클래스이고, 그 코드는 이미지의 `/system/framework/services.jar` 에 담겨 있습니다.

같은 디렉터리에 `services.odex`, `services.vdex`, `services.art` 도 함께 있습니다. 이건 설치 시점이 아니라 **빌드 시점에 미리 컴파일해 둔 산출물**입니다. 부팅할 때마다 dex 를 해석하지 않고 바로 실행하기 위한 것입니다.

그래서 "코드를 읽는다"고 할 때 무엇을 읽는지가 문제가 됩니다. 이번에는 `services.jar` 안의 dex 를 읽었습니다. 이 선택의 한계는 뒤에서 다시 적겠습니다.

## 1. 실습 환경과 준비

19주차에 만든 AVD 두 대를 그대로 씁니다. 각각 냉부팅한 뒤 파일을 하나씩 꺼냈습니다.

```bash
adb pull /system/framework/services.jar
```

| | 크기 | SHA-256 |
| --- | --- | --- |
| `services-r03.jar` | 18,218,029 B | `4d9f14b09bb8010e…` |
| `services-r05.jar` | 18,221,869 B | `91961084056cda40…` |

두 jar 모두 `classes.dex`(11.3MB)와 `classes2.dex`(6.8MB)를 담고 있습니다. dex 가 그대로 들어 있으니 디컴파일할 수 있습니다.

클래스 하나만 필요하므로 jadx 에 범위를 좁혀 줬습니다. 18MB jar 전체를 푸는 것과 시간 차이가 큽니다.

```bash
jadx --no-res --single-class com.android.server.notification.ZenModeHelper -d out-r03 services-r03.jar
```

## 2. 수행 절차

이번 회차의 검증은 네 갈래입니다.

1. **코드 대조** — 두 이미지의 같은 클래스를 통째로 diff 해서, 동작을 바꿀 수 있는 다른 변경이 그 안에 있는지 본다
2. **예측 검증** — 코드가 예측하는 수치와 실측이 맞는지 본다
3. **재현성** — 핵심 수치를 독립 실행으로 다시 낸다
4. **대조군** — 한도가 패키지별이라는 것을 다른 패키지로 확인한다

## 3. 관측 결과

### 3-1. 클래스 전체에서 17줄

`ZenModeHelper` 는 r03 이 1,541행, r05 가 1,557행입니다. 통째로 diff 한 결과가 이게 전부입니다.

```diff
             int newRuleInstanceCount = getCurrentInstanceCount(automaticZenRule.getOwner())
                     + getCurrentInstanceCount(automaticZenRule.getConfigurationActivity()) + 1;
-            if (newRuleInstanceCount > 100 || (ruleInstanceLimit > 0 && ruleInstanceLimit < newRuleInstanceCount)) {
+            int newPackageRuleCount = getPackageRuleCount(pkg) + 1;
+            if (newPackageRuleCount > 100 || (ruleInstanceLimit > 0 && ruleInstanceLimit < newRuleInstanceCount)) {
                 throw new IllegalArgumentException("Rule instance limit exceeded");
             }
```

그리고 r05 에만 있는 메서드 하나입니다.

```java
private int getPackageRuleCount(String pkg) {
    if (pkg == null) return 0;
    int count = 0;
    synchronized (this.mConfig) {
        for (ZenModeConfig.ZenRule rule : this.mConfig.automaticRules.values()) {
            if (pkg.equals(rule.getPkg())) count++;
        }
    }
    return count;
}
```

**이 클래스 안에 다른 차이는 없습니다.** 18주차에 gitiles 에서 받아 읽은 AOSP 커밋 `0c607e70` 과 형태가 같습니다.

재미있는 부분은 `newRuleInstanceCount` 가 r05 에서도 **여전히 계산된다**는 점입니다. 다만 첫 조건에서는 빠지고 두 번째 조건(앱이 스스로 선언한 한도)에만 남습니다. 상류 커밋의 diff 도 정확히 그 모양이었습니다.

### 3-2. 경로에 걸린 다른 클래스도 봤다

"이 클래스 안에는 다른 차이가 없다"만으로는 부족합니다. 호출 경로에 걸린 클래스가 더 있고, 그중 하나가 바뀌었다면 설명이 달라집니다. 그래서 두 개를 더 뽑아 대조했습니다.

| 클래스 | 소속 | 두 이미지 차이 |
| --- | --- | --- |
| `ZenModeHelper` | services.jar | **17줄 — 전부 이 패치** |
| `NotificationManagerService` | services.jar | 36줄이지만 **진입점 `addAutomaticZenRule` 은 동일** |
| `ZenModeConfig` | framework.jar | **0줄 — 완전 동일** |

`NotificationManagerService` 의 36줄을 열어보니 실제 변경은 알림 스누즈 개수를 제한하는 수정 하나였고(`mSnoozeHelper.canSnooze` 호출 추가), 나머지는 jadx 가 남긴 주석과 오프셋 표시였습니다. 우리가 지나가는 진입점 코드는 한 글자도 다르지 않습니다.

`ZenModeConfig` 는 규칙을 담는 자료구조이고 `getPkg()` 를 제공하는 클래스입니다. 1,962행이 완전히 같았습니다.

정리하면 **인증 검사도, 규칙 저장 구조도, 패키지 이름을 돌려주는 코드도 두 이미지에서 같습니다.** 달라진 것은 한도를 세는 방식 하나뿐입니다.

### 3-3. 같은 달 같은 패키지에 한도 수정이 하나 더 있었다

> **덧붙임**: 이 글을 올린 뒤 결론을 재검토하다가 확인한 내용입니다. 위에서 "무관한 스누즈 수정"이라고 한 줄로 넘긴 것이 실은 **별개의 보안 수정**이었습니다.

`SnoozeHelper` 를 따로 뽑아 대조해보니 r05 에만 이게 있습니다.

```java
static final int CONCURRENT_SNOOZE_LIMIT = 500;

protected boolean canSnooze(int numberToSnooze) {
    synchronized (this.mLock) {
        if (this.mPackages.size() + numberToSnooze > 500) return false;
        return true;
    }
}
```

**공교롭게도 이것도 자원 한도 수정입니다.** 스누즈해 둘 수 있는 알림 개수에 상한을 새로 건 것입니다. 같은 달, 같은 notification 패키지에, 같은 계열의 수정이 둘 들어온 셈입니다.

그래서 주의할 점이 하나 생깁니다. **"notification 쪽이 바뀌었으니 이 CVE 패치겠지"로 읽으면 틀립니다.** 이번 대조에서 그 함정을 피할 수 있었던 이유는 클래스 단위로 봤기 때문입니다. 패키지 단위나 "diff 가 있다/없다" 수준으로 봤다면 두 수정을 구분하지 못했을 겁니다.

거꾸로 보면, 2022-10 에 이 영역에서 자원 한도를 두 군데 손봤다는 뜻이기도 합니다. 한 결함을 고치면서 같은 유형을 함께 훑은 흔적으로 읽힙니다.

### 3-4. 코드가 예측한 값이 그대로 나왔다

![r03은 컴포넌트 기준으로 세어 5개면 500까지 허용하고 501에서 거부되며, r05는 패키지 기준으로 세어 컴포넌트 수와 무관하게 101에서 거부되는 것을 코드와 실측으로 대응시킨 도식](/assets/img/android-security-study/24-code-to-observation.svg)

| 측정 | r03 (2022-08-01) | r05 (2022-10-01) |
| --- | --- | --- |
| 컴포넌트 1개 · 400회 | 101 거부 | 101 거부 |
| 컴포넌트 5개 · 400회 | 거부 없음 | 101 거부 |
| 컴포넌트 5개 · 600회 | **501 거부** (2회 재현) | **101 거부** |

- r03 은 컴포넌트 기준이므로 컴포넌트 5개면 500까지 → **501에서 거부**
- r05 는 패키지 기준이므로 컴포넌트 수와 무관하게 100까지 → **101에서 거부**

방향만 맞은 것이 아니라 **수치가 맞습니다.** 20주차에 비어 있던 칸(r05·600회)도 채웠는데, 시도 횟수를 늘려도 101 그대로입니다.

### 3-5. 재현성

핵심 수치인 501 을 독립된 두 실행에서 다시 냈습니다. 각각 `-wipe-data` 냉부팅으로 시작했고, 출력이 완전히 같았습니다. 한 번 나온 숫자를 그대로 쓰지 않으려고 한 것인데, 앞선 회차에서 스냅샷 인공물에 한 번 속았던 것이 영향을 줬습니다.

### 3-6. 대조군 — 한도는 전역이 아니다

r05 에서 프로브 규칙 100개가 등록된 상태에서 `pkg=android` 의 기본 규칙 2개가 **함께 존재**했습니다. 합계 102 입니다.

전역 상한이었다면 100에서 전체가 막혔어야 합니다. 패키지 단위로 센다는 것과 일치합니다.

## 4. 결과 해석

### 4-1. 18주차의 추정 두 개가 정리됐다

조사 카드에 `[추정]` 으로 남겨뒀던 항목이 있습니다.

| 18주차 | 21주차 결과 |
| --- | --- |
| r05 백포트의 한도 값이 100인지 **[추정]** | **[확인]** — 바이트코드에서 `> 100` 을 읽었고, `RULE_LIMIT_PER_PACKAGE = 100` 상수도 있습니다 |
| Android 12 백포트는 상수까지 함께 들여왔을 것 **[추정]** | **틀렸습니다** — 상수는 **양쪽 이미지에 다 있습니다** |

두 번째가 20주차에 가설이 어긋난 뿌리입니다. 소스 태그 `android-12.0.0_r34` 에는 그 상수가 없어서 "백포트가 상수까지 가져왔겠구나"라고 추론했는데, 실제로는 **SDK 브랜치 빌드에 이미 있었습니다.** 그래서 백포트는 상수를 들여올 필요 없이 검사식만 바꾼 상류 커밋 그대로였습니다.

18주차 글에서 "제가 받은 diff 는 main/13 브랜치 버전이고 Android 12 백포트는 별개 커밋"이라고 적었는데, **형태로는 같은 커밋**이었던 셈입니다. 다른 것은 소스 태그와 배포 이미지였지 브랜치가 아니었습니다.

### 4-2. 이번 검증이 좁힌 것과 좁히지 못한 것

좁힌 것은 이겁니다. **동작을 결정하는 코드 경로가 그 17줄이고, 같은 클래스에도 이웃 클래스에도 다른 후보가 없습니다.** 그리고 그 17줄이 예측하는 수치(500, 100)가 실측(501, 101)과 맞습니다.

좁히지 못한 것도 분명합니다. 두 이미지가 그 외에 같다는 뜻은 아닙니다. 7개 파일 차이는 그대로 남아 있습니다. 다만 커널이나 램디스크가 "컴포넌트 이름을 바꾸면 한도가 5배가 되는" 자바 레벨 동작을 만들어낼 경로를 저는 찾지 못했고, 그런 경로를 가정하는 것보다 눈앞의 17줄로 설명하는 쪽이 훨씬 단순합니다.

## 5. 시행착오와 정정

이번 회차는 도구가 순순히 동작해서 크게 헤맨 곳이 없습니다. 대신 판단을 한 번 바꿨습니다.

처음에는 시스템 이미지를 마운트해서 파일을 직접 꺼내려고 했습니다. Windows 에서 ext4 이미지를 여는 것이 번거로워 방법을 찾다가, **AVD 가 이미 있는데 그냥 부팅해서 `adb pull` 하면 된다**는 것을 뒤늦게 알아차렸습니다. 19주차에 만들어 둔 자산을 잊고 더 어려운 길을 보고 있었습니다.

그리고 하나를 한 줄로 넘겼습니다. `NotificationManagerService` 의 36줄을 보고 "무관한 스누즈 수정"이라고 적고 지나갔는데, 뒤에 다시 열어보니 **별개의 보안 수정**이었습니다(3-3). 제 관심사가 아니라는 것과 중요하지 않다는 것은 다른데, 앞의 이유로 뒤의 판단을 내렸습니다. **"무관하다"고 쓸 때는 무관함을 확인하고 써야 합니다.**

한 가지 더. `services.jar` 를 읽었지만 기기가 실제로 실행하는 것은 미리 컴파일된 `services.odex` 일 수 있습니다. 둘은 같은 dex 에서 나온 것이라 내용이 어긋날 이유는 없지만, **"실행되는 코드를 읽었다"고 말하려면 그 연결을 확인해야** 합니다. 이번에는 확인하지 않았으므로 아래 한계에 적습니다.

## 6. 도달 상태와 다음 구간

| 커리큘럼 | 상태 |
| --- | --- |
| 1~20주 | 완료 |
| **21주 안전한 검증** | **완료** — 코드 경로 대조, 예측 검증, 재현성, 대조군 |
| 22주 근본 원인 분석 | 다음 |
| 23~24주 최종 보고서 | |

한계를 정리해 둡니다.

- **이미지 쌍은 여전히 단일 변수가 아닙니다.** 이번 검증이 보인 것은 "동작을 결정하는 코드 경로가 그 17줄"이라는 것이지 두 이미지가 그 외에 같다는 것이 아닙니다.
- **읽은 것은 `services.jar` 안의 dex 입니다.** 실행 시점에 AOT 산출물(`services.odex`)이 쓰인다면 그것과 dex 가 일치하는지는 따로 확인해야 합니다.
- **한도 100 이 r03 계열에 언제 들어왔는지는 추적하지 않았습니다.** 소스 태그에는 없고 SDK 브랜치 빌드에는 있다는 사실만 확인했습니다.
- 디컴파일 결과는 jadx 의 해석입니다. 바이트코드 수준에서 교차 확인하지 않았습니다.

22주차는 근본 원인 분석입니다. 코드와 관측을 붙여 뒀으니, 남은 것은 **왜 컴포넌트 단위 카운팅이 신뢰 경계를 잘못 그은 것인가**를 설명하는 일입니다.

20주차에 결과가 나왔을 때 이미 끝난 것 같았습니다. 숫자가 깔끔했고 방향도 맞았습니다. 그런데 그 시점에 제가 가진 것은 "두 이미지에서 다르게 동작한다"였지 "이 패치 때문이다"가 아니었습니다. 둘 사이의 거리가 이번 회차였습니다.

거리를 좁히는 방법은 결국 코드를 여는 것이었고, 열어보니 1,541행 중 17줄이었습니다. 그 17줄이 예측하는 숫자가 기기에서 나온 숫자와 맞았습니다.

재현했다는 말과 원인을 안다는 말은 다릅니다. 앞의 것은 20주차에, 뒤의 것은 이번에 겨우 얻었습니다. 그리고 뒤의 것도 완전하지 않아서 한계를 네 줄이나 적어야 했습니다.
