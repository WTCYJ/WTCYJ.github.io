> **한 줄 결론**: 사용자가 상호작용하던 주소는 스테이킹 컨트랙트가 아니라 **owner 가 로직을 갈아끼울 수 있는 업그레이드 프록시**였다. 감사받은 V1 으로 예치금을 모은 뒤 숨겨진 인출 함수가 박힌 V2 로 교체하는 것이 이 러그풀의 전부다.

## 분석 대상

스테이킹 서비스 `supersafestaking.xyz` 와 그 온체인 컨트랙트. 프론트엔드는 Next.js 이고 JS 청크에 컨트랙트 주소와 ABI 가 하드코딩돼 있다.

| 항목 | 값 |
|---|---|
| 체인 | Ethereum **Sepolia 테스트넷** (chainId 11155111) |
| 자산 단위 | Sepolia 테스트넷 ETH (tETH) — **메인넷 ETH 아님, 금전 가치 없음** |
| 시각 기준 | UTC |

이 글의 모든 ETH 금액은 테스트넷 자산이다. 실제 금전 피해가 아니라 **러그풀 기법과 자금 흐름을 온체인에서 재현·입증한 것**이다.

## 1. 컨트랙트 주소 특정

Next.js 청크를 내려받아 `0x` 로 시작하는 40자리 주소와 ABI 를 검색했다. wagmi 라이브러리 예제에 들어 있는 주소를 제외하면, `deposit`/`withdraw`/`claimRewards`/`APR_BPS` ABI 와 함께 쓰이는 주소는 하나뿐이었다.

```
0x59d9c89a98d65d5e6fe4c76ec3f1c8c06e04c7ef
```

`eth_getCode` 를 여러 체인에 호출한 결과 Sepolia 에서만 바이트코드가 반환돼 배포 체인도 확정됐다. **프론트엔드 번들은 온체인 조사의 출발점이다** — 라이브러리 예제 주소를 걸러 내는 것만 주의하면 된다.

## 2. 런타임 바이트코드가 800바이트

여기서 이상 신호가 나왔다. 사용자 접점 주소의 런타임 바이트코드가 **약 800바이트**뿐이다. deposit/withdraw/보상 계산/APR 로직이 들어갈 크기가 아니다.

디스어셈블하면 스테이킹이 아니라 프록시 패턴이었다.

```
셀렉터 0x3659cfe6 = upgradeTo(address)    // owner 전용, 실패 시 "SuperSafeProxy: not owner"
셀렉터 0xaaf10f42 = implementation()      // 현재 구현체 주소 반환
fallback          : delegatecall(implementation)   // 모든 호출을 구현체로 위임

implementation slot = 0x6bdfe5ec314fb770be4b83bf2e2e4d90431d9a0919b0bf94bcb046d69e2c537f
storage slot 0 (owner) = 0xd239a6cbdce7bbe371d5cf1d079f7576e1a67845
```

`delegatecall` 구조라 **구현체 코드는 프록시의 잔액과 스토리지 컨텍스트에서 실행된다.** 즉 owner 가 구현체를 바꾸면 예치금을 다루는 로직 전체가 바뀐다. 이게 이번 탈취의 본질이다.

크기 이상은 프록시를 알아채는 가장 싼 신호다. "이 기능들을 다 하는 컨트랙트치고 코드가 너무 작다" 는 위화감에서 시작해 `implementation()` 셀렉터를 확인하면 5분 안에 판별된다.

## 3. 정상 구현체와 악성 구현체

| 컨트랙트 | 역할 | 배포자 | 특징 |
|---|---|---|---|
| `0x59d9c89a…04c7ef` | 프록시 (사용자 접점) | `0xd239a6…` | `upgradeTo` + `delegatecall` |
| `0xd0147142…84f474` | V1 구현체 (정상) | `0xd239a6…` | deposit/withdraw/claimRewards, **인출 백도어 없음** |
| `0x7f6f65ed…59281e` | V2 구현체 (악성) | `0xcc51ccae…` | 숨겨진 인출 함수 `0x0c0ceb53`, 수취 주소 하드코딩 |

V1 을 감사받는 데 문제가 없다. **실제로 백도어가 없기 때문이다.** 감사 보고서는 정직할 수 있고, 그래도 자금은 나간다. 감사 대상이 "지금 배포된 구현체" 일 뿐 "앞으로 배포될 구현체" 가 아니라서다.

악성 V2 바이트코드에는 주소 두 개가 `PUSH20` 으로 박혀 있다.

```asm
PUSH20 0xcc51ccaebe1a4a5ac00cf14128d02532e75ec9a3   ; require(msg.sender == 이 주소)
PUSH20 0x313eb3ad72a2357d2cdc1fce15640bcfd9544a24   ; payable(이 주소).transfer(balance)
```

호출자 검증 주소와 자금 수취 주소가 컴파일 타임에 고정돼 있다. 소스 없이 바이트코드만 봐도 **누가 부를 수 있고 어디로 나가는지**가 그대로 읽힌다.

## 4. 타임라인 — 3분의 간격

| 시각 (UTC) | 행위 | 주체 | 트랜잭션 |
|---|---|---|---|
| 2026-06-14 06:18:24 | 프록시·V1 배포 및 `initialize()` | `0xd239a6…` | `0xd1a9c762…0d09` |
| 2026-06-17 17:29:36 | **악성 V2 구현체 배포** | `0xcc51ccae…` | `0xfd3c7f12…8b28` |
| 2026-06-17 17:32:24 | **`upgradeTo(0x7f6f65ed…)` — 러그 활성화** | `0xd239a6…` | `0xfce1c6bc…9f80` |
| 2026-06-18 08:46:24 | drain `0x0c0ceb53` — 19.95879 tETH 반출 | `0xcc51ccae…` | `0x98941f14…fbb9` |
| 2026-06-24 16:16:00 | 2차 drain — 0.204739 tETH 반출 | `0xcc51ccae…` | `0xf518857a…a091` |

**악성 구현체가 러그 3분 전에 미리 배포됐다.** 즉흥적 판단이 아니라 사전에 계획된 행위임이 이 간격에서 드러난다. 배포와 교체가 서로 다른 지갑에서 3분 간격으로 일어나는 건 우연이 아니다.

러그 활성화(06-17 17:32)와 실제 인출(06-18 08:46) 사이에도 15시간이 있다. 그동안 프록시는 여전히 예치를 받았고, 실제로 그 구간에 추가 입금이 들어왔다.

## 5. 피해 규모

전체 트랜잭션을 페이지네이션으로 수집한 뒤, **`to` 가 대상 컨트랙트이고 메서드가 `deposit()`(`0xd0e30db0`)이며 실패하지 않은 `value > 0`** 트랜잭션만 예치로 집계했다. 이 컨트랙트는 Sepolia 에서 아직 살아 있어 조회 시점마다 누계가 변하므로, **탈취 대상이 확정되는 2차 드레인 시점까지**를 기준으로 고정했다.

| 구간 | deposit 건수 | 고유 지갑 | 금액 (tETH) |
|---|---|---|---|
| 1차 드레인(06-18 08:46)까지 예치 | 2,487 | 200 | 19.963425 |
| 1차~2차 드레인 사이 추가 예치 | 18 | 18 (기존 지갑 포함) | 0.200104 |
| **합계 (탈취 대상)** | **2,505** | **200 (고유)** | **20.163529** |

두 차례 드레인 합계(19.95879 + 0.204739 = **20.163529 tETH**)가 예치 합계와 정확히 일치하고, 수취 지갑 `0x313eb3ad…` 의 현재 잔액과도 같다. 세 숫자가 맞아떨어지므로 집계 기준이 옳았다고 볼 수 있다.

피해 지갑 200개, deposit 2,505건. 지갑 하나가 평균 12번 넘게 예치했다는 뜻이다.

## 6. 피의자 연관 지갑

| 지갑 | 역할 | 판단 근거 |
|---|---|---|
| `0xd239a6cbdce7bbe371d5cf1d079f7576e1a67845` | 프록시·V1 배포자 / owner / 러그 실행 | storage slot 0 의 owner 값과 일치. CREATE2 배포, `initialize()`, `upgradeTo()` 호출자 |
| `0xcc51ccaebe1a4a5ac00cf14128d02532e75ec9a3` | 악성 V2 배포자 / drain 실행자 | V2 컨트랙트 Creator. **V2 바이트코드에 호출자 검증 주소로 하드코딩.** 2회 drain 발신자 |
| `0x313eb3ad72a2357d2cdc1fce15640bcfd9544a24` | 탈취 자금 수취 지갑 | **V2 바이트코드에 수취 주소로 하드코딩.** 20.163529 tETH 수령 후 전출 이력 없음 |

세 지갑의 연결 고리가 **시간과 코드 양쪽**에서 나온다. `0xcc51ccae…` 가 배포한 컨트랙트를 3분 뒤 `0xd239a6…` 이 `upgradeTo` 대상으로 지정했고, 그 컨트랙트 안에는 `0x313eb3ad…` 가 수취 주소로 박혀 있다.

바이트코드에 주소가 하드코딩돼 있다는 건 강한 증거다. 트랜잭션 그래프는 우연히 이어질 수 있지만, **컴파일 시점에 다른 지갑의 주소를 알고 있었다**는 사실은 사전 조율 없이 설명되지 않는다.

## 종합

감사 완료를 내세운 15% APR 스테이킹 서비스였지만, 실제 컨트랙트는 owner 가 로직을 언제든 교체할 수 있는 업그레이드 프록시였다. 200개 지갑이 2,505건에 걸쳐 예치한 뒤 2026-06-17 구현체가 악성본으로 교체됐고, 이튿날 예치금 20.163529 tETH 가 피의자 지갑으로 반출됐다. 탈취 자금은 지금까지 이동 없이 `0x313eb3ad…` 에 그대로 남아 있다.

## 정리 — 이 문제에서 남는 것

**"감사받았다" 는 시점의 진술이다.** 업그레이드 가능한 프록시에서 감사는 그 순간의 구현체에만 유효하다. 사용자가 확인해야 하는 것은 감사 여부가 아니라 **`upgradeTo` 가 존재하는지, owner 가 누구인지, 타임락이 걸려 있는지**다.

**바이트코드 크기가 첫 신호다.** 기능 대비 코드가 지나치게 작으면 프록시를 의심한다. `implementation()` 셀렉터 하나로 확정된다.

**하드코딩된 주소는 소스 없이도 읽힌다.** `PUSH20` 두 개가 "누가 부를 수 있나" 와 "어디로 나가나" 를 다 말해 줬다.

**집계 구간을 고정하고 세 숫자를 맞춘다.** 살아 있는 컨트랙트는 계속 변한다. 예치 합계 · 드레인 합계 · 수취 지갑 잔액이 셋 다 일치하는 것이 집계가 옳다는 증명이었다.
