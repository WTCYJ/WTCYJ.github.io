마지막 구간입니다. 로드맵이 정해둔 최종 보고서 목차를 따라 지금까지의 결과를 정리했습니다.

그런데 정리하기 전에 한 가지를 먼저 했습니다. **제 결론을 스스로 무너뜨려 보는 것**입니다. 20주차부터 21주차까지 쌓은 근거를 놓고 "이 관측이 정말 이 패치 때문인가"를 세 방향에서 반박했습니다. 결론은 버텼고, 오히려 증적을 더 단단하게 만들 지점 세 개를 건졌습니다. 그중 가장 값진 건 데이터가 두 설명에 똑같이 들어맞고 있다는 지적이었는데, 세 번째 측정점 하나로 갈렸습니다.

## 배경 개념 - 세 번째 점이 직선을 확정한다

반박에서 나온 지적이 이겁니다.

제가 가진 데이터는 컴포넌트 1개일 때 101, 5개일 때 501 이었습니다. 여기서 "컴포넌트당 100개"라고 결론지었습니다. 그런데 같은 두 점에 들어맞는 설명이 하나 더 있습니다. **"컴포넌트당 100개 + 별도로 전역 500개 천장"** 입니다. C=5 에서는 두 모델이 똑같이 501 을 예측하므로 이 점만으로는 갈리지 않습니다.

이건 측정으로 모델을 고를 때의 기본 문제입니다. 서로 다른 두 모델이 우연히 같은 값을 내는 지점에서 재면, 데이터가 아무리 깨끗해도 둘을 구분할 정보가 없습니다. 가르려면 **두 모델의 예측이 갈라지는 지점**을 골라 재야 합니다. C=3 이 그 지점입니다 — 컴포넌트 모델은 301 을, 전역 천장 모델은 501 을 예측하니, 여기서 나온 값이 곧 판정입니다. 이 결함 자체가 호출자가 자원 소비량을 좌우하는 [CWE-400 계열](https://cwe.mitre.org/data/definitions/400.html)이라, "증폭 계수가 정말 컴포넌트 수에 선형인가"는 완화책의 강도를 정하는 실무 질문이기도 했습니다.

그래서 C=3 을 재봤습니다.

### 3-1. 세 번째 점

| --- | --- | --- | --- |
| 1 | 101 | **101** | 101 |
| 2 | 201 | **201** | 101 |
| 3 | 301 | **301** | 101 |
| 4 | 401 | **401** | 101 |
| 5 | 501 | **501** | 101 |

**301 이 나왔습니다.** 전역 500 천장 모델은 501 을 예측했으니 반증됐습니다. 이제 "컴포넌트 단위로 센다"는 설명만 남습니다.

r05 는 컴포넌트를 몇 개로 늘리든 101 입니다.

> **추가 측정**: 처음에는 C=1·3·5 만 재고 나머지를 한계로 남겨뒀는데, 이후 **C=2·C=4 를 채우고 C=7 까지 늘렸습니다.** 201·401·601·701 로 전부 예측대로였고, 이제 일곱 점이 모두 `100·C+1` 위에 있습니다.
>
> C=2 와 C=4 는 다른 점들과 **같은 하드웨어 구성**으로 돌렸습니다. C=6 과 C=7 은 별칭이 더 필요해 **APK 를 다시 빌드해야 했는데**, 그러면 5-1 에서 지적한 "다른 빌드로 잰 값을 같은 표에 섞기"가 됩니다. 그래서 **각각 같은 새 빌드로 직전 점을 다시 재**(C=6 때는 C=5 → 501, C=7 때는 C=6 → 601) 값이 그대로인 것을 확인하고 나서 표에 올렸습니다. 쓰지 않는 별칭을 매니페스트에 더 선언해도 곡선은 움직이지 않습니다.

## 4. 결과 해석

### 4-1. 최종 결론

패치가 바꾼 것은 **한도의 유무가 아니라 개수를 세는 단위**입니다.

- 패치 전: `getCurrentInstanceCount(ComponentName)` — 호출자가 정하는 값이 카운팅 키
- 패치 후: `getPackageRuleCount(pkg)` — 인증된 신원이 카운팅 키

일반 앱이 매니페스트 권한을 하나도 선언하지 않고, 정책 접근 하나만 받은 상태에서, [`activity-alias`](https://developer.android.com/guide/topics/manifest/activity-alias-element) 를 선언한 수만큼 자동 Zen 규칙([`AutomaticZenRule`](https://developer.android.com/reference/android/app/AutomaticZenRule)) 상한을 곱할 수 있었습니다. 규칙은 시스템 설정 파일에 영속화되므로 재부팅해도 남습니다.

이건 쿼터의 **카운팅 키를 호출자가 정하게 둔** 결함입니다 — 인증된 신원(패키지)이 아니라 호출자가 넘긴 이름(`ComponentName`)으로 셌으니, 같은 앱이 이름만 여러 개 만들어 한도를 곱할 수 있었습니다. 수정은 그 키를 인증된 값으로 바꾼 것이고, **그 값은 이미 같은 레코드에 저장돼 있었습니다.** 새 상태 없이 17줄로 끝난 이유입니다.

### 4-2. 무엇을 확정했고 어디를 경계로 명시했나

배제한 것:

- 한도가 전역이라는 설명 — r05 에서 프로브 100개와 `pkg=android` 2개가 공존(합계 102)
- 전역 500 천장 모델 — C=3 에서 301
- 측정 기법이 만든 인공물 — 위 3-2
- 같은 경로의 다른 코드 변경 — 21주차 클래스 대조

경계로 명시한 것, 그리고 그 경계를 어떻게 관리했는지:

- 이미지 쌍은 단일 변수가 아니라 7개 파일이 다릅니다(커널 포함). 그래서 결론의 무게를 diff 가 아니라 **용량-반응 관계**에 실었습니다 — 부록에서 정식화하지만, 커널·HAL·빌드 지문 중 어느 것도 "거부 순번을 서드파티 매니페스트의 `activity-alias` 개수의 1차 함수로 만드는" 메커니즘을 갖지 않습니다.
- 읽은 코드는 `services.jar` 의 dex 입니다. 이 dex 가 실제로 실행되는 코드라는 점은 **이미 가진 데이터로 부록에서 확정**했습니다(services.vdex 207KB ≪ dex 18MB → 이미지 안의 services dex 사본은 하나뿐).
- `RULE_LIMIT_PER_PACKAGE` 는 `static final int` 라 호출부에 인라인됩니다. 그래서 소스의 상수 이름을 믿지 않고 **디컴파일에서 실제로 남은 리터럴 `> 100`** 을 근거로 삼았습니다.

## 5. 시행착오와 정정

결론을 스스로 반박하며 찾아낸 세 지점을, 측정으로 하나씩 되짚었습니다. 세 번 다 결론은 그대로였지만 근거는 더 단단해졌습니다 — 측정을 세 번 바로잡은 셈이고, 이 자기교정 과정이 이 시리즈에서 제일 값나가는 부분이라 그대로 남깁니다.

### 5-1. 다른 빌드로 잰 값을 같은 표에 넣고 있었다

"컴포넌트 1개 → 101" 행은 별칭 기능을 넣기 **전** 프로브로 측정한 것이었습니다. APK 를 다시 빌드한 시각이 두 측정 사이에 있었습니다.

이걸 잡아낸 방법 자체가 증적 설계의 성과였습니다. 지금 스크립트는 `components(사용한 컴포넌트 수)` 를 무조건 출력하는데, 그 옛 증적 파일에는 **그 줄이 없어서** 다른 빌드로 잰 값임이 바로 드러났습니다. 구버전 APK 는 이미 덮어써졌지만, 결론에 필요한 건 그 옛 값이 아니라 **지금 재현되는 값**이었습니다.

현재 빌드로 다시 쟀더니 101/101 로 같았고, 그 행을 재측정으로 확정했습니다. 결론은 그대로였지만, 여기서 규칙 하나를 세웠습니다 — **표에는 같은 빌드로 잰 값만 올린다.** 서로 다른 도구·빌드로 잰 값을 한 표에 섞지 않는다는 이 규칙이 이후 측정의 기준이 됐습니다.

### 5-2. 증적이 어느 이미지에서 나왔는지 파일명으로만 주장하고 있었다

초기 ceiling 측정 세 건은 프로브 출력만 저장하고 빌드 지문·시작 상태·logcat 을 남기지 않았습니다. `week20-r03-ceiling.txt` 라는 **파일 이름이 사실상 유일한 출처 표시**였습니다.

게다가 r03 ceiling 두 파일은 SHA-256 이 같습니다. 프로브가 변동값을 안 찍도록 설계한 결과라 정상이지만, 파일 내용만 놓고 보면 "다시 재서 같은 값"인지 "파일을 복사"한 것인지가 파일 자신으로는 증명되지 않습니다. 이 자각이 증적 표준을 만들었습니다.

이후 측정(C=1 재실행, C=3)부터는 하네스로 돌려 `fingerprint.txt` 와 시작 상태를 함께 남겨, 각 값이 어느 이미지·어느 부팅에서 나왔는지 파일 스스로 증명하게 했습니다. 초기 세 건은 이 표준을 세우기 전 것이라 출처를 명시해 그대로 두었습니다.

### 5-3. 두 점으로 직선을 그었다

앞에서 적은 그것입니다. "별칭을 늘린 수만큼 증폭된다"는 문장을 두 점만 보고 썼습니다. 위험이 낮긴 했습니다 — 코드에 500 같은 상수가 없고, 501 의 예외 문자열이 우리가 읽은 그 분기에서 나오는 것과 같았으니까요. 그래도 **데이터가 지지하는 것보다 강한 문장**이었습니다.

C=3 을 재고 나서야 그 문장을 쓸 자격이 생겼습니다.

## 마치며

24주를 돌아보면, 이 연구에서 제가 **중간 결론을 여섯 번 고쳤습니다.** 불리틴 표만 보고 CVE 를 고르려던 것, 불리틴이 링크한 커밋이 그 수정이라고 믿은 것, 소스 태그를 보고 배포 이미지를 추론한 것, 백포트의 형태를 짐작한 것, 스냅샷으로 시작 상태를 맞춰도 된다고 본 것, 두 점으로 직선을 그은 것.

여섯 번 다 **틀린 게 결론이 아니라 근거였습니다.** 그리고 여섯 번 다 그럴듯해 보였습니다. 그대로 뒀으면 글에 그대로 실렸을 겁니다.

그래서 마지막에 스스로를 반박해보는 단계를 넣었는데, 그게 세 번째 점을 재게 만들었습니다. 그 뒤로 나머지도 채워 결국 **일곱 점**이 됐습니다. 결론은 안 바뀌었지만 결론의 자격이 바뀌었습니다. 같은 문장이라도 두 점으로 쓴 것과 일곱 점으로 쓴 것은 다릅니다.

가장 오래 남을 것 같은 건 17줄짜리 패치입니다. 자원 한도를 세는 키를 호출자가 정하고 있었고, 제대로 셀 수 있는 값은 이미 같은 레코드에 저장돼 있었습니다. 없어서 못 센 게 아니라 있는데 안 쓰고 있었습니다. 그런 종류의 결함은 앞으로도 보일 것 같습니다.

## 부록 — 게시 후 정정

이 글을 올린 뒤 결론을 한 번 더 적대적으로 검토했습니다. **인과 귀속은 그대로 살아남았지만, 제가 쓴 문장 중 데이터보다 강한 것들이 잡혔습니다.** 고칠 것을 적어둡니다.

### 해소된 한계 하나

본문 4-2 에서 "읽은 코드는 `services.jar` 의 dex 이고, 이게 실행되는 AOT 산출물과 일치하는지"를 경계로 표시하며 부록에서 확정하겠다고 예고했습니다. 그 확정을 여기서 합니다 — 이미 가진 데이터로 답이 나옵니다.

```
services.jar   18,218,029 B   (classes.dex 11.3MB + classes2.dex 6.8MB)
services.vdex     207,876 B
services.odex  44,769,128 B
```

**`services.vdex` 가 207KB 뿐입니다.** dex 두 개가 18MB 인데 vdex 가 그걸 담고 있을 수 없습니다. 즉 이미지 안에 services 의 dex 사본은 jar 안의 것 하나뿐이고, `services.odex` 는 그 dex 에서 [dex2oat 가 AOT 컴파일한](https://source.android.com/docs/core/runtime) 기계어입니다. `.vdex` 는 검증 결과·의존성을 담은 작은 사이드카일 뿐 두 번째 바이트코드 사본이 아니고, 그래서 제가 읽은 것과 다른 바이트코드가 따로 존재하지는 않습니다. system_server 의 부트 클래스패스는 완전 AOT(`speed`)로 컴파일되므로 44MB 짜리 `services.odex` 가 나온 것입니다.

같은 산출물 모델은 별도 에뮬레이터(API33)의 설치 앱에서도 그대로 관측했습니다 — 앱 하나의 dexopt 산출물이 `base.odex`(17,296 B) + `base.vdex`(3,980 B) 로 갈리고 상태가 `status=verify` 였습니다. 여기서 `verify` 는 "검증만 하고 네이티브 코드는 만들지 않는" 필터라, `speed` 로 완전 컴파일된 `services.odex` 와 대비됩니다. 삼중 구조(dex·vdex·odex)는 같아도 컴파일 필터에 따라 odex 안에 든 것이 달라진다는 뜻이고, 뒤집어 말하면 "vdex 가 작다 → dex 사본은 하나뿐"이라는 위 추론은 필터와 무관하게 성립합니다.

남는 것은 dex2oat 가 만든 기계어가 dex 의미를 충실히 구현하는지 — 이건 ART 컴파일러 자체의 정확성 문제라, 개별 CVE 재현이 아니라 컴파일러 감사의 축으로 이번 범위 밖에 명시해 둡니다. 무엇을 읽었는지(dex)와 그것이 실행되는 코드라는 점(위 용량 논증)은 확정했고, 컴파일러 신뢰는 별개 축으로 남깁니다.

### 정정 세 가지

**하나.** "두 이미지가 다른 파일은 7개"는 **이미지 디렉터리 최상위 기준**입니다. `system.img` 를 풀어 안쪽 파일 단위로 보면 차이는 훨씬 많고, 대부분 AOT 재컴파일 산출물입니다. 읽는 분이 "이 시스템에서 다른 건 일곱 개뿐"으로 받아들일 소지가 있어 하네스가 출력하는 문구도 함께 고쳤습니다.

**둘.** `services.jar` 전체로 보면 **여러 클래스의 실행 코드가 다릅니다.** 제가 확인한 것은 "자동 Zen 규칙 등록 경로에 걸리는 클래스 중에서는 `ZenModeHelper` 하나만 다르다"이지, "이 jar 가 이 패치만 다르다"가 아닙니다. 나머지는 2022-08 에서 2022-10 사이의 다른 수정들입니다.

**셋.** 증폭은 **컴포넌트 1~7 에서 확인했고 실측한 최대 누적은 규칙 700개**입니다. "별칭을 늘린 수만큼"이라는 표현은 그 범위 안에서만 유효합니다. (처음에는 1·3·5 만 재고 이렇게 적었는데, 이후 2·4 를 채우고 6·7 까지 늘렸습니다.)

### 함께 발견한 것

같은 notification 패키지에 **이 CVE 와 무관한 별개 보안 수정**이 함께 들어 있습니다.

```java
// SnoozeHelper — r05 에만 있음
static final int CONCURRENT_SNOOZE_LIMIT = 500;

protected boolean canSnooze(int numberToSnooze) {
    synchronized (this.mLock) {
        if (this.mPackages.size() + numberToSnooze > 500) return false;
        return true;
    }
}
```

공교롭게도 이것도 자원 한도 수정입니다. 같은 달 같은 패키지에 한도 관련 수정이 둘 들어온 셈인데, **"notification 쪽이 바뀌었으니 이 CVE 패치겠지"로 읽으면 틀립니다.** 21주차에 `NotificationManagerService` 의 36줄을 "무관한 snooze 수정"이라고만 적고 넘어갔는데, 그게 실은 별도의 보안 수정이었습니다.

### 유지되는 것

- `ZenModeHelper` 의 **17줄**(삭제 1 + 추가 16)은 추가된 줄을 하나씩 다시 세어 확인했습니다.
- 인과 귀속은 그대로입니다. 다만 근거의 무게가 어디 있는지는 분명히 해두는 편이 낫겠습니다. **diff 가 아니라 용량-반응 관계입니다.** 컴포넌트 수 1, 3, 5 에서 패치 전이 101 / 301 / 501 이고 패치 후는 셋 다 101 입니다. 커널이나 HAL 이나 빌드 지문 중 어떤 것도 "거부 순번을 서드파티 앱 매니페스트의 `activity-alias` 개수의 1차 함수로 만드는" 메커니즘을 갖지 않습니다.

### 도구 수정

증적으로 남는 `comparison.md` 에 **"이 하네스는 스냅샷 복원으로 시작 상태를 맞추므로"** 라는 문장이 남아 있었습니다. 19주차에 냉부팅으로 바꾼 뒤였는데 경고 문구만 고치지 않은 것입니다. 같은 파일의 표에 `start_state=wipe-data-냉부팅` 이 찍혀 있어서 자기 모순이었습니다.

문구는 고쳤지만 **이미 생성된 증적 파일에는 그 문장이 남아 있습니다.** 그 파일들을 볼 때는 본문의 표와 `boot.txt` 를 기준으로 읽어야 합니다.

이번 검토에서 배운 것이 하나 더 있다면, **틀린 것은 결론이 아니라 결론을 감싼 문장들이었다**는 점입니다. 앞선 회차들에서는 근거가 틀렸는데, 이번엔 근거는 맞고 표현이 앞서 있었습니다.
