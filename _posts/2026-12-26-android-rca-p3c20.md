취약점 보고서를 받아 읽는 트라이아저는 하루에 수십 건을 본다. 그중 만점 심각도로 접수되는 보고서는 예외 없이 **깨진 invariant를 지목하고, 독자가 위험을 스스로 재계산하도록** 적은 것들이다. 반대로 "앱이 죽습니다 + 크래시 로그"만 붙은 보고서는 대개 DoS로 강등되거나 재현 불가로 마감된다. 크래시는 증상일 뿐, 보고서의 값어치는 그 뒤의 사슬에 있다.

이 글은 파트 3에서 쌓은 RCA 조각들 — 증상/트리거/폴트사이트/근본원인 구분, security invariant, 크래시와 익스플로잇 가능성 구분, 증거 등급 — 을 하나의 **제출 가능한 근본원인 보고서**로 조립하는 방법을 정리한 기록이다. 파트 3의 마지막 장이자, 방법론을 실제 산출물로 바꾸는 장이다.

> **한 줄 결론**: 제출 가능한 RCA 보고서는 "무엇이 크래시했다"가 아니라 "어떤 invariant가, 어디서, 왜 깨졌고, 그 결과 어떤 프리미티브가 생기는가"를 재현·재계산 가능하게 적은 문서다. 관측과 주장을 분리하지 못하면 신뢰를 잃고 전체가 강등된다.

## 무엇을 다루고, 무엇을 알아야 하는가

이 글은 개별 분석 결과를 하나의 보고서 골격으로 조립하고, 심각도를 **정직하게** 산정하며, 증거를 등급과 함께 제시하는 방법을 다룬다. 다섯 가지 선수 개념이 밑에 깔린다. 1장의 **증상→트리거→폴트사이트→근본원인** 사슬은 "근본 원인" 절의 뼈대가 되고, 2장의 **security invariant**는 "무엇이 깨졌나"를 한 문장으로 만든다. 7장의 **크래시와 익스플로잇 가능성 구분**은 영향 클래스와 CVSS를 정직하게 묶는 근거이고, 16·17장의 **patch diff·variant analysis**는 패치 절을, 19장의 **증거 등급·Confidence**는 증거 절을 채운다. 완화 배경은 Atlas C37을 참조한다.

전체 구조에서 이 장은 **파트 3의 종착점**이다. 앞의 열아홉 장이 "어떻게 원인을 찾는가"였다면, 이 장은 "찾은 것을 어떻게 남이 검증할 수 있게 넘기는가"다. 안전 범위는 파트 3 전체와 동일하다 — 자작 결함 앱, 에뮬레이터/Cuttlefish, 이미 패치된 공개 CVE, 명시적 허가 대상. 무기화된 완성 익스플로잇·실데이터·지속성·전파는 다루지 않는다.

## 핵심 개념 — 보고서 골격과 정직한 심각도

제출 가능한 RCA 보고서는 아래 절들을 순서대로 채운다. 각 절이 파트 3의 어느 장에서 온 산출물인지 함께 표기한다.

| 절 | 무엇을 적나 | 근거 장 |
|--|--|--|
| 요약 | 한 줄: 깨진 invariant + 영향 클래스 + 심각도 | 2장 |
| 영향·심각도 | 영향 클래스(RCE/EoP/ID/DoS) + CVSS 벡터·점수 | 7장 |
| 대상 | 컴포넌트·버전·보안 패치 레벨·ABI | — |
| 재현 | 최소 재현·환경·개념 수준 PoC | 6장 |
| 근본 원인 | 증상→트리거→폴트사이트→근본원인 사슬, 파일:함수:라인 | 1장 |
| 증거 | tombstone/ASan/KASAN/logcat + 등급·Confidence | 19장 |
| 익스플로잇 가능성 | 존재를 증명한 프리미티브까지, 정직한 경계 | 7장 |
| 패치·변종 | patch diff·Patch Invariant·variant analysis | 16·17장 |

영향 클래스는 Android Security Bulletin의 분류를 그대로 쓴다 — **RCE**(원격 코드 실행), **EoP**(권한 상승), **ID**(정보 노출), **DoS**(서비스 거부). 각 CVE 항목이 유형·심각도·영향 버전·참조 버그 ID로 구성된다. `Source-confirmed`

심각도는 CVSS v3.1 벡터로 적되, **벡터와 점수가 서로 재계산 가능해야** 한다. 예를 들어 익스포트 컴포넌트에 조작 입력을 넣어 그 컴포넌트가 죽는 로컬 DoS는 `AV:L/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H`이고, FIRST 계산기로 돌리면 Base **6.2(Medium)**가 나온다. `Source-confirmed` 여기서 흔한 부풀리기 하나 — 같은 크래시를 근거 없이 `C:H/I:H/A:H`로 올리면 Base가 **8.4(High)**로 뛰지만, 정보 노출·무결성 침해를 **증명하지 못했다면** 그 벡터는 허위다. 트라이아저는 벡터를 다시 계산해 보므로, 증명 못 한 축은 반드시 `N`으로 둔다.

> **[그림 1]** FIRST CVSS v3.1 계산기에 `AV:L/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H`를 입력해 Base 6.2(Medium)가 나온 화면 — *실측 스크린샷 자리*

## 신뢰 경계와 위협 모델

보고서의 위협 모델은 "누가 이 표면에 도달하는가"다. 같은 크래시라도 **트리거 주체**에 따라 심각도가 완전히 갈린다. 익스포트된 컴포넌트를 임의의 제3자 앱이 죽일 수 있으면 신뢰 경계를 넘는 DoS지만, 죽는 것이 내 앱 자신이라면 자기-DoS라 대개 반려된다. 시스템 프로세스(system_server 등)를 죽이면 심각도가 크게 오르고, 앱 하나면 낮다. 보고서의 "대상" 절에 **어느 프로세스가, 어느 신뢰 경계 너머에서** 죽는지를 못 박아야 하는 이유다. `Inferred`

## 분석 — 자작 결함 앱으로 조립한 미니 보고서

에뮬레이터에 올린 자작 결함 앱(`com.wtcy.flawed`)을 예로, 위 골격이 실제로 어떻게 채워지는지 본다. 이 앱은 익스포트 액티비티가 Intent extra의 배열 인덱스를 검증 없이 읽는 로직 버그를 심어 둔 것이다.

- **증상** — 앱 프로세스가 `FATAL EXCEPTION`으로 종료.
- **트리거** — 특정 extra를 담은 Intent를 외부 앱이 전송.
- **폴트사이트** — 예외를 던진 프레임(스택 최상단), 즉 `Parser.readField`.
- **근본 원인** — "공격자 통제 인덱스는 접근 전 경계 검사되어야 한다"는 invariant가 깨짐.

logcat에서 폴트사이트를 확인한다.

```
예시 출력(교체)
FATAL EXCEPTION: main
Process: com.wtcy.flawed, PID: 12345
java.lang.ArrayIndexOutOfBoundsException: length=8; index=64
    at com.wtcy.flawed.Parser.readField(Parser.java:41)
    at com.wtcy.flawed.ExportedActivity.onCreate(ExportedActivity.java:27)
```

스택 최상단 프레임 `Parser.java:41`이 폴트사이트다. 이것이 곧 근본 원인은 아니다 — 근본 원인은 그 라인에 도달하도록 인덱스 검사를 생략한 데이터 흐름이고, 폴트사이트는 그 흐름이 터진 지점일 뿐이다(1장의 구분). 두 배열 로그(`length=8; index=64`)가 인덱스가 경계를 넘었다는 직접 증거다.

> **[그림 2]** 자작 결함 앱을 에뮬레이터에서 크래시시킨 뒤 얻은 logcat에서 backtrace 최상단 프레임(폴트사이트)을 표시한 캡처 — *실측 스크린샷 자리*

**익스플로잇 가능성.** 여기서 확보된 것은 **크래시 프리미티브**(제어된 예외로 인한 프로세스 종료)까지다. 임의 메모리 읽기·쓰기나 제어 흐름 탈취는 증명되지 않았다. 그러므로 영향 클래스는 DoS, CVSS는 앞의 `A:H`만 세운 6.2(Medium)로 남는다. Java 예외 경로의 크래시를 네이티브 메모리 손상처럼 적으면 재현 단계에서 바로 들통난다 — ASan/KASAN 흔적이 없기 때문이다. `Inferred`

## Root Cause — 왜 이렇게 되는가

여기서의 "근본 원인"은 취약점이 아니라 **보고서가 반려되는 이유**다. 잘 찾은 결함도 아래 넷 중 하나만 어기면 강등된다.

- **증상과 근본원인을 섞음** — "앱이 죽는다"만 적고 어떤 invariant가 깨졌는지 없으면, 트라이아저가 위험을 재구성할 수 없어 DoS로 강등하거나 반려한다.
- **영향 과장** — 크래시를 RCE로, CVSS 벡터를 증거 없이 올리면 계산이 안 맞고, 한 축이 무너지면 보고서 전체 신뢰가 무너진다.
- **재현 불가** — 최소 재현·환경(이미지 태그·API·ABI)·개념 PoC가 없으면 `NOT REPRODUCIBLE`로 마감된다.
- **증거 등급 부재** — 추론을 사실처럼 적으면(19장), 한 곳만 틀려도 나머지 관측까지 의심받는다.

공통 뿌리는 하나다 — 보고서가 **관측(무엇을 봤나)과 주장(그래서 무슨 위험인가)을 분리하지 못하고**, 독자가 위험을 재계산할 수 있는 형태로 넘기지 못한 것. 골격의 각 절과 증거 등급 라벨은 바로 이 분리를 강제하기 위한 장치다.

## 방어와 회귀 검증

- **개념 수준 PoC만.** 원리를 이해시키는 최소 트리거까지다. 지속성·전파·AV 우회·C2 같은 무기화는 넣지 않는다 — 프리미티브의 **존재**를 보이는 것과 완성된 공격을 넘기는 것은 다르다.
- **최소 재현 + 스냅샷 기준선.** 에뮬레이터 Quick Boot 스냅샷에서 시작해 "이 입력 → 이 크래시"가 환경 오염 없이 재현됨을 보인다(6장의 입력 축소와 짝).
- **회귀 테스트를 증거로 첨부.** 패치 전 크래시 / 패치 후 정상을 나란히 붙이면, 그 자체가 Patch Invariant 검증(16장)이자 보고서의 가장 강한 증거가 된다.
- **공개 정책 준수.** 벤더 통보 → 유예 기간 → 공개 순서를 지키고, 실습·재현은 자작 앱·에뮬·이미 패치된 공개 CVE로만 한다. Android Security Rewards 계열 프로그램은 근본 원인 분석과 재현 가능한 PoC가 붙은 보고서에 더 높은 등급·보상을 부여한다(구체 금액·배수는 프로그램 규칙 원문 확인 필요). `Reported`

## 정리

- 보고서의 값어치는 크래시 로그가 아니라 **깨진 invariant + 폴트사이트 + 정직한 영향**의 재현·재계산 가능성에 있다.
- CVSS는 벡터와 점수가 서로 재계산되게 적고, 증명 못 한 영향 축은 `N`으로 둔다 — 부풀린 한 축이 전체를 강등시킨다.
- 관측(증거 등급 라벨)과 주장(영향·익스플로잇 가능성)을 절 단위로 분리하는 것이 반려를 막는 유일한 장치다.
- PoC는 프리미티브 존재까지, 무기화 없이. 회귀 테스트가 가장 강한 증거다.

**점검 질문** — (1) 폴트사이트와 근본 원인을 각각 보고서 어느 절에 적고, 둘은 어떻게 다른가? (2) Java 예외 DoS를 `C:H/I:H`로 올리면 CVSS가 어떻게 바뀌며, 그 벡터가 허위인 이유는? (3) 자작 결함 앱의 자기-DoS가 대개 반려되는 이유는 무엇이고, 무엇이 바뀌면 접수 가능해지는가?
