> S16까지 앱을 뜯는 쪽이었다면, 난독화는 그걸 늦추려는 방어입니다. 어디까지 늦추고 어디서 멈추는지, 같은 앱의 난독화 전후를 나란히 놓고 봤습니다.

R8(옛 ProGuard)은 안드로이드 릴리스 빌드의 기본 난독화·축소 도구입니다. 클래스·메서드·필드 이름을 짧은 기호로 바꿔 디컴파일 결과를 읽기 어렵게 만듭니다. 그런데 "읽기 어렵게"가 어디까지인지가 중요합니다. 이름은 바뀌지만 문자열은 그대로고, 서명·무결성 검사 같은 안티탬퍼도 클라이언트에 있는 한 뒤집힙니다. 같은 앱을 난독화 전/후로 빌드해 이 경계를 확인했습니다.

---

## 실습 목표

- 같은 앱을 R8 난독화 전(d8)과 후(R8)로 빌드한다.
- 리플렉션으로 자기 메서드 이름을 찍어 이름 변화를 본다.
- 코드에 박힌 비밀 문자열이 난독화 후에도 남는지 확인한다.
- 서명 검증·무결성 검사 같은 안티탬퍼의 한계를 정리한다.

---

## 윤리적 범위와 허가 조건

대상은 내가 직접 작성한 데모 앱(`com.aas.obf`)입니다. 난독화 전후 두 빌드 모두 `aas-api33` 에뮬레이터에서만 실행했습니다.

---

## 환경 및 도구 버전

- R8 8.10.9(build-tools 36.0.0의 `d8.jar`), d8(비난독)과 비교
- 대상 기기: `aas-api33` (S01)
- 앱 빌드: S05 툴체인

---

## 위협 모델 — 난독화는 무엇을 지키나

- 난독화가 무엇을 바꾸는가(이름? 문자열? 로직?)?
- 코드에 박힌 비밀이 난독화로 숨는가?
- 안티탬퍼(서명·무결성)가 방어가 되는가?

---

## 재현 절차

### 1. 같은 앱, 두 빌드

메서드 몇 개(비밀 반환, 무결성 검사, 서명 해시)와 리플렉션으로 자기 메서드 이름을 찍는 `onCreate`를 가진 앱을 만들었습니다. 이걸 두 번 빌드합니다.

- v1: `d8`로 그대로(비난독).
- v2: `R8`로 난독화. keep 규칙은 진입점만 남기고 나머지는 이름을 바꾸게 뒀습니다.

```
# R8 규칙 (v2)
-keep class com.aas.obf.MainActivity { <init>(); protected void onCreate(android.os.Bundle); }
-dontoptimize
```

### 2. 이름 변화 — 리플렉션으로

두 빌드를 각각 실행해 `getDeclaredMethods()`로 자기 메서드 이름을 찍었습니다.

```
v1 (비난독): buildSignatureHash(), getApiKey(), onCreate(), verifyIntegrity()
v2 (R8):     a(), b(), c(), onCreate()
```

`getApiKey`·`verifyIntegrity`·`buildSignatureHash`가 `a`·`b`·`c`로 바뀌었습니다(keep한 `onCreate`만 이름 유지). 디컴파일러로 봐도 의미 있는 이름 대신 기호만 보이니, 코드를 읽는 비용이 올라갑니다. 여기까지가 난독화가 하는 일입니다.

### 3. 문자열은 그대로

정작 중요한 비밀은 어떻게 됐을까요. 코드에 박힌 API 키 문자열을 두 빌드의 DEX에서 찾아봤습니다.

```console
$ strings v1/classes.dex | grep APIKEY   ->  APIKEY-9f3c-SECRET
$ strings v2/classes.dex | grep APIKEY   ->  APIKEY-9f3c-SECRET
```

난독화 후에도 그대로 있습니다. R8은 기본적으로 문자열을 암호화하지 않습니다. 이름은 바꿔도 문자열 상수는 손대지 않으니, 하드코딩된 비밀은 난독화로 숨지 않습니다. 화면에서도 두 빌드 모두 같은 `APIKEY-9f3c-SECRET`을 찍었습니다.

## 안티탬퍼(서명·무결성)에 대해

난독화와 함께 자주 쓰이는 게 안티탬퍼입니다. 앱이 자기 서명(S02의 `apksigner`가 확인하던 그 서명)이나 코드 해시를 런타임에 검사해, 변조·재패키징을 막으려 합니다. 원리는 이렇습니다.

- 서명 검증: `PackageManager`로 자기 서명 인증서를 읽어 기대값과 비교. 재패키징하면 서명이 바뀌니 잡겠다는 것.
- 무결성 검사: DEX·리소스의 해시를 계산해 기대값과 비교.

문제는 이 검사도 결국 클라이언트에서 boolean 하나로 끝난다는 것입니다. S14에서 본 대로 그 반환을 Frida로 뒤집거나, smali를 패치해 검사를 건너뛰면 됩니다. 기대 해시·기대 서명 값도 앱 안에 있으니 그것까지 바꿀 수 있습니다. 난독화가 이걸 조금 더 귀찮게 만들 뿐, 넘지 못하는 벽은 아닙니다.

## 관측 결과

- R8 난독화로 메서드 이름이 `a`·`b`·`c`로 바뀌었다(리플렉션으로 확인). keep한 `onCreate`만 이름을 유지했다.
- 코드에 박힌 비밀 문자열은 난독화 전후 DEX 모두에 그대로 있었다. R8은 문자열을 암호화하지 않는다.
- 서명·무결성 검사도 클라이언트 판정이라, 뒤집거나 건너뛸 수 있다.

---

## 근본 원인과 보안 영향

- 난독화는 리버싱 비용을 올리는 지연책입니다. 이름을 가려 읽기를 어렵게 하지만, 문자열·로직·동작은 그대로라 시간과 도구를 들이면 복구됩니다.
- 그래서 난독화를 "보안 경계"로 오해하면 안 됩니다. 하드코딩된 비밀은 난독화해도 새고, 안티탬퍼는 클라이언트에 있는 한 우회됩니다.
- 난독화·안티탬퍼는 방어의 보조일 뿐, 근본 방어는 앞선 편들과 같습니다 — 비밀은 서버·Keystore로, 판정은 서버로.

## 수정 방법 / 권고

- 난독화(R8)는 켜되, 그것에 기대어 비밀을 코드에 두지 않는다. 하드코딩 비밀 제거가 먼저다(S04).
- 정말 문자열을 가려야 하면 문자열 암호화를 별도로 적용하되, 이 역시 지연책임을 안다.
- 안티탬퍼는 부가 신호로만 쓰고, 우회 가능성을 전제로 서버 측 검증(Play Integrity, S15)에 무게를 둔다.

---

## 재검증

같은 소스를 d8과 R8로 빌드해, 리플렉션 메서드 이름이 `getApiKey/...` ↔ `a/b/c`로 갈리는 걸 두 화면으로 확인했습니다. 그리고 비밀 문자열은 두 DEX 모두에서 그대로 나왔습니다. 이름은 바뀌고 문자열은 남는다는 게 화면과 DEX 양쪽에서 확인됩니다.
