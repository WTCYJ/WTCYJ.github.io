리버싱 문제를 풀다 보면 가끔 '이걸 어떻게 이렇게까지 꼬아놨지' 싶은 게 있습니다. o-o-overflow(OOO)가 DEF CON 2019 예선에 낸 안드로이드 문제 [Vitor](https://github.com/o-o-overflow/dc2019q-vitor-public)가 딱 그랬습니다. 출제자가 저장소 README에 "Matryoshka-style Android reversing chall"이라고 적어놨는데, 러시아 인형이라는 비유가 과장이 아니었습니다. 앱 하나를 열면 암호화된 스테이지가 안에 들어 있고, 그걸 풀면 또 다른 성격의 스테이지가 나오고, 그게 또 다음을 품고 있습니다. 그렇게 여섯 겹이었습니다.

더 고약한 건 각 겹의 복호 키가 전부 입력 플래그에서 파생되도록 엮여 있다는 점이었습니다. 그러니까 "플래그를 넣으면 앱이 맞는지 확인해주는" 흔한 구조가 아니라, 반대로 각 겹을 깨끗하게 복호할 수 있는 키 조합을 역으로 찾아내면 그 제약들이 모여 플래그가 복원되는 구조였죠. 공개된 소스와 공식 APK를 받아서, 각 겹을 전부 벗기고 플래그를 되맞춘 과정을 정리합니다.

## 여섯 겹이 뭐로 되어 있나

출제자가 붙인 단계 이름이 그대로 성격을 말해줍니다.

```text
P0 : 메인 앱        - APK / Java, 사용자가 플래그를 입력
P1 : DEX 바이트코드  - DexClassLoader 로 동적 로드
P2 : .so           - libnative-lib.so, 32비트 x86 ELF (JNI)
P3 : 쉘코드         - 생 x86 머신코드
P4 : ROP 체인       - 가젯 + 상대 오프셋
P5 : 자바스크립트    - WebView 안에서 실행
```

실행 패러다임이 `자바 → DEX → 네이티브 → 쉘코드 → ROP → JS`로 계속 바뀝니다. 한 겹을 이해했다고 다음 겹에서 같은 도구가 통하지 않는다는 뜻이기도 하죠. 그리고 각 겹 n은 다음 겹 n+1을 자기 키 Kn으로 복호해서 실행합니다.

플래그 구조부터 보면 이야기가 풀립니다. 플래그는 `OOO{` + 40글자 본문 + `}` 꼴이고, 본문 40글자는 4바이트씩 열 덩어리(f1부터 f10)로 쪼개집니다. 이 중 뒤쪽 다섯 덩어리는 사실상 알려진 값이었습니다. 마지막 겹인 P5 자바스크립트가 플래그 꼬리를 `" => pHd_1w_e4rL13r;)"`와 비교하거든요. 그러니 f6부터 f10까지는 처음부터 손에 쥐고 시작하는 셈입니다. 진짜로 캐내야 하는 건 앞의 다섯 덩어리, f1~f5였습니다.

키가 어떻게 플래그에서 나오는지는 각 겹의 소스에 그대로 박혀 있습니다. 메인 앱의 `fc.g0`는 열 덩어리를 전부 XOR 합니다.

```java
// P0: K0 = 모든 덩어리 XOR
for (i = 0; i < 10; i++)
    for (j = 0; j < 4; j++)
        K0[j] ^= fb[4*i + j];
```

P1(DEX)은 짝수 덩어리만, 네이티브 P2는 3의 배수 덩어리만 XOR 하는 식으로, 겹마다 다른 덩어리 조합을 씁니다. 정리하면 이렇게 됩니다.

```text
K0 = f1⊕f2⊕f3⊕f4⊕f5⊕f6⊕f7⊕f8⊕f9⊕f10   (모든 덩어리)
K1 = f2⊕f4⊕f6⊕f8⊕f10
K2 = f3⊕f6⊕f9
K3 = f4⊕f8
K4 = f5⊕f10
```

여기서 역산 경로가 보입니다. f6~f10을 이미 알고 있으니, K4를 알면 f5가, K3를 알면 f4가, K2를 알면 f3가 바로 떨어집니다. f2는 K1과 (이미 구한) f4로, f1은 K0과 나머지 전부로 풀립니다. 결국 다섯 키 K0~K4만 손에 넣으면 플래그가 완성됩니다. 그래서 이 문제의 본질은 "각 겹의 복호 키를 복호문이 아니라 암호문에서 거꾸로 캐낼 수 있느냐"로 귀결됩니다.

## 빌드와 작업 환경에 대한 메모

저장소에는 소스만 있는 게 아니라 빌드 스크립트와 완성된 `vitor.apk`, 그리고 암호화된 스테이지들이 랜덤한 파일명으로 들어 있는 assets 폴더까지 다 들어 있습니다. 어떤 asset이 어느 겹인지는 `build.sh`가 친절하게 알려줍니다. P1은 `ckxalskuaewlkszdva`, P2는 `mmdffuoscjdamcnssn`, P3는 400바이트짜리 `xtszswemcwohpluqmi`, P5는 `cxnvhaekljlkjxxqkq`였고 나머지는 눈속임용 더미였습니다.

원래는 `build.sh`로 처음부터 다시 빌드해보려 했는데, 2019년산 빌드 스택이 2026년 머신과 정면으로 부딪혔습니다. 래퍼가 Gradle 5.1.1에 AGP 3.4.0을 쓰는데 이 조합은 Java 8~11만 받고, 지금 이 PC엔 Java 21과 26밖에 없더군요. compileSdk 28 플랫폼도 설치돼 있지 않았고요. 여기에 옛 NDK까지 맞춰 가며 죽은 툴체인을 되살리는 건 투자 대비 소득이 안 맞는 삽질이라, 그 길은 접었습니다.

대신 패키징을 repo의 실제 코드로 재현하는 쪽을 택했습니다. 저장소의 암호화기 `Cryptor.java`를 그대로 컴파일해서, 나중에 벗겨낸 평문 스테이지를 복원한 키로 다시 암호화해봤더니 배포된 asset과 바이트 하나까지 똑같이 떨어졌습니다. 네이티브 쪽도 마찬가지로, 32비트 x86 하네스를 직접 만들어 쉘코드를 돌렸습니다. 공식 APK는 어차피 이 소스로 빌드된 같은 산출물이니, "처음부터 다시 조립하는" 부분은 이렇게 더 확실한 방법으로 메웠습니다.

## 바깥 두 겹, AES를 브루트포스로

P1과 P2는 둘 다 AES-128-CBC로 암호화돼 있습니다. 키는 4바이트짜리 Kx를 MD5한 값이고, IV는 `13 37 13 37 ...`로 고정이었습니다. 겉보기엔 AES라 막막하지만, 키 공간이 생각보다 훨씬 좁습니다. Kx가 ASCII 플래그 덩어리들의 XOR이라 각 바이트의 최상위 비트가 항상 0이거든요. 4바이트 전부 0x00~0x7f 범위라 실질 키 공간은 2²⁸밖에 안 됩니다.

여기에 '다음 겹이 어떻게 생겼는지 안다'는 힌트가 결정타였습니다. P1을 복호하면 APK(즉 ZIP)가 나와야 하니 첫 바이트가 `PK\x03\x04`일 테고, P2는 ELF라 `\x7fELF`로 시작할 테죠. 그러면 후보 키마다 첫 블록만 복호해서 매직바이트가 맞는지 보면 됩니다. AES-CBC의 첫 평문 블록은 `AES_decrypt(C0) ⊕ IV` 한 번이면 나오니까 후보 하나당 연산이 MD5 한 번 + AES 블록 한 번뿐입니다.

파이썬으로는 2²⁸을 돌리기 벅차서 OpenSSL 붙인 C로 짜고 OpenMP로 코어를 다 썼습니다.

```c
unsigned char K[4] = { i&0x7f, (i>>7)&0x7f, (i>>14)&0x7f, (i>>21)&0x7f };
MD5(K, 4, md);
AES_set_decrypt_key(md, 128, &ak);
AES_decrypt(C0_p1, pb, &ak);        // 첫 블록만
if ((pb[0]^IV[0])==0x50 && (pb[1]^IV[1])==0x4b &&
    (pb[2]^IV[2])==0x03 && (pb[3]^IV[3])==0x04) { /* K0 발견 */ }
```

10코어에서 9초 남짓 만에 둘 다 나왔습니다. K0은 `17012f03`, K1은 `3c274360`. 이 두 키가 플래그의 앞 두 덩어리 f1, f2를 쥐고 있는 열쇠였습니다.

복호한 P1은 정말로 `classes.dex`를 담은 APK였고, 그 안에 `ooo.p1.P1` 클래스가 들어 있었습니다. P2는 32비트 x86 ELF 공유 라이브러리였고 `Java_ooo_p1_P1_xxx` JNI 심볼을 그대로 달고 있었죠.

![복호한 스테이지들의 파일 타입과 심볼 확인 — p1.apk는 classes.dex를 담은 APK, p2.so는 Intel 80386 ELF32에 Java_ooo_p1_P1_xxx 심볼, p3.bin은 32바이트 NOP 슬레드 뒤에 위치 독립 셀프 로케이터가 이어지는 쉘코드](/assets/img/vitor/stages.png)

앱 쪽 흐름을 따라가 보면, 메인 액티비티가 입력 플래그로 K0을 만들어 P1을 AES 복호한 다음 `DexClassLoader`로 로드하고 `ooo.p1.P1.cf`를 부릅니다.

```java
byte[] K0 = g0(flag.substring(4, 44));
File p1 = dp1(ma, p1Enc, K0);                 // AES-CBC 복호 -> DEX
DexClassLoader cl = new DexClassLoader(p1..., parent);
Class<?> c = cl.loadClass("ooo.p1.P1");
c.getDeclaredMethod("cf", Context.class, String.class).invoke(c, ctx, flag);
```

그 P1이 다시 K1으로 P2(.so)를 복호해 `System.loadLibrary`로 올리고, 네이티브 함수 `xxx`로 넘어갑니다. 겹이 하나씩 벗겨지는 게 코드에서도 그대로 보입니다.

## 네이티브로 내려가서, 쉘코드와 ROP

P2의 네이티브 코드는 여기서 더 날것으로 내려갑니다. 400바이트짜리 P3를 RWX로 mmap 한 메모리에 올리고, 플래그에서 K2를 계산해 복호한 뒤 그대로 함수처럼 점프합니다.

```c
unsigned int g2(unsigned char *flag) {       // K2 = f3⊕f6⊕f9
    unsigned int K2 = 0;  flag += 4;          // OOO{ 건너뛰기
    for (int i = 3; i < 10; i += 3)
        K2 ^= *((unsigned int *)&flag[4*(i-1)]);
    return K2;
}
void dp3(unsigned char *p3, unsigned int K2) {  // 롤링 XOR
    for (int i = 0; i < 100; i++) {
        *((unsigned int*)(p3 + 4*i)) ^= K2;
        K2 += 0x31333337;
    }
}
```

P3는 AES가 아니라 이렇게 K2로 시작해서 4바이트마다 `0x31333337`씩 더해가며 XOR 하는 롤링 방식이었습니다. 그런데 이 겹은 브루트포스조차 필요 없었습니다. 쉘코드가 32바이트 NOP 슬레드로 시작하니까요. 즉 첫 4바이트 평문이 `0x90909090`인 게 확정이라, K2는 암호문 첫 더블워드에서 그걸 XOR 해주면 바로 나옵니다. 출제자가 `native-lib.cpp`에 "909090을 기대하라고 알려주려고 이 주석을 남긴다"고 친절하게 적어두기까지 했더군요.

복호한 P3를 디스어셈블하면 교과서 같은 위치 독립 쉘코드가 보입니다. `call` 한 번으로 자기 주소를 스택에서 꺼내 기준점을 잡고, 플래그에서 K3를 계산한 다음, 자기 몸통 뒤쪽에 숨겨둔 P4를 그 자리에서 복호합니다.

```nasm
call myself
myself:
    pop  ebx                 ; ebx = _start (자기 위치)
    sub  ebx, 5
    sub  ebx, 32             ; NOP 슬레드 보정
    mov  edi, [esp+4]        ; edi = flag
    xor  ecx, ecx            ; K3 계산 시작 (f4 ⊕ f8)
```

P4, 즉 ROP 가젯과 체인은 P3 안에서 또 한 겹 K3로 XOR 돼 있었습니다. 이 겹도 알려진 평문으로 풀립니다. 가젯 영역의 첫 가젯이 `mov eax, 0; ret`, 바이트로 `b8 00 00 00 00 c3`이니 첫 더블워드가 `00 00 00 b8`인 걸 알거든요. 그걸로 K3를 뽑아 복호하면 자잘한 가젯들이 줄줄이 드러납니다.

```nasm
b8 00 00 00 00  mov eax, 0 ; ret
83 c0 04  c3    add eax, 4 ; ret
31 0e     c3    xor [esi], ecx ; ret     ; <- P5 복호의 핵심
83 c6 04  c3    add esi, 4 ; ret
c1 c1 08  c3    rol ecx, 8 ; ret         ; 키 스케줄
33 4f 14  c3    xor ecx, [edi+0x14] ; ret ; f5
33 4f 28  c3    xor ecx, [edi+0x28] ; ret ; f10
```

마지막 두 가젯이 재미있습니다. `[edi+0x14]`는 플래그의 f5, `[edi+0x28]`은 f10을 가리키니, ROP 체인이 실행 중에 `K4 = f5 ⊕ f10`을 만들어내는 겁니다. 그리고 `rol ecx, 8`로 키를 돌려가며 `xor [esi], ecx`로 P5를 한 더블워드씩 복호합니다. 빌드 때 쓰인 암호화기는 키를 "바이트 단위로 오른쪽 회전"시키는데, 32비트 레지스터를 왼쪽으로 8비트 돌리는 `rol ecx,8`이 리틀엔디언에서 정확히 그 바이트 회전과 같습니다. 양쪽이 깔끔하게 맞아떨어지죠.

## 마지막 겹, 난독화된 자바스크립트

P5는 다시 평범한(?) 웹의 세계로 돌아옵니다. K4로 복호하면 나오는 건 HTML 한 조각인데, `<html>`로 시작하는 게 확정이라 K4도 첫 더블워드에서 바로 떨어집니다. 안을 열어보면 자바스크립트가 obfuscator로 한 번 꼬여 있었지만, 하는 일은 단순했습니다. URL로 넘어온 플래그의 꼬리를 `" => pHd_1w_e4rL13r;)}"`와 비교해서 맞으면 `JSInterface.setFlagAsValid()`를 부르는 것.

```javascript
theflag = findGetParameter('flag');
if (theflag.substr(0x18) == ' => pHd_1w_e4rL13r;)}')
    window['JSInterface']['setFlagAsValid']();
```

즉 P5는 이미 알려진 꼬리만 확인합니다. 진짜 검증은 자바스크립트 안에 있는 게 아니라, 여기까지 오는 복호 사슬 전체가 성공했다는 사실 그 자체에 있었습니다. 플래그가 한 글자라도 틀리면 어느 한 겹의 키가 어긋나고, 그 순간 AES 복호가 깨지거나 쉘코드가 쓰레기로 변해 사슬이 끊깁니다. 다섯 키가 모두 맞아야 bam.html이 제대로 만들어져 WebView까지 도달하죠. 메인 앱은 이 WebView가 `setFlagAsValid`를 불러줬는지만 보고 결과를 띄웁니다.

## 플래그 되맞추기

이제 재료가 다 모였습니다. 브루트포스로 K0, K1을, 알려진 평문으로 K2, K3, K4를 얻었고, 플래그 꼬리 f6~f10은 처음부터 알고 있었습니다. 앞서 적은 역산 식에 그대로 넣으면 됩니다.

```python
f5 = K4 ^ f10
f4 = K3 ^ f8
f3 = K2 ^ f6 ^ f9
f2 = K1 ^ f4 ^ f6 ^ f8 ^ f10
f1 = K0 ^ (f2^f3^f4^f5^f6^f7^f8^f9^f10)
flag = b"OOO{" + f1+f2+f3+f4+f5+f6+f7+f8+f9+f10 + b"}"
```

브루트포스부터 여섯 겹 복호, 플래그 조립까지 한 번에 돌린 결과입니다. 복원한 플래그가 `info.yml`의 공식 정답과 정확히 일치했습니다.

![brute-force로 K0=17012f03, K1=3c274360을 찾고 여섯 스테이지를 전부 복호한 뒤, 다섯 키로 되맞춘 플래그가 공식 정답과 일치(OK True)하는 터미널 출력](/assets/img/vitor/solve.png)

맞게 풀었는지 한 번 더 못을 박으려고, 벗겨낸 평문 스테이지들을 복원한 키로 다시 암호화해봤습니다. 네 스테이지 모두 배포된 asset과 바이트 단위로 똑같았습니다. P1, P2는 repo의 실제 `Cryptor.java`로 돌렸는데도 그랬고요. 복호가 맞았다는 얘기이자, 이 문제의 패키징 과정을 그대로 재현했다는 얘기이기도 합니다.

```text
r2con{} 같은 포맷이 아니라 OOO 포맷:
OOO{pox&mpuzz,U_solve_it => pHd_1w_e4rL13r;)}
```

## 실제로 돌려보기

정적으로 다 맞췄지만, 네이티브 사슬이 진짜로 돈다는 것도 눈으로 보고 싶었습니다. `native-lib.cpp`가 쉘코드를 부르는 방식 그대로, 32비트 x86 하네스를 만들어 P3를 실행했습니다. 복호된 쉘코드를 RWX 메모리에 올리고 `(flag, 암호화된_P5, 길이)`를 넘기면, 쉘코드가 플래그에서 K3를 계산해 P4를 복호하고, 그 ROP가 다시 K4를 만들어 P5를 제자리에서 복호한 다음 `0x31337`을 돌려주도록 돼 있습니다.

맞는 플래그로는 쉘코드가 `0x31337`을 반환하고 P5 버퍼가 `<html>`로 복호됐습니다. 반대로 아무 플래그나 넣으면 K3가 어긋나 가젯이 쓰레기가 되고, ROP가 엉뚱한 곳으로 튀면서 프로세스가 그대로 죽습니다. 무결성이 코드가 아니라 암호 사슬 자체에 박혀 있다는 게 이렇게 드러납니다.

![32비트 x86 하네스로 P3 쉘코드를 실행한 결과 — 맞는 플래그에선 shellcode ret가 0x31337이고 P5가 html로 복호되지만, 틀린 플래그에선 ROP가 깨져 프로세스가 죽는다](/assets/img/vitor/harness.png)

마지막으로 공식 `vitor.apk`를 수정 없이 그대로 돌려 끝을 봤습니다. P2가 32비트 x86이고 앱에 네이티브 라이브러리가 들어있지 않아, 64비트 x86_64 이미지에선 프로세스가 64비트로 떠버려 그 .so를 못 올립니다. 그래서 32비트 x86 시스템 이미지로 에뮬레이터를 따로 띄웠습니다(abilist가 `x86, armeabi-v7a, armeabi`라 네이티브 겹이 그대로 실행됩니다). 복원한 플래그를 입력하고 버튼을 누르자, 로그에 "Jumping to nopsled in 3, 2, 1, ..."에 이어 "Flag is valid!"가 찍히고 화면엔 초록색 Valid flag가 떴습니다.

![32비트 x86 에뮬레이터에서 공식 Vitor 앱에 복원한 플래그를 입력하자 Valid flag가 초록색으로 표시된 화면](/assets/img/vitor/app-valid.png)

## 이게 실전에서 쓰는 기법인가

Vitor의 포장은 CTF용이 맞지만, 바탕에 깔린 발상 하나는 지금 안드로이드에서 흔하게 쓰입니다. 진짜 코드를 암호화해 숨겨두고 앱이 실행될 때 복호해서 메모리에 올리는 것, 이른바 패킹입니다. 정적으로 APK를 뜯어봐도 핵심 로직이 보이지 않게 만들어서 분석 비용을 올리는 게 목적이죠.

가장 전형적인 형태가 암호화된 DEX를 assets에 넣어두고 런타임에 복호해서 `DexClassLoader`로 올리는 구조입니다. Vitor에서 P0이 P1을 복호해 `DexClassLoader`로 로딩하는 장면이 정확히 이 패턴이고요. 여기서 한 발 더 나가면 복호 루틴 자체를 자바가 아니라 네이티브(.so)로 내립니다. 자바는 디컴파일이 너무 쉬우니, 언패킹 로직을 네이티브에 숨겨 분석을 한 단계 더 어렵게 만드는 거죠. P1이 네이티브 P2로 넘어가 거기서 다음 복호를 이어가는 흐름이 바로 그겁니다.

이건 교과서 속 얘기가 아니라 상용 제품과 실제 악성코드가 쓰는 코어입니다. 360 Jiagu, Tencent Legu, DexProtector 같은 상용 패커가 암호화 DEX에 네이티브 언패킹 스텁을 붙인 구조를 그대로 쓰고, Cerberus나 Anubis 계열 뱅킹 트로이목마와 플레이스토어 드로퍼도 암호화된 페이로드를 런타임에 `DexClassLoader`로 올리는 식으로 진짜 코드를 숨깁니다.

## 마치며

Vitor가 기억에 남는 건 난이도보다 설계의 맵시 때문입니다. 안드로이드 동적 코드 로딩을 Dalvik, 네이티브, 생 쉘코드, ROP, 자바스크립트 경계까지 전부 한 줄에 꿰어놓고, 거기에 "키는 플래그에서 나오고 각 겹은 다음 겹이 어떻게 생겼는지로 검증된다"는 암호 퍼즐을 얹었습니다. 덕분에 공격자는 복호문 없이도 매직바이트와 알려진 평문만으로 겹을 하나씩 열 수 있고, 그렇게 모은 키가 거꾸로 플래그를 뱉어냅니다. 방어와 공격이 같은 구조의 양면인 셈이죠.

브루트포스가 필요했던 건 바깥 두 겹뿐이었고, 그마저도 키 바이트의 최상위 비트가 0이라는 사소한 관찰 하나로 2³²가 2²⁸로 줄었습니다. 안쪽 네 겹은 NOP 슬레드, 가젯 바이트, `<html>` 같은 '다음 겹이 이렇게 생겨야 한다'는 사실만으로 열렸고요. 결국 이 문제는 암호 세기가 아니라 '구조를 읽는 눈'을 물어보는 문제였습니다.
