> **한 줄 결론**: 패스프레이즈도 키파일도 없었지만 VM 이 suspend 상태였다. `.vmem` 을 4바이트씩 훑으며 **"이 240바이트가 앞 32바이트로부터 확장된 AES-256 키 스케줄인가"** 를 검사해 후보 11개를 얻었고, 그 조합으로 LUKS2 볼륨 키를 복구했다.

## 무엇이 주어졌나

| 파일 | 의미 |
|---|---|
| `DFC2026_L.vmdk` | VMware monolithicSparse 디스크 (8 GiB) |
| `DFC2026_L-15f1e2a0.vmem` | **1 GiB 물리 메모리 덤프** |
| `DFC2026_L-15f1e2a0.vmss` | VMware suspend/checkpoint state |
| `DFC2026_L.vmx` | VM 설정 |

원본 zip MD5 는 `E01D861A9DCA9128C746120FFC1A9794`.

`.vmx` 를 먼저 봤다.

```
memsize = "1024"
checkpoint.vmState = "DFC2026_L-15f1e2a0.vmss"
```

1024 MiB Linux VM, **checkpoint/suspend state 존재.** 이 한 줄이 문제 전체의 방향을 정한다. 디스크만 분석하는 문제가 아니라 휘발성 메모리에서 키를 찾는 문제다.

> **재현 시 주의**: VM 을 실행하다 오류가 나서 discard 를 고르면 suspend/checkpoint 상태가 날아간다. 이 문제의 핵심 증거가 `.vmem` 이므로, 원본 zip 과 추출된 `.vmem` 을 먼저 보존해 두고 시작해야 한다.

## 1. VMDK → raw

monolithicSparse 는 grain directory / grain table 을 타고 들어가면 표준 라이브러리만으로 풀린다. 헤더에서 읽은 값:

```
capacity_sectors = 16777216   (8 GiB)
grain_size       = 128 sectors
allocated_grains = 2054
```

8 GiB 중 실제 할당된 grain 이 2054개뿐이다 — 스파스가 아주 성긴 디스크다.

```python
with args.vmdk.open("rb") as f:
    header = f.read(512)
    magic, version, flags = struct.unpack_from("<III", header, 0)
    if magic != 0x564D444B or version != 1:
        raise SystemExit("unsupported VMDK sparse extent")
    capacity   = struct.unpack_from("<Q", header, 0x0C)[0]
    grain_size = struct.unpack_from("<Q", header, 0x14)[0]
    num_gtes   = struct.unpack_from("<I", header, 0x2C)[0]
    gd_offset  = struct.unpack_from("<Q", header, 0x38)[0]
```

grain table 엔트리가 0 이면 미할당이므로 건너뛰고, 아니면 해당 섹터에서 grain 을 읽어 가상 오프셋에 쓴다. 결과 raw 이미지의 파티션 테이블:

```

Device   Boot   Start       End   Sectors   Size Id Type
raw1     *       2048    616447    614400   300M 83 Linux
raw2           616448   4462591   3846144   1.8G 82 Linux swap
raw3          4462592  16777215  12314624   5.9G 83 Linux
```

## 3. LUKS2 메타데이터 — 뭘 복호화해야 하는지

헤더의 JSON 영역에서 필요한 값만 뽑았다.

```json
{
  "keyslots": { "0": {
      "type": "luks2", "key_size": 64,
      "area": { "offset": "32768", "encryption": "aes-xts-plain64", "key_size": 64 },
      "kdf": { "type": "argon2id", "time": 9, "memory": 360656, "cpus": 2 }
  }},
  "segments": { "0": {
      "type": "crypt", "offset": "16777216", "size": "dynamic",
      "iv_tweak": "0", "encryption": "aes-xts-plain64", "sector_size": 4096
  }},
  "digests": { "0": { "type": "pbkdf2", "hash": "sha256", "iterations": 258015 } }
}
```

읽어야 할 네 가지:

- payload 시작 offset = **16777216** bytes
- 암호화 방식 = **aes-xts-plain64**
- volume key = **64 bytes** (앞 32 = data key, 뒤 32 = tweak key)
- sector_size = **4096** → `plain64` IV 는 512바이트 섹터 번호 기준이므로 4096바이트 데이터 유닛마다 IV 는 0, 8, 16, 24, … 로 증가

keyslot 의 KDF 는 argon2id, time 9, memory 352 MiB. **패스프레이즈 브루트포스는 애초에 답이 아니다.** 볼륨 키를 직접 찾아야 한다.

## 4. 메모리가 말해 주는 것

`.vmem` 문자열 검색으로 LUKS 장치가 열려 있던 흔적을 확인했다.

```
 98853185  cryptsetup open /root/vvault
199697136  cryptsetup close vault
200337744  aes-xts-plain64
200370768  cryptsetup:73bc4374-a2e1-47da-8e2a-5df2af3905f3-d0
200370960  CRYPT-LUKS2-73bc4374a2e147da8e2a5df2af3905f3-vault
200442448  vault (253:0): read ahead is 5120
563262160  dm create vault CRYPT-LUKS2-73bc4374a2e147da8e2a5df2af3905f3-vault
563282512  /dev/loop0
563283440  dm resume vault  [ opencount flush securedata ]   [16384] (*1)
```

- `/root/vault.img` 가 loop device 를 통해 device-mapper `vault` 로 열려 있었다
- 메모리 속 `CRYPT-LUKS2-73bc…-vault` UUID 가 헤더 UUID 와 **일치**한다

그런데 키 문자열은 없다. `dm reload … securedata` 플래그가 보이는데, userspace 가 넘긴 device-mapper 테이블의 민감 문자열은 지워졌거나 애초에 문자열로 남지 않았다. **hex 로 된 키를 문자열 검색으로 찾는 접근은 여기서 막힌다.**

남은 것은 커널 암호화 컨텍스트다. AES 는 라운드 키를 미리 확장해 두고 쓰기 때문에, 열려 있던 dm-crypt 의 **키 스케줄**이 메모리에 그대로 있다.

## 5. AES-256 키 스케줄 스캔

핵심 아이디어는 단순하다. AES-256 키 스케줄은 240바이트고, 그 **앞 32바이트가 나머지 208바이트를 결정한다.** 그러니까 메모리의 임의 위치에서 240바이트를 읽어 앞 32바이트로 키 확장을 돌린 뒤, 결과가 원본 240바이트와 같으면 그 자리는 진짜 키 스케줄이다.

```c
for (size_t off = 0; off + 240 <= (size_t)size; off += 4) {
    for (int little = 0; little <= 1; little++) {
        aes256_expand(buf + off, little, sched);
        if (memcmp(buf + off, sched, 240) == 0) {
            printf("%zu\t%s\t", off, little ? "le" : "be");
            print_hex(buf + off, 32);
            printf("\n");
            hits++;
        }
    }
}
```

**자기 자신으로 검증되는 구조**라 오탐이 거의 없다. 240바이트가 우연히 이 관계를 만족할 확률은 사실상 0 이다. 엔디안 두 가지를 다 시도한 건 커널 구현에 따라 워드 저장 순서가 다를 수 있어서다.

1 GiB 전체를 4바이트 스텝으로 훑어 **hits = 11**. 그중 정답에 쓰인 두 개:

```
59793456  be  2aa52ff521de567d8b3b2c7baaa26266d8544f44158cdf973784b93041398195
59793952  be  fb2b11126c7cc0d9e32b96759b7cd7f8b8609f23b5315d772fe41c33053017d1
```

## 6. 후보 조합 검증 — ext4 매직으로

XTS 는 32바이트 키 두 개(data, tweak)를 쓴다. 후보 11개의 순서쌍을 전부 만들어 payload 첫 4096바이트 유닛을 tweak 0 으로 복호화하고, **평문 offset `1024 + 0x38` 에 ext4 슈퍼블록 매직 `53 ef`** 가 나오는지 봤다.

```python
def decrypt_first_unit(key, ciphertext):
    d = Cipher(algorithms.AES(key), modes.XTS((0).to_bytes(16, "little"))).decryptor()
    return d.update(ciphertext) + d.finalize()

...
plaintext  = decrypt_first_unit(key1 + key2, first_unit)
ext4_magic = plaintext[1024 + 0x38 : 1024 + 0x3A]
if ext4_magic == b"\x53\xef":
    hits.append(...)
```

전체 조합 중 hit 은 **정확히 1개**.

```
hit data_schedule_offset=59793952 data_endian=be
    tweak_schedule_offset=59793456 tweak_endian=be
volume_key_hex=fb2b11126c7cc0d9e32b96759b7cd7f8b8609f23b5315d772fe41c33053017d1
               2aa52ff521de567d8b3b2c7baaa26266d8544f44158cdf973784b93041398195
hits=1
```

`53 ef` 는 2바이트라 우연히 맞을 확률이 1/65536 이다. 후보 조합 수가 110개 정도인 상황에서는 충분히 판별력이 있지만, 그래도 이것만으로 확정하기는 약하다.

## 7. LUKS2 digest 로 재검증

복구한 64바이트를 헤더의 digest 영역으로 다시 검증했다.

```
PBKDF2-HMAC-SHA256(
  password = 복구한 64-byte volume key,
  salt     = base64("udY2k079E5nzBASElh2rS3r1bXqtJYyU+0yCzNVnL94="),
  iter     = 258015,
  dkLen    = 32
)
= 3e9921f8ee57320d22a4f087fc6575568f2bbbee5b08317142dd7dca2e278e3b
```

헤더 digest 와 일치. 이제 **"메모리에서 주운 바이트가 이 컨테이너의 실제 볼륨 키" 라는 게 암호학적으로 확정**된다. ext4 매직은 후보를 좁히는 필터였고, digest 가 증명이다.

## 8. payload 복호화

```python
payload_offset = int(segment["offset"])        # 16777216
sector_size    = int(segment["sector_size"])   # 4096
plain64_step   = sector_size // 512            # 8

unit = 0
while (ciphertext := f.read(sector_size)):
    iv_sector = unit * plain64_step            # 0, 8, 16, 24, ...
    d = Cipher(algorithms.AES(key), modes.XTS(iv_sector.to_bytes(16, "little"))).decryptor()
    out.write((d.update(ciphertext) + d.finalize())[:len(ciphertext)])
    unit += 1
```

여기서 틀리기 쉬운 지점이 IV 증가폭이다. `plain64` 는 **512바이트 섹터 번호**를 IV 로 쓰는데 이 컨테이너의 암호화 단위는 4096바이트다. 유닛 인덱스를 그대로 IV 로 넣으면 첫 유닛만 맞고 두 번째부터 전부 깨진다. 8씩 건너뛰어야 한다.

복호화 결과 16777216 bytes 의 ext4 이미지가 나오고,

```bash
debugfs -R 'cat /flag.txt' vault_decrypted_payload.ext4
```

```

```

## 정리 — 이 문제에서 남는 것

**`.vmss`/`.vmem` 이 있으면 그게 1순위 증거다.** 디스크만 보고 "LUKS2 argon2id 라 못 푼다" 로 끝낼 수 있는 문제였다. `.vmx` 의 `checkpoint.vmState` 한 줄이 방향을 바꿨다.

**키 스케줄은 자기 자신을 검증한다.** 240바이트 중 앞 32바이트가 나머지를 결정하는 구조라, 별도 사전이나 휴리스틱 없이 메모리에서 AES 키를 직접 찾을 수 있다. 이 성질은 dm-crypt·BitLocker·FileVault 등 AES 를 쓰는 모든 대상에 동일하게 적용된다.

**필터와 증명은 다른 일이다.** ext4 매직 2바이트는 110개 조합을 1개로 줄이는 필터였고, LUKS2 PBKDF2 digest 가 그 1개를 증명했다. 필터에서 멈추면 "아마 맞을 것" 이고, digest 까지 가야 "맞다" 가 된다.

**IV 스텝은 sector_size 가 정한다.** `plain64` 의 IV 단위는 512바이트로 고정이고 컨테이너의 암호화 단위는 별개다. 둘을 같다고 두면 첫 블록만 맞는 함정에 빠진다.
