> **대상**: CVE-2022-20425 (`ZenModeHelper.addAutomaticZenRule`, DoS/High) / AVD `sec-31-r03`·`sec-31-r05`
> **이전 글**: [19주차 이미지 쌍 준비](/posts/android-security-study-week19/) · [18주차 CVE 선정](/posts/android-security-study-week18/) · [24주 로드맵](/posts/android-security-study-roadmap/)

18주차에 재현할 CVE 를 고르고, 19주차에 패치 전·후 이미지를 나란히 띄울 실험대를 만들었습니다. 이번 회차는 그 위에서 실제로 취약점을 관측하는 구간입니다.

결론부터 적으면 재현에 성공했는데, **처음 세운 가설은 틀렸습니다.** 예상은 "패치 전에는 한도가 없고 패치 후에 생긴다"였는데, 실제로는 패치 전에도 한도가 있었습니다. 갈린 것은 다른 지점이었습니다.

## 배경 개념 - 자동 Zen 규칙과 한도

Android 의 "방해 금지"에는 앱이 프로그램으로 등록하는 **자동 규칙**이 있습니다. 캘린더 앱이 회의 중에 알림을 줄이거나, 수면 앱이 취침 시간에 켜지도록 하는 용도입니다. `NotificationManager.addAutomaticZenRule()` 한 번이면 등록됩니다.

여기에 두 가지 안전장치가 걸립니다. 하나는 **정책 접근**입니다. 아무 앱이나 부를 수 없고, 사용자가 허용한 앱만 가능합니다. 매니페스트에 선언하는 권한이 아니라 런타임에 부여되는 접근입니다. 다른 하나가 **개수 한도**입니다. 규칙은 시스템 설정 파일에 영속화되므로, 개수에 상한이 없으면 앱 하나가 계속 쌓아 올릴 수 있습니다.

CVE-2022-20425 는 두 번째 장치의 문제입니다. 유형은 DoS 이고, CWE 는 자원 소모(CWE-400)입니다. 18주차에 확인한 패치 커밋 `0c607e70` 은 `getPackageRuleCount(pkg)` 라는 메서드를 새로 만들어 개수 검사를 바꿉니다.

## 1. 실습 환경과 준비

19주차에 만든 쌍을 그대로 씁니다. 같은 API 31, 같은 Android 12, 하드웨어 프로파일 동일, 보안 패치 수준만 다릅니다.

| AVD | 역할 | `ro.build.id` | 패치 수준 |
| --- | --- | --- | --- |
| `sec-31-r03` | baseline | `SE1A.220621.001` | 2022-08-01 |
| `sec-31-r05` | patched | `SE1A.220826.006.A1` | 2022-10-01 |

매 실행 전 `-wipe-data` 냉부팅으로 공장 초기 상태에서 시작합니다. 19주차에 스냅샷 복원이 가짜 차이를 만들어내는 것을 확인하고 바꾼 방식입니다.

## 2. 수행 절차

### 2-1. 프로브 앱

APK 9KB, 소스 한 파일입니다. 의존성이 없고 androidx 도 쓰지 않습니다. 측정 대상이 플랫폼 API 하나뿐인데 라이브러리를 끼우면 변수만 늘어납니다.

**매니페스트에 권한을 하나도 선언하지 않습니다.** 이게 이 취약점의 성격을 보여주는 부분입니다. 필요한 것은 런타임 정책 접근 하나뿐이고, 그건 `adb shell cmd notification allow_dnd <패키지>` 로 부여합니다.

규칙 객체를 만드는 부분은 상류 소스를 보고 맞췄습니다. 진입점의 검사가 이렇게 걸려 있습니다.

```java
// NotificationManagerService.java (android-12.0.0_r34)
Objects.requireNonNull(automaticZenRule.getName(), "Name is null");
if (automaticZenRule.getOwner() == null
        && automaticZenRule.getConfigurationActivity() == null) { … }
Objects.requireNonNull(automaticZenRule.getConditionId(), "ConditionId is null");
checkCallerIsSameApp(pkg);
if (automaticZenRule.getZenPolicy() != null
        && automaticZenRule.getInterruptionFilter() != INTERRUPTION_FILTER_PRIORITY) { … }
enforcePolicyAccess(Binder.getCallingUid(), "addAutomaticZenRule");
```

`owner`(ConditionProviderService)나 `configurationActivity` 중 **하나만** 있으면 됩니다. 그래서 CPS 를 만들지 않고 앱의 액티비티 자신을 `configurationActivity` 로 넘겼습니다. `ZenPolicy` 는 `null` 로 둬야 필터 제약에 걸리지 않습니다.

```java
AutomaticZenRule rule = new AutomaticZenRule(
        "ZENPROBE-" + i,
        null,                                            // CPS 없음
        comps[(i - 1) % comps.length],                   // configurationActivity
        Uri.parse("condition://kr.wtcy.zenprobe/" + i),  // 매번 달라야 함
        null,                                            // ZenPolicy
        NotificationManager.INTERRUPTION_FILTER_PRIORITY,
        false);                                          // 활성화하지 않음
```

마지막 `false` 가 중요합니다. 규칙을 **활성화하지 않으므로** 기기의 실제 알림 동작은 바뀌지 않습니다. 보려는 것은 등록이 거부되는 지점이지 방해 금지가 걸리는 모습이 아닙니다.

### 2-2. 판정을 세 갈래로 나눴다

프로브가 내는 `limit_hit_at` 은 세 가지 값을 가집니다.

| 값 | 뜻 |
| --- | --- |
| `none` | 시도한 횟수 안에서는 거부되지 않았다 |
| `<순번>` | 그 지점에서 거부됐다 |
| `측정불가` | 정책 접근을 못 받았거나 컴포넌트 해석에 실패했다 — 판정 자체가 성립 안 함 |

세 번째를 따로 둔 이유가 있습니다. 취약 코드에는 한도 말고도 예외를 던지는 자리가 하나 더 있습니다.

```java
if (component == null) {
    throw new IllegalArgumentException("Lacking enabled CPS or config activity");
}
```

같은 `IllegalArgumentException` 이라 예외 종류만 보면 구분되지 않습니다. **메시지까지 봐야** 한도에 막힌 것인지 내 컴포넌트가 해석되지 않은 것인지 갈립니다. 이걸 섞으면 측정 실패를 발견으로 읽게 됩니다.

## 3. 관측 결과

### 3-1. 첫 대조 — 차이가 없었다

```
                        baseline(r03)   patched(r05)
limit_hit_at            101             101
added_ok                100             100
```

두 이미지의 프로브 출력이 **완전히 같았습니다.** diff 가 비었습니다.

### 3-2. 판별 측정 — 컴포넌트를 늘리자 갈렸다

18주차 조사 카드에 이 경우를 대비한 측정을 하나 적어뒀습니다. `activity-alias` 로 **같은 액티비티를 가리키는 서로 다른 컴포넌트 이름**을 여러 개 만들고, 규칙마다 번갈아 쓰는 것입니다.

- 한도를 **컴포넌트 단위**로 세면 별칭마다 카운터가 갈라져 한도가 곱해집니다
- **패키지 단위**로 세면 별칭과 무관하게 같은 한도에 합산됩니다

별칭 4개를 더해 컴포넌트 5개로 돌렸습니다.

![컴포넌트 1개일 때는 두 이미지 모두 101에서 거부되지만, 컴포넌트 5개로 늘리면 r03은 501에서 거부되고 r05는 그대로 101에서 거부되는 측정 결과 행렬](/assets/img/android-security-study/23-zen-limit-matrix.svg)

| 측정 | r03 (2022-08-01) | r05 (2022-10-01) |
| --- | --- | --- |
| 컴포넌트 1개 · 400회 시도 | `101에서 거부` | `101에서 거부` |
| 컴포넌트 5개 · 400회 시도 | **`거부 없음`** (400 성공) | `101에서 거부` |
| 컴포넌트 5개 · 600회 시도 | **`501에서 거부`** (500 성공) | — |

거부는 전부 `java.lang.IllegalArgumentException: Rule instance limit exceeded` 였고, 앱이 센 개수와 `dumpsys notification --zen` 의 서버 쪽 개수가 모든 실행에서 일치했습니다.

## 4. 결과 해석

### 4-1. 바뀐 것은 세는 단위다

- **r03 은 컴포넌트당 100개.** 컴포넌트를 5개로 늘리니 500개까지 들어갔습니다.
- **r05 는 패키지당 100개.** 컴포넌트를 몇 개로 늘리든 100에서 막힙니다.

패치가 바꾼 것은 한도의 유무가 아니라 **개수를 어느 단위로 세는가**였습니다. 이건 18주차에 읽은 패치 diff 가 예측한 그대로입니다.

```java
- if (newRuleInstanceCount > RULE_LIMIT_PER_PACKAGE
+ int newPackageRuleCount = getPackageRuleCount(pkg) + 1;
+ if (newPackageRuleCount > RULE_LIMIT_PER_PACKAGE
```

기존 `newRuleInstanceCount` 는 `getCurrentInstanceCount(owner) + getCurrentInstanceCount(configurationActivity) + 1` 로 **컴포넌트 이름을 기준으로** 셌습니다. 이름이 다르면 카운터가 따로 돕니다. 패치는 패키지 기준으로 세는 검사를 추가합니다.

그리고 커밋에 함께 들어온 회귀 테스트 이름이 이겁니다.

```
testAddAutomaticZenRule_beyondSystemLimit_differentComponents
```

**이번 판별 측정이 그 테스트와 같은 것을 기기에서 확인한 셈입니다.** 소스에서 읽은 수정 의도와 기기에서 관측한 동작이 방향뿐 아니라 수치(100, 500)까지 맞아떨어졌습니다.

### 4-2. 실제 의미

일반 앱이 **매니페스트에 권한을 하나도 선언하지 않고**, 사용자가 허용한 정책 접근 하나만 가지고, `activity-alias` 를 늘린 수만큼 자동 Zen 규칙을 누적할 수 있었습니다. 규칙은 시스템 설정 파일에 영속화되므로 재부팅해도 남습니다.

> 이 문장은 게시 당시 **두 점만 보고 쓴 것**입니다. 나중에 세 번째 점을 재고 나서야 근거가 생겼고, 그마저도 측정 범위가 있습니다. [부록](#부록--게시-후-정정)을 함께 보십시오.

여기서 멈췄습니다. 실제로 기기를 사용 불능으로 만드는 것은 목표가 아니었고 시도하지 않았습니다. 규칙을 전부 비활성 상태로 만든 것도 그래서입니다.

### 4-3. 18주차 가설을 정정합니다

조사 카드의 주 가설은 **틀렸습니다.** 카드는 이렇게 적었습니다.

> Android 12 취약 코드에는 `RULE_LIMIT_PER_PACKAGE` 상수가 없으므로 r03 에는 사실상 한도가 없다.

근거는 소스 태그 `android-12.0.0_r34` 와 `android-12.1.0_r1` 을 직접 열어 확인한 것이었고, **그 확인 자체는 맞습니다.** 두 태그에는 정말 그 상수가 없습니다. 틀린 것은 거기서 이미지로 건너뛴 추론입니다. 에뮬레이터 이미지는 소스 태그가 아니라 SDK 브랜치 빌드이고, r03 이미지에는 상수가 들어 있었습니다.

다행히 카드가 이 가능성을 위험 항목으로 적어두고 있었습니다.

> R1 — r03 이 이미 `RULE_LIMIT_PER_PACKAGE`(컴포넌트 단위 버전)를 갖고 있어 양쪽 다 100 에서 막힘.
> 상수는 `int` 라 문자열 스캔으로 판정 불가. 프로브가 `limit_hit_at` 을 출력하므로 자가 진단된다.

정확히 그 일이 일어났고, 대비해 둔 판별 측정이 회차를 살렸습니다. 결과적으로 **부속 가설이 실제 판정**이었습니다.

## 5. 시행착오와 정정

### 5-1. 또 곁다리로 상태를 추측했다

정책 접근이 부여됐는지 셸에서 확인하려고 이렇게 썼습니다.

```bash
adb shell settings get secure enabled_notification_policy_access_packages
```

결과가 비어서 프로브가 "정책 접근 실패 — 이하 판정은 무효"를 찍었습니다. 그런데 같은 실행에서 앱은 `policy_access=true` 를 보고했고 규칙 100개가 실제로 등록됐습니다. **부여는 됐고 제 확인 방법이 틀린 것**이었습니다.

19주차의 `cmd notification --help` 오류와 완전히 같은 유형입니다. 상태를 직접 묻는 API 가 있는데 곁다리 경로로 추측한 것입니다. 권위 있는 값은 앱이 부르는 `isNotificationPolicyAccessGranted()` 하나뿐이므로 셸 쪽 확인을 지우고 앱 보고를 판정에 쓰도록 고쳤습니다.

### 5-2. "차이 없음"에서 프로브를 의심하지 않았다

첫 대조가 완전히 같게 나왔을 때, 보통이라면 프로브가 잘못됐나 보러 갔을 겁니다. 그러지 않아도 됐던 이유는 출력이 `실패`가 아니라 **`limit_hit_at=101` 이라는 구체적인 값**이었기 때문입니다.

값이 나왔다는 것은 측정이 성립했다는 뜻이고, 양쪽이 같다는 것은 "이 측정으로는 두 이미지가 안 갈린다"는 정보입니다. 프로브를 고칠 일이 아니라 **측정을 바꿀 일**이었습니다. 판정을 이진값(막혔다/안 막혔다)이 아니라 순번으로 설계해 둔 것이 여기서 값을 했습니다.

### 5-3. `none` 을 결론으로 쓰지 않았다

별칭 변형에서 r03 이 400회를 전부 통과했을 때, 그대로 "한도 없음"이라고 적을 수도 있었습니다. 하지만 400 은 제가 정한 상한일 뿐입니다. **거부되지 않았다는 것은 한도가 없다는 증거가 아니라 한도를 못 만났다는 것**뿐입니다.

600회로 다시 재서 **501에서 거부**되는 것을 보고 나서야 "컴포넌트당 100"이라고 말할 수 있었습니다. 5 × 100 = 500 이라는 예측한 천장이 그대로 나온 것이라, 부정 관측이 긍정 증거로 바뀌었습니다.

7~8주차에 "검증을 부정 조건으로 짜지 말 것"을 배웠는데, 그 교훈이 이번엔 상한값 해석에서 나왔습니다.

| 23~24주 최종 보고서 | |

한계도 적어둡니다. 이미지 쌍이 단일 변수가 아니라는 점(19주차 실측: 7개 파일 차이, 커널 포함)은 그대로입니다. 다만 이번 관측은 패치 diff 가 예측한 **방향과 수치까지** 맞으므로 다른 변경으로 설명하기 어렵습니다. 21주차에 그 설명 가능성을 정면으로 따질 예정입니다.

그리고 r05 백포트의 한도 값이 100 이라는 것은 **관측으로** 확인했지, 바이트코드에서 상수를 읽어 확정하지는 않았습니다. 한도 100 이 언제부터 r03 계열에 들어왔는지도 추적하지 않았습니다.

## 마치며

이번 구간에서 가장 배운 것은 **가설이 틀렸는데도 실험이 성립했다**는 점입니다.

18주차에 세운 주 가설("패치 전에는 한도가 없다")은 이미지에서 성립하지 않았습니다. 소스 태그를 직접 읽고 세운 가설이었는데도 그랬습니다. 태그와 배포 이미지가 같지 않다는 것을 알고 있었고 위험 항목에도 적었는데, 막상 가설은 태그 쪽을 믿고 썼습니다.

그런데 그 위험을 적어두면서 **대비 측정을 같이 설계해 둔 것**이 결과를 바꿨습니다. 첫 대조에서 차이가 없었을 때 "재현 실패"로 끝내지 않고 30분 만에 판별로 넘어갈 수 있었던 건, 18주차의 제가 "이렇게 되면 이걸 해봐라"를 남겨줬기 때문입니다.

조사 카드에 위험을 적는 일이 형식처럼 느껴졌는데, 이번에 그 항목 하나가 회차를 살렸습니다. 틀릴 수 있는 지점을 미리 적어두면, 틀렸을 때 그게 실패가 아니라 다음 단계가 됩니다.

## 부록 — 게시 후 정정

이 글을 올린 뒤 결론을 적대적으로 다시 검토했습니다. **판정(세는 단위가 바뀌었다)은 그대로 살아남았지만, 이 글의 근거에 두 가지 문제가 있었습니다.**

### 하나. 이 데이터는 다른 설명과도 들어맞았다

본문 3-2 의 표는 컴포넌트 1개와 5개, 두 점입니다. 여기서 "컴포넌트당 100개"라고 결론지었는데, **같은 두 점에 들어맞는 설명이 하나 더 있습니다.**

| 모델 | C=1 예측 | C=5 예측 |
| --- | --- | --- |
| 컴포넌트당 100 | 101 | 501 |
| 컴포넌트당 100 **+ 전역 500 천장** | 101 | 501 |

두 모델이 C=5 에서 똑같이 501 을 냅니다. 제가 가진 데이터로는 구분되지 않았습니다. 두 점만 있으면 두 직선이 다 지나갑니다.

갈라놓으려면 세 번째 점이 필요합니다. C=3 이면 컴포넌트 모델은 301 을, 전역 천장 모델은 501 을 예측합니다. 나중에 재봤더니 **301** 이었고, 전역 천장 모델은 반증됐습니다.

### 둘. 표의 첫 행은 다른 빌드로 잰 것이었다

"컴포넌트 1개 → 101" 행은 별칭 기능을 넣기 **전** 프로브로 측정한 것이었습니다. APK 를 다시 빌드한 시각이 그 측정과 별칭 측정 사이에 있었습니다.

증거는 명확했습니다. 지금 프로브는 `components(사용한 컴포넌트 수)` 를 항상 출력하는데, 그 측정의 증적 파일에는 그 줄이 없습니다. 현재 빌드로 다시 재서 101/101 을 확인했고, 이번엔 빌드 지문과 시작 상태까지 함께 남겼습니다.

### 완성된 측정 행렬

| 컴포넌트 수 C | 예측 `100·C+1` | r03 (2022-08-01) | r05 (2022-10-01) |
| --- | --- | --- | --- |
| 1 | 101 | **101** | 101 |
| 2 | 201 | **201** | 101 |
| 3 | 301 | **301** | 101 |
| 4 | 401 | **401** | 101 |
| 5 | 501 | **501** | 101 |
| 6 | 601 | **601** | 101 |

본문에서 `—` 로 비워뒀던 칸(r05 · 5컴포넌트 · 600회)도 채웠습니다. **101** 로, 시도 횟수를 늘려도 그대로입니다.

### 범위를 명시합니다

증폭은 **컴포넌트 1부터 6까지 전부 확인했고 실측한 최대 누적은 규칙 600개**입니다. "별칭을 늘린 수만큼"은 그 범위 안에서 유효한 표현이지, 무제한이라는 뜻이 아닙니다. (C=6 은 별칭을 하나 더 넣은 새 빌드로 쟀고, 같은 빌드로 C=5 를 다시 재 501 이 그대로인 것을 확인한 뒤 표에 올렸습니다.)

### 이 글의 다른 문장 하나

3-3 의 후보 표에서 `NotificationManagerService` 쪽 변경을 넘어간 것과 관련해, 21주차에 "무관한 스누즈 수정"이라고 적었던 것이 실은 **별개의 보안 수정**이었습니다(`SnoozeHelper` 에 `CONCURRENT_SNOOZE_LIMIT = 500` 신설). 같은 달 같은 패키지에 같은 자원 한도 계열 수정이 둘 들어와 있습니다. 자세한 것은 [21주차 글의 3-3](/posts/android-security-study-week21/) 에 적었습니다.
