> **진행 구간**: 24주 로드맵의 19주차 (원안: AOSP 패치 전·후 빌드 → 환경 제약으로 이미지 쌍 준비로 대체)
> **대상**: AVD `sec-31-r03`(Android 12, 패치 2022-08-01) / `sec-31-r05`(Android 12, 패치 2022-10-01)
> **이전 글**: [18주차 CVE 선정](/posts/android-security-study-week18/) · [17주차 비교 하네스](/posts/android-security-study-week17/) · [24주 로드맵](/posts/android-security-study-roadmap/)

18주차에 재현할 CVE 를 골랐으니, 이제 그것을 볼 실험대를 만들 차례입니다. 로드맵의 원안은 AOSP 를 패치 전과 후로 각각 빌드하는 것이었는데 이 장비에서는 불가능합니다(공식 요구 400GB). 대신 17주차에 찾아둔 경로를 씁니다. **같은 API 레벨의 과거 리비전 이미지를 URL 로 직접 받아 baseline/patched 로 쓰는 것**입니다.

작업 자체는 단순해 보였습니다. 이미지 두 개를 SDK 에 넣고 AVD 두 대를 만들면 끝입니다. 그런데 이 구간에서 정작 오래 붙잡은 것은 구성이 아니라 검증이었습니다. **두 AVD 가 정말 이미지 말고는 같은가**, 그리고 **대조에서 나온 차이가 정말 이미지 때문인가**입니다. 두 번째 질문에서 하나가 걸렸습니다.

## 배경 개념 - 왜 "쌍"이어야 하는가

CVE 재현에서 확인하고 싶은 것은 "취약하다"가 아니라 **"패치가 이 동작을 바꿨다"** 입니다. 그러려면 패치만 다르고 나머지는 같은 두 환경이 필요합니다. 한쪽에서만 관찰되는 현상이 있어도, 두 환경이 여러 면에서 다르면 그 현상의 원인을 패치로 지목할 수 없습니다.

17주차에 만든 하네스는 Android 13 과 Android 16 을 baseline/patched 자리에 놓았습니다. 동작은 했지만 API 레벨이 세 단계 차이라 사실상 "두 개의 다른 운영체제"를 비교하는 것이었고, 글에도 그렇게 적었습니다. 이번에 쓰는 쌍은 **같은 API 31, 같은 Android 12, 보안 패치 수준만 2022-08-01 과 2022-10-01** 입니다. 훨씬 좁습니다.

여기서 미리 짚어둘 것이 있습니다. 좁아졌다는 것이 **단일 변수가 됐다는 뜻은 아닙니다.** 이번 회차의 절반은 그 차이가 정확히 얼마나 남았는지 재는 데 썼습니다.

## 1. 실습 환경과 준비

먼저 자리를 비웠습니다. 이미지 두 개를 풀면 8.3GB 가 필요한데 여유가 15GB 뿐이었습니다.

1~17주차에 쓰던 앱 실습용 AVD 두 대(`sec-api33` 5.8GB, `sec-api36` 5.6GB)를 지웠습니다. 시스템 이미지는 SDK 에 그대로 남아 있어서 `avd-setup.sh` 로 언제든 되만들 수 있고, 만약을 위해 삭제 전에 두 AVD 의 `config.ini` 를 증적 폴더에 보존했습니다. 실제로 이 보존본이 뒤에서 템플릿으로 쓰이게 됩니다.

다른 프로젝트의 AVD(HexTree, Toss 계열 네 대)는 건드리지 않았습니다. 정리 후 여유는 26GB 가 됐습니다.

## 2. 수행 절차

### 2-1. 같은 패키지의 두 리비전을 한 SDK 에 두기

여기서 첫 번째 벽을 만납니다. 시스템 이미지의 표준 경로는 이렇게 생겼습니다.

```
$ANDROID_HOME/system-images/android-31/default/x86_64/
```

API 레벨·태그·ABI 로 경로가 정해지므로 **같은 조합의 리비전 두 개를 동시에 둘 칸이 없습니다.** r03 과 r05 는 셋 다 같습니다.

해결은 단순합니다. 최상위 디렉터리만 슬롯별로 나누고, 뒤 세 칸은 표준과 똑같이 유지합니다.

![표준 경로에는 리비전 한 개만 들어가므로 최상위 디렉터리를 슬롯별로 나누고, AVD의 image.sysdir.1로 각각을 가리키는 구조도](/assets/img/android-security-study/21-sysimg-slot-layout.svg)

뒤 세 칸을 유지한 이유는 에뮬레이터가 경로 조각에서 태그나 ABI 를 읽는 경우에 대비한 것입니다. 그리고 최상위가 `system-images` 가 아니므로 `sdkmanager` 가 이 트리를 관리 대상으로 보지 않습니다. 나중에 SDK 업데이트가 우리 실험용 이미지를 건드릴 일이 없습니다.

AVD 는 `config.ini` 의 한 줄로 자기 이미지를 고릅니다.

```
image.sysdir.1 = system-images-r03\android-31\default\x86_64\
```

이 값이 무엇을 기준으로 한 경로인지가 관건이었는데, 부팅 산출물에서 확인할 수 있었습니다. 부팅하면 에뮬레이터가 `hardware-qemu.ini` 에 실효값을 적어둡니다.

```
kernel.path = C:/Users/.../Sdk\system-images-r03\android-31\default\x86_64\\kernel-ranchu
```

SDK 루트 문자열 뒤에 `image.sysdir.1` 값이 그대로 이어 붙습니다. 끝의 `\\` 가 단순 문자열 연결이라는 증거입니다. 즉 **`$ANDROID_HOME` 기준 상대 경로**이고, 절대 경로 지원 여부에 기대지 않아도 됩니다.

### 2-2. avdmanager 를 쓸 수 없다

두 번째 벽입니다. AVD 생성의 표준 방법은 이것인데,

```bash
avdmanager create avd -n sec-31-r03 -k "system-images;android-31;default;x86_64"
```

동작하지 않습니다. `sdkmanager` 로 설치한 이미지 디렉터리에는 `package.xml` 이 있는데(19KB), **URL 로 직접 받은 zip 에는 이 파일이 없습니다.** 설치본과 zip 의 파일 목록을 대조해보면 차이가 정확히 그것 하나입니다. `package.xml` 이 없으면 SDK 패키지 목록에 잡히지 않고, `-k` 가 그 경로를 인식하지 못합니다.

그래서 AVD 정의를 직접 썼습니다. 삭제 전에 보존해둔 `sec-api33` 의 `config.ini` 를 템플릿으로 삼고 이미지 관련 키만 바꾸는 방식입니다. 하드웨어 프로파일(pixel_6)을 통째로 물려받으므로 **두 AVD 사이에 하드웨어 차이가 생기지 않습니다.** 비교 실험에서는 이게 중요합니다.

### 2-3. 부팅 확인

두 대 모두 요청한 이미지로 떴습니다.

| AVD | `ro.build.id` | 패치 수준 |
| --- | --- | --- |
| `sec-31-r03` | `SE1A.220621.001` | 2022-08-01 |
| `sec-31-r05` | `SE1A.220826.006.A1` | 2022-10-01 |

## 3. 관측 결과

### 3-1. 하드웨어 조건은 같다

두 AVD 의 `config.ini` 를 diff 하면 다른 줄이 **세 개**뿐입니다.

```
avd.id / avd.name / image.sysdir.1
```

RAM, CPU 수, 파티션 크기, 화면, 기기 프로파일이 전부 같습니다. 구성 수준에서는 전제가 충족됐습니다.

### 3-2. 이미지는 단일 변수가 아니다

이쪽이 문제였습니다. 두 이미지 디렉터리를 파일별 SHA-256 으로 전부 비교했습니다.

| 파일 | 결과 |
| --- | --- |
| `system.img` | 다름 — 의도한 차이 |
| `vendor.img` | 다름 |
| `kernel-ranchu` | **다름** |
| `ramdisk.img` | **다름** |
| `build.prop` | 다름 (26행) |
| `VerifiedBootParams.textproto` | 다름 (vbmeta digest) |
| `advancedFeatures.ini` | **다름** |
| `NOTICE.txt`, `encryptionkey.img`, `source.properties`, `userdata.img` | 같음 |

7개가 다릅니다. **커널과 ramdisk 가 함께 바뀝니다.**

> **범위 주의(이후 정정)**: 이 "7개"는 **이미지 디렉터리 최상위** 기준입니다. `system.img` 를 풀어 안쪽 파일 단위로 보면 차이는 훨씬 많고, 대부분 AOT 재컴파일 산출물입니다. "이 시스템에서 다른 건 일곱 개뿐"이라는 뜻이 아닙니다. 프레임워크 패치만 갈아끼운 것이 아닙니다. 여기에 빌드 컷 자체가 2022-06-22 와 2023-05-04 로 약 10개월 차이라, 목표 패치 외의 변경도 당연히 섞여 있습니다.

API 33 대 API 36 보다는 훨씬 좁아졌지만, "패치만 다르다"고 말할 수는 없습니다. 하네스의 경고 문구를 이 실측 목록으로 바꿔 적었습니다.

### 3-3. 내가 적은 설정이 이미지에 덮어써졌다

`advancedFeatures.ini` 의 차이는 한 줄(`VsockSnapshotLoadFixed_b231345789 = on` 이 r05 에만)이었는데, 이 파일을 열어본 김에 내용을 보다가 더 중요한 것을 발견했습니다. 2022년 이미지가 켜는 플래그와 현재 에뮬레이터의 기본값이 정반대입니다.

| 플래그 | 이미지(2022) | 호스트 기본값 |
| --- | --- | --- |
| `Vulkan` | on | off |
| `GLESDynamicVersion` | on | off |
| `GrallocSync` | on | off |

그리고 이미지 쪽이 이깁니다. 결과를 확인해보니 이렇습니다.

| | `config.ini` 가 요청한 값 | `hardware-qemu.ini` 실효값 |
| --- | --- | --- |
| `hw.gpu.enabled` | `no` | **`true`** |
| `hw.gpu.mode` | `auto` | **`lavapipe`** |

`lavapipe` 는 소프트웨어 Vulkan 구현입니다. **제가 GPU 를 끄겠다고 적어둔 설정이 무시되고 소프트웨어 렌더링으로 낙착됐습니다.** 헤드리스로 띄우니 화면은 상관없지만, 문제는 다른 데 있었습니다.

## 4. 결과 해석

### 4-1. 소프트웨어 렌더링에서 스냅샷을 믿으면 안 된다

에뮬레이터 스냅샷은 소프트웨어 렌더링 환경에서 지원되지 않습니다. 그런데 17주차에 만든 하네스는 **매 실행 전 `clean` 스냅샷으로 되돌리는 방식**으로 시작 상태를 맞추고 있었습니다. 정면으로 걸립니다.

시작 상태를 맞추는 방법을 `-wipe-data` 냉부팅으로 바꿨습니다. 스냅샷 기계를 아예 쓰지 않고 공장 초기 상태에서 시작하므로 이 위험이 사라지고, "두 실행의 시작 상태가 같다"가 구조적으로 보장됩니다. 대가는 속도입니다. 매 실행 냉부팅이라 대조 한 번이 훨씬 오래 걸립니다.

### 4-2. 바꾸자 차이 하나가 사라졌다

바꾸기 전후로 같은 프로브를 같은 두 이미지에 돌렸습니다. 프로브도 이미지도 그대로고, 시작 상태를 맞추는 방법만 다릅니다.

![clean 스냅샷 복원으로 대조했을 때 나타난 mDefaultPhoneApp 차이가, wipe-data 냉부팅으로 바꾸자 사라지고 빌드 지문 차이만 남는 것을 보여주는 비교도](/assets/img/android-security-study/22-snapshot-artifact.svg)

스냅샷 복원으로 대조했을 때는 기본 전화 앱 설정이 한쪽은 `com.android.dialer`, 다른 쪽은 `null` 로 나왔습니다. 이미지 차이처럼 보입니다. 냉부팅으로 바꾸니 이 줄은 아예 나타나지 않고 빌드 지문 두 줄만 남았습니다.

두 스냅샷은 각자 첫 부팅 뒤 서로 다른 시점에 저장됐습니다. 그 시점 차이가 게스트 상태로 굳어서 대조에 나온 것입니다. **이미지의 차이가 아니라 제 실험 절차가 만든 차이였습니다.**

이번엔 다행히 눈에 띄는 항목이었습니다. 만약 20주차에 규칙 개수 같은 미묘한 값에서 이런 일이 생겼다면, 그걸 패치의 효과로 읽었을 가능성이 높습니다.

### 4-3. 18주차가 남긴 미확인 항목이 해소됐다

기준선 프로브를 돌려 조사 카드가 "[미확인]"으로 남겨둔 것들을 확인했습니다.

```
cmd notification allow_dnd                     있음
자동 규칙 개수(id 중복 제거)                   2
  규칙 id 목록                                 EVENTS_DEFAULT_RULE EVERY_NIGHT_DEFAULT_RULE
  pkg=android 규칙 수                          2
```

정책 접근을 부여하는 `cmd notification allow_dnd PACKAGE` 가 Android 12 에 존재합니다. 카드가 위험 항목으로 잡아뒀던 것이 해소됐습니다. 규칙 표기 형식도 확정했습니다.

```
automaticRules=ZenRule[id=<ID>,…,pkg=<패키지>,component=…,configActivity=…]
```

초기 자동 규칙은 양쪽 다 2개이고 둘 다 `pkg=android` 입니다. 20주차에 "몇 번째 요청에서 거부됐는가"를 셀 때 두 이미지의 출발점이 같다는 뜻입니다.

최종 대조에서 두 이미지의 프로브 출력 차이는 **빌드 지문 두 줄뿐**입니다. 기준선으로는 이게 맞는 모습입니다.

## 5. 시행착오와 정정

### 5-1. 없다고 판정한 것이 있었다

기준선 프로브의 첫 실행이 이렇게 나왔습니다.

```
cmd notification allow_dnd                     없음
cmd notification disallow_dnd                  없음
cmd notification allow_listener                없음
```

18주차 카드가 `allow_dnd` 를 정책 접근 부여 경로로 잡아뒀는데 그게 없다는 뜻이니, 20주차 계획이 통째로 흔들립니다. 그런데 직접 확인해보니 셋 다 멀쩡히 있었습니다.

원인은 제 탐지 방식이었습니다. `cmd notification --help` 로 사용법을 받으려 했는데 이건 유효한 인자가 아닙니다.

```
$ adb shell cmd notification --help
Unknown command: --help
```

사용법은 **인자 없이** 실행해야 나옵니다. 저는 "Unknown command" 한 줄을 받아놓고 거기서 서브커맨드 이름을 찾고 있었으니 전부 "없음"이 나올 수밖에 없습니다.

신호는 있었습니다. **셋이 나란히 "없음"으로 나왔다는 것** 자체가 이상했습니다. `allow_listener` 는 아주 흔한 서브커맨드입니다. 하나가 없는 것과 전부 없는 것은 의심할 대상이 다릅니다. 지금은 사용법 헤더(`SUBCMDs:`)를 못 받으면 판정 자체를 무효로 표시하게 고쳤습니다.

### 5-2. 맞는 값을 틀린 방법으로 냈다

규칙 개수를 세는 부분이 처음엔 2를 냈습니다. 실제 규칙도 2개라 맞는 값입니다. 그런데 `pkg=android` 로 세어봤더니 8이 나왔습니다.

`dumpsys notification --zen` 은 같은 설정을 여러 번 찍습니다. 그래서 매치를 그냥 세면 덤프 반복 횟수만큼 배수가 됩니다. 처음 쓴 정규식이 2를 낸 것은 **우연히 첫 항목만 잡았기 때문**이었지, 규칙 수를 센 것이 아니었습니다.

정답이 나왔다고 방법이 맞는 것은 아닙니다. 규칙 id 를 뽑아 중복을 제거하는 방식으로 바꿨습니다. 20주차에 규칙이 수백 개로 늘어나면 처음 방식은 곧바로 깨졌을 것입니다.

### 5-3. 엉뚱한 기기를 측정했다

이번 구간에서 가장 위험했던 오류입니다. `sec-31-r03` 을 띄우라고 했는데 출력된 지문이 r05 였습니다.

```
$ bash tools/boot-avd.sh sec-31-r03
[ok] boot_completed=1
ro.build.fingerprint=…/SE1A.220826.006.A1/…    ← r05!
ro.build.version.security_patch=2022-10-01
```

앞선 작업의 에뮬레이터가 종료되지 않고 5554 를 쥐고 있었습니다. 새로 띄운 r03 은 5556 으로 밀렸고, `adb wait-for-device` 와 인자 없는 `adb shell` 은 **먼저 붙은 쪽**을 잡습니다. 스크립트는 성공했다고 보고했습니다.

**baseline 과 patched 가 조용히 뒤바뀔 수 있는 오류입니다.** 그 상태로 20주차를 돌렸다면 "패치된 이미지에서 취약점이 재현된다" 같은 결론이 나왔을 것이고, 원인을 찾느라 한참 헤맸을 겁니다.

세 겹으로 막았습니다.

- `boot-avd.sh` 가 실행 중인 에뮬레이터를 발견하면 시작하지 않고 실패합니다
- 부팅 후 `adb emu avd name` 이 요청한 AVD 와 같은지 확인합니다
- `compare-images.sh` 의 이전 인스턴스 정리를 고정 `sleep 5` 에서 **사라질 때까지 폴링**으로 바꿨습니다

세 번째가 근본 원인입니다. 17주차에 "고정 대기가 콜드 스타트를 못 따라간다"는 걸 배워놓고 부팅 쪽만 폴링으로 고쳤는데, **정리 쪽에는 같은 교훈을 적용하지 않았습니다.** 같은 실수를 같은 파일 안에서 반쪽만 고쳐둔 셈입니다.

### 5-4. 부팅 완료가 사용 가능을 뜻하지 않는다

`sys.boot_completed=1` 이 떠도 패키지 매니저는 아직 응답하지 않을 수 있습니다. 20주차에는 프로브 앱을 설치해야 하는데 바로 `install` 을 걸면 실패합니다. `pm list packages` 가 응답할 때까지 기다리는 단계를 추가했습니다.

## 6. 도달 상태와 다음 구간

| 커리큘럼 | 상태 |
| --- | --- |
| 1~18주 | 완료 |
| **19주 이미지 쌍 준비·기준선** | **완료** — AVD 2대, 냉부팅 대조, 기준선 수집 |
| 20주 프로브 작성과 대조 실행 | 다음 |
| 21주 안전한 검증 | 하네스로 대조, 한계 명시 |
| 22주 근본 원인 분석 | 패치 diff·호출 흐름 |

20주차에는 Activity 하나짜리 프로브 앱을 쓰고, 자동 Zen 규칙을 반복 등록하면서 **몇 번째 요청에서 거부되는지**를 기록합니다. 기대하는 차이는 이것입니다.

```diff
- ZENPROBE limit_hit_at=none
+ ZENPROBE limit_hit_at=<순번>
```

한계도 적어둡니다. 이미지가 단일 변수가 아니라는 점(7개 파일, 커널 포함)이 가장 큽니다. 그리고 r03 이 컴포넌트 단위 한도를 이미 갖고 있을 가능성은 여전히 확정하지 못했습니다 — 상수는 정수라 문자열 스캔으로 판정할 수 없습니다. 프로브가 거부된 순번을 출력하도록 설계했으므로, 양쪽이 같은 순번에서 막히면 그 자체가 신호가 됩니다.

> **이후 확정**: 이 우려는 현실이 됐습니다. 20주차 첫 대조에서 두 이미지가 똑같이 101 에서 막혔고, **r03 에도 한도 100 이 있었습니다.** 여기서 설계해 둔 "순번 출력" 덕분에 재현 실패로 끝나지 않고 판별 측정으로 넘어갈 수 있었습니다. [20주차](/posts/android-security-study-week20/) 참조.

디스크는 13GB 남았습니다. 이미지 두 개가 8.4GB, AVD 두 대가 5GB 입니다.

## 마치며

구성 작업이라 기록할 것이 별로 없을 줄 알았는데, 오히려 이 구간에서 측정 오류를 세 개 잡았습니다. 그중 하나는 **엉뚱한 기기를 측정하면서 성공했다고 보고하는** 것이었고, 그대로 뒀으면 다음 구간의 결론이 통째로 뒤집혔을 겁니다.

그리고 실험 절차 자체가 만들어낸 차이를 하나 봤습니다. 스냅샷으로 시작 상태를 맞추면 편하지만, 그 스냅샷을 언제 떴는지가 결과에 남습니다. 두 이미지를 비교한다고 생각했는데 실제로는 **두 스냅샷을 비교하고 있었습니다.**

17주차에 "관측 결과보다 관측 도구를 먼저 의심하자"고 적고, 18주차에 "측정 대상이 정말 그것인지부터 확인하자"고 적었는데, 이번엔 하나가 더 붙습니다. **비교할 두 대상을 같은 상태로 놓는 절차 자체가 차이를 만들 수 있다.** 세 번 다 결론이 아니라 준비 과정에서 생긴 문제였다는 게 공통점입니다.
