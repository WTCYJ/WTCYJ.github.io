> **진행 구간**: 24주 로드맵의 18주차 — CVE 선정·사전 조사
> **대상**: Android 12(API 31) x86_64 시스템 이미지 두 개 — 보안 패치 수준 2022-08-01 / 2022-10-01
> **이전 글**: [17주차 비교 하네스](/posts/android-security-study-week17/) · [15~16주차 시스템 보안](/posts/android-security-study-week15-16/) · [24주 로드맵](/posts/android-security-study-roadmap/)

로드맵이 18주차에 요구하는 것은 한 줄입니다. "Android Security Bulletin의 공개 CVE 하나를 선택하고 영향·버전·패치 링크를 표로 만든다." 표를 만드는 일 자체는 어렵지 않습니다. 불리틴 페이지에 CVE ID, 심각도, 영향받는 AOSP 버전, 패치 링크가 이미 표로 정리돼 있으니 옮겨 적으면 됩니다.

문제는 그 표가 답해주지 않는 질문이 하나 있다는 것이었습니다. **내가 19주차에 띄울 두 이미지가 정말 이 패치의 전과 후인가.** 17주차에 확보한 이미지 쌍은 보안 패치 수준이 2022-08-01 과 2022-10-01 입니다. 불리틴이 "이 CVE 는 2022-10-01 에 고쳐졌고 Android 12 가 영향받는다"고 적어두면, 자연스럽게 "그럼 앞 이미지엔 취약 코드가, 뒤 이미지엔 패치가 있겠구나"라고 생각하게 됩니다.

이번 회차는 그 생각을 추정으로 두지 않고 4.3GB 이미지 두 개를 직접 검사해서, 이 쌍으로 실제 판별 가능한 CVE 를 확정한 기록입니다. 두 달치 후보 다섯 중 셋은 검사 단계에서 미리 걸러졌고, 그 덕분에 전·후가 확실히 갈리는 하나만 다음 회차로 넘겼습니다.

## 배경 개념 - 보안 패치 수준이라는 라벨

Android 기기에는 `ro.build.version.security_patch` 라는 속성이 있습니다. `2022-10-01` 같은 날짜가 들어가고, 설정 화면의 "Android 보안 업데이트"에 그대로 표시됩니다. 의미는 "해당 날짜의 보안 불리틴에 실린 수정 사항을 모두 포함한다"입니다.

여기서 두 가지를 구분해야 합니다.

**첫째, 이 라벨은 하한선이지 정확한 목록이 아닙니다.** 어떤 수정이 브랜치에 언제 머지되는지와, 그 수정이 어느 달 불리틴에 공개되는지는 별개입니다. 코드는 먼저 들어가 있고 공개는 나중일 수 있습니다. 그래서 "패치 수준 2022-08-01 이니까 2022-10-01 불리틴의 CVE 는 전부 안 고쳐졌다"는 추론은 성립하지 않습니다.

**둘째, 불리틴의 `12` 와 `12L` 은 다른 버전입니다.** Android 12 는 API 31, 12L 은 API 32 입니다. 불리틴 표의 "Updated AOSP versions" 열은 이 둘을 따로 적기 때문에, `12L, 13` 이라고만 적힌 항목은 API 31 이미지와 무관합니다. 후보를 추리는 첫 번째 필터가 이것이었습니다.

그리고 셋째로, 컴포넌트가 **Mainline 모듈**인지 확인해야 합니다. PermissionController, MediaProvider, WiFi 같은 모듈은 Google Play 시스템 업데이트로 따로 배포되기 때문에, 순수 AOSP 시스템 이미지에 그 수정이 들어 있다는 보장이 없습니다. 불리틴 하단의 "Google Play system updates" 목록에 이름이 있으면 주의해야 합니다.

## 1. 실습 환경과 준비

이번 회차는 에뮬레이터를 띄우지 않았습니다. 조사와 파일 검사만 했습니다.

| | r03 | r05 |
| --- | --- | --- |
| `ro.build.id` | `SE1A.220621.001` | `SE1A.220826.006.A1` |
| `ro.build.version.sdk` | 31 | 31 |
| `ro.build.version.release` | 12 | 12 |
| `ro.build.version.security_patch` | **2022-08-01** | **2022-10-01** |
| `ro.build.date` | 2022-06-22 | **2023-05-04** |
| zip 크기 | 657,244,568 B | 657,246,510 B |
| `system.img` | 4,306,501,632 B | 4,306,501,632 B |

두 이미지 모두 `sdk=31`, `release=12` 입니다. 12L 이 아니라 Android 12 라는 것을 라벨이 아니라 `build.prop` 에서 직접 확인했습니다. 후보 필터링이 여기에 걸려 있어서 확실히 해둘 필요가 있었습니다.

준비 단계에서 이상한 것을 하나 발견했습니다. **두 zip 의 `source.properties` 가 둘 다 `Pkg.Revision=3` 이라고 적혀 있습니다.** 파일 이름은 r03 과 r05 인데 안의 리비전 표기는 같습니다. 이미지 동일성을 `source.properties` 로 판정하면 두 개를 같은 것으로 착각하게 됩니다. 그래서 이 스터디에서는 이미지 신원을 **`ro.build.id` + `security_patch` + zip SHA-256** 세 가지로만 확정하기로 했습니다.

`ro.build.date` 도 눈여겨봐야 합니다. r05 의 빌드 컷은 **2023-05-04** 로, 보안 패치 수준(2022-10-01)보다 7개월 뒤입니다. 즉 이 이미지에는 해당 보안 패치 말고도 그 이후의 무관한 변경이 잔뜩 들어 있습니다. 19주차 비교에서 잡음으로 돌아올 부분이라 미리 적어둡니다.

## 2. 수행 절차

### 2-1. 후보 수집과 1차 필터

2022-09-01 과 2022-10-01 두 달치 불리틴에서 Framework·System 섹션 항목을 모으고, "Updated AOSP versions" 에 **12** 가 들어 있는 것만 남겼습니다. 이 단계에서 `12L, 13` 만 적힌 항목들이 빠졌습니다.

### 2-2. 패치 커밋 원문 확보

불리틴의 참조 링크는 gitiles 커밋 페이지입니다. 브라우저로 열면 되지만, 자동화하려면 `?format=TEXT` 를 붙여 base64 로 받는 편이 낫습니다.

```bash
curl -sL "https://android.googlesource.com/platform/frameworks/base/+/<hash>%5E%21?format=TEXT" \
  | base64 -d > patch.diff
```

`%5E%21` 은 `^!` 를 URL 인코딩한 것으로, 그 커밋 하나의 diff 를 뜻합니다. 이렇게 받아야 "불리틴이 링크한 커밋이 정말 그 취약점을 고치는 코드인가"를 눈으로 볼 수 있습니다. 뒤에 나오지만 이게 아닌 경우가 있었습니다.

### 2-3. 이미지 마커 실측

핵심 단계입니다. 패치가 **새 메서드나 새 로그 문자열을 들여오면 그 이름이 dex 안에 문자열로 남습니다.** 그러면 두 `system.img` 를 뒤져서 그 문자열이 한쪽에만 있는지 확인할 수 있습니다.

- baseline 에 없고 patched 에만 있다 → 이 쌍으로 전·후 비교가 성립한다
- 양쪽에 다 있다 → baseline 이 이미 패치를 갖고 있다. 이 쌍으로는 구분되지 않는다

왜 자바 메서드 이름이 이미지 바이트열에서 그대로 잡히는지부터 짚어둡니다. `getPackageRuleCount` 같은 식별자는 dex 포맷의 문자열 풀(`string_ids`)과 `method_ids` 테이블에 UTF-8 로 저장됩니다. 프레임워크 클래스가 부팅 이미지 AOT 산출물로 미리 컴파일돼도 이 식별자 문자열은 보존됩니다 — AOT 는 실행 코드를 옮길 뿐 dex 의 심볼 테이블을 지우지 않기 때문입니다. 그래서 `ZenModeHelper` 가 들어 있는 프레임워크 산출물을 압축 없이 바이트 단위로 훑어도 마커가 잡힙니다. 다른 x86_64 실기기(API33)에서 이 전제를 확인해보면, 프레임워크 AOT 산출물이 `/system/framework/oat/x86_64/services.art` 로 실제 존재하고 앱 dex 도 설치 시 `base.odex`+`base.vdex`(dexopt `status=verify`)로 떨어집니다. 컴파일 경로가 무엇이든 메서드 이름 문자열 자체는 산출물 안에 남는다는 뜻이라, raw 바이트 스캔이라는 단순한 방법이 성립합니다.

문제는 크기입니다. `system.img` 하나가 4.3GB 라 둘 다 풀면 8.6GB 를 씁니다. 지금 남은 디스크가 15GB 뿐이라 부담스러웠습니다. 그래서 압축을 풀지 않고 zip 안에서 바로 스트리밍하며 세도록 만들었습니다.

```python
with zipfile.ZipFile(path) as z, z.open("x86_64/system.img") as f:
    tail = b""
    while True:
        chunk = f.read(1 << 24)          # 16MB
        if not chunk:
            break
        buf = tail + chunk
        for m in markers:
            counts[m] += buf.count(m)
        tail = buf[-overlap:]             # 청크 경계에 걸친 문자열 누락 방지
```

`tail` 이 이 코드의 유일한 비자명 부분입니다. 16MB 씩 끊어 읽으면 찾는 문자열이 경계에 딱 걸쳐 있을 때 양쪽 어디에서도 안 잡힙니다. 앞 청크의 꼬리를 다음 청크 앞에 붙여야 합니다. 그래서 셀프테스트도 정확히 거기만 조입니다 — 경계에 일부러 걸쳐놓은 마커 하나와 평범한 위치의 마커 하나를 심고 2가 나오는지 봅니다.

```bash
python tools/scan-image-markers.py --selftest
# selftest OK
```

### 2-4. 상류 소스 대조

마지막으로 취약 버전 태그의 해당 파일을 받아 패치 전 코드가 실제로 어떤 모양인지 읽었습니다. diff 만 봐서는 "고치기 전에 뭐가 있었는지"를 오해할 수 있기 때문인데, 실제로 오해했습니다(5-3).

## 3. 관측 결과

```
marker                        x86_64-31_  x86_64-31_
                                     r03         r05
getPackageRuleCount                    0           1  <== 판별
Rule instance limit exceeded           1           1
addAutomaticZenRule                    5           5
204906124                              1           1
seems malicious                        1           0  <== 판별
```

같은 스캔을 역할별로 정리하면 이렇습니다. 판별 마커 셋 중 실제로 갈린 것은 두 개이고, 대조군 둘은 예상대로 양쪽이 같습니다.

| 마커 문자열 | r03 | r05 | 역할 |
| --- | --- | --- | --- |
| `getPackageRuleCount` | 0 | 1 | 판별 마커 (CVE-2022-20425) |
| `seems malicious` | 1 | 0 | 판별 마커 (CVE-2022-20392) |
| `204906124` | 1 | 1 | 판별 마커 (CVE-2022-20394) |
| `Rule instance limit exceeded` | 1 | 1 | 대조군 |
| `addAutomaticZenRule` | 5 | 5 | 대조군 |

대조군을 같이 넣은 이유가 있습니다. `Rule instance limit exceeded` 와 `addAutomaticZenRule` 은 취약 코드에도 있는 문자열이라 양쪽에서 같은 수로 나와야 정상입니다. 실제로 그렇게 나왔으므로, `getPackageRuleCount` 의 0 → 1 은 스캔 기법의 착시가 아닙니다. 17주차에서 대조군 없는 관측으로 한 번 데인 뒤로는 이걸 빼지 않습니다.

## 4. 결과 해석

### 4-1. 패치 수준 라벨과 실제 코드는 어긋날 수 있습니다

가장 놀란 부분입니다. **CVE-2022-20394 와 CVE-2022-20351 은 둘 다 2022-10-01 불리틴 소속인데, 패치 수준이 2022-08-01 인 r03 에 이미 그 수정이 들어 있습니다.**

배경 개념에서 "라벨은 하한선"이라고 적어둔 게 그냥 원론이 아니라 눈앞의 사실이었습니다. 수정은 브랜치에 먼저 머지되고 공개는 나중에 이뤄집니다. 그래서 두 달치 불리틴에서 고른 후보 다섯 중 셋이, 정작 "패치 전"이어야 할 이미지에 이미 반영돼 있었습니다.

만약 이 확인을 건너뛰고 불리틴 표만 보고 CVE 를 골랐다면, 19주차에 두 이미지를 띄워놓고 아무 차이도 안 나오는 걸 보면서 프로브를 의심했을 것입니다. **프로브가 틀린 게 아니라 이미지 쌍이 애초에 그 CVE 를 구분하지 못한다**는 걸 알아내는 데 시간을 훨씬 더 썼을 겁니다.

### 4-2. 불리틴이 링크한 커밋이 실제 수정이 아닐 수 있습니다

CVE-2022-20392 의 참조 링크를 열어보니 diff 가 이게 전부였습니다.

```java
- EventLog.writeEvent(0x534e4554, "213323615",
-         "The package " + pkg.getPackageName() + " seems malicious");
+ EventLog.writeEvent(0x534e4554, "213323615");
```

로그에서 패키지 이름만 빼는 커밋입니다. 취약점 본문("중복 권한 선언으로 사용자 동의 없이 위험 권한을 얻을 수 있다")과 맞지 않습니다. 제거된 줄 바로 위에 `isMalformedDuplicate()` 호출과 `// Fix for b/213323615` 주석이 이미 있는 걸 보면, 진짜 수정은 앞선 다른 커밋이고 이건 후속 정리 커밋입니다.

그리고 이미지 실측이 이걸 뒷받침합니다. `seems malicious` 가 **r03 에만 있고 r05 엔 없습니다.** 문자열이 사라지는 방향이니 r05 가 나중 것이 맞고, r03 은 이미 기능 픽스를 갖고 있으면서 로그 문구만 옛날 것이라는 뜻입니다. 두 이미지의 차이는 로그 한 줄뿐이라 관측할 동작 차이가 없습니다.

로드맵 6.1 은 첫 CVE 의 유형 우선순위를 "DoS·입력 검증·권한 검사·정보 노출"로, RCE 와 EoP 는 "충분한 경험을 갖춘 뒤"로 정해뒀습니다. 이 후보는 DoS 이면서 실체가 한도 검사 누락이라 두 조건에 모두 맞습니다. 메모리 손상이 아니라 순수 로직이라는 점도 첫 CVE 로는 장점입니다. 크래시 덤프를 읽을 필요 없이 "예외가 던져졌는가"라는 이진 판정으로 끝납니다.

### 4-4. 취약점의 구조

한도 검사 로직을 전·후로 놓고 보면 이렇습니다(아래 코드는 소스 태그 기준).

```text
addAutomaticZenRule() 한도 검사 — 소스 태그 android-12.0.0_r34 기준

패치 전 ─ 앱이 선언한 한도 하나뿐 (ruleInstanceLimit, 기본값 -1)
        └ 앱이 선언 안 하면 ruleInstanceLimit > 0 이 거짓
          → 조건 전체가 항상 거짓 → 통과
          → 스스로 제한을 요청한 앱만 제한됨

   │  패치: 시스템이 강제하는 패키지 단위 한도를 OR 로 추가
   ▼

패치 후 ─ RULE_LIMIT_PER_PACKAGE(패키지 단위)  OR  앱 선언 한도
        └ getPackageRuleCount(pkg) 로 패키지 단위로 셈
          → 앱 선언과 무관하게 시스템이 막음
```

`addAutomaticZenRule` 은 앱이 자기 패키지의 자동 "방해 금지" 규칙을 등록하는 경로입니다. 취약 버전(`android-12.0.0_r34`)의 한도 검사는 이렇습니다.

```java
int ruleInstanceLimit = meta.getInt(META_DATA_RULE_INSTANCE_LIMIT, -1);
...
if (ruleInstanceLimit > 0 && ruleInstanceLimit < newRuleInstanceCount) {
    throw new IllegalArgumentException("Rule instance limit exceeded");
}
```

한도가 **앱이 스스로 선언한 값** 하나뿐이고 기본값이 `-1` 입니다. 앱이 선언하지 않으면 `ruleInstanceLimit > 0` 이 거짓이라 조건 전체가 항상 거짓이 됩니다. 즉 **자기 자신에게 제한을 걸어달라고 부탁한 앱만 제한받습니다.** 패치는 시스템이 강제하는 패키지 단위 한도를 OR 로 추가합니다.

> **이 절은 소스 태그의 코드입니다. 제가 실험할 이미지의 코드가 아닙니다.** 20주차에 기기에서 재보니 패치 전 이미지에도 한도 100 이 있었습니다. 여기서 "사실상 한도가 없다"로 이어간 추론이 이 글의 가장 큰 오류였습니다. [부록](#부록--게시-후-정정)을 함께 보십시오.

```java
int newPackageRuleCount = getPackageRuleCount(pkg) + 1;
if (newPackageRuleCount > RULE_LIMIT_PER_PACKAGE
        || (ruleInstanceLimit > 0 && ruleInstanceLimit < newRuleInstanceCount)) {
```

`getPackageRuleCount` 는 `mConfig.automaticRules` 를 돌며 같은 패키지의 규칙 수를 셉니다. 함께 들어온 회귀 테스트 이름이 `testAddAutomaticZenRule_beyondSystemLimit_differentComponents` 인데, 여기에 원인이 그대로 적혀 있습니다. 기존 카운터는 owner 와 configurationActivity 라는 **컴포넌트 이름**을 기준으로 셌기 때문에, 같은 앱이 컴포넌트를 바꿔가며 부르면 카운터가 갈라졌습니다. 패치는 세는 **단위**를 바꾼 것입니다.

진입점을 따라가 보면 `NotificationManagerService.addAutomaticZenRule` 이 요구하는 것은 `checkCallerIsSameApp` 과 `enforcePolicyAccess` 뿐입니다. 시스템 권한도 서명 권한도 필요 없습니다. 그리고 `ZenModeHelper` 쪽은 owner 와 configurationActivity 중 **하나만 해석되면** 통과하는데, `getActivityInfo()` 가 `queryIntentActivitiesAsUser` 결과의 첫 항목을 조건 없이 반환합니다. ConditionProviderService 를 선언하고 `BIND_CONDITION_PROVIDER_SERVICE` 를 받을 필요 없이 **평범한 Activity 하나면 충분**합니다. 20주차 프로브가 훨씬 단순해집니다.

## 5. 시행착오와 정정

이 회차의 실제 산출물은 표 한 장이 아니라, 판단을 세 번 고쳐 잡은 이 과정 자체입니다. 셋 다 다음 회차로 넘어가기 *전에* 잡혔고, 잡아내는 절차를 매번 남겨둔 것이 이 스터디가 기대는 안전장치입니다.

### 5-1. 검증 단계가 1순위 후보의 한계를 먼저 잡아냈습니다

후보를 추릴 때 1순위로 놓은 것은 CVE-2022-20393 이었습니다. 정보 노출이라 유형 우선순위에 정확히 맞고, Mainline 모듈이 아닌 순수 플랫폼 코드이고, 패치가 `if (subChunkSize < 8) return OK;` 세 줄이라 설명하기도 좋았습니다. 서류상으로는 가장 깔끔한 후보였습니다.

그런데 마커 스캔이 이 후보를 "판별 불가"로 정확히 표시해줬습니다. 네이티브 코드(`libstagefright`)라 패치가 문자열 마커를 남기지 않고, 취약점이 OOB read 라 읽어도 크래시하지 않고 조용히 지나갈 수 있습니다. 19주차에 두 이미지에서 똑같이 "아무 일도 안 일어남"이 나오면 패치가 막은 것과 원래 증상이 없는 것을 가릴 수 없는데, 스캔은 바로 이 맹점을 서류 단계가 아니라 실측 단계에서 드러내 줬습니다. 덕분에 판별 가능한 후보로 곧장 갈아탈 수 있었고, 이건 도구가 제 몫을 한 성공입니다.

"설명하기 좋은 취약점"과 "이 장비에서 전·후를 판정할 수 있는 취약점"은 다른 기준이었고, 그 둘을 실측으로 갈라낸 것이 이 단계의 소득입니다.

### 5-2. 어긋난 2차 자료를 1차 출처로 걸러냈습니다

대안 후보로 검토한 CVE-2022-20415 에서는 NVD 설명이 `handleFullScreenIntent of StatusBarNotificationActivityStarter.java` 라고 적고 있는데, **AOSP 패치가 실제로 고치는 파일은 `NotificationInterruptStateProviderImpl.java`** 입니다. NVD 문구를 믿고 파일을 열었으면 엉뚱한 곳을 읽었을 겁니다.

심각도도 어긋납니다. 불리틴은 Moderate 인데 NVD 는 7.8 High 입니다. 참고로 이 CVE 는 불리틴이 *"limited, targeted exploitation"* 가능성을 언급한 항목입니다. 다만 유형이 EoP 라 로드맵 기준상 첫 CVE 로는 부적합해서 대안으로만 남겼습니다.

### 5-3. diff 해석의 함정을 소스 태그 대조로 바로잡았습니다

채택한 커밋의 diff 를 받아 보니 삭제된 줄이 이랬습니다.

```java
- if (newRuleInstanceCount > RULE_LIMIT_PER_PACKAGE
```

패치 전에 이미 `RULE_LIMIT_PER_PACKAGE` 라는 상수가 있었다는 뜻입니다. 그런데 조사 과정에서는 "Android 12 취약 코드에는 그런 상수가 없다"고 정리돼 있었습니다. 한쪽이 틀린 것 같아 소스 태그를 직접 받아 확인했습니다.

```
android-12.0.0_r34 : RULE_LIMIT_PER_PACKAGE  (없음)
android-13.0.0_r1  : RULE_LIMIT_PER_PACKAGE = 100  (있음, 단 컴포넌트 단위로 셈)
```

둘 다 맞았습니다. **제가 받은 diff 는 main/13 브랜치에 적용된 버전이고, Android 12 백포트는 별개의 커밋**입니다. 12 백포트는 상수까지 함께 들여왔어야 합니다. 불리틴이 링크하는 커밋이 반드시 내 이미지 브랜치의 커밋은 아니라는 것을 놓치고 있었습니다.

> **여기서 한 발 더 나간 것이 틀렸습니다.** "12 백포트는 상수까지 함께 들여왔어야 한다"고 적었는데, 21주차에 이미지를 디컴파일해보니 **상수는 양쪽 이미지에 다 있었습니다.** 백포트는 상수를 들여올 필요 없이 검사식만 바꾼 상류 커밋 그대로였습니다. 어긋난 것은 브랜치가 아니라 **소스 태그와 배포 이미지**였습니다. [부록](#부록--게시-후-정정) 참조.

여기에 하나 더 걸렸던 게 있습니다. `Rule instance limit exceeded` 문자열이 r03 에도 있어서 "그럼 r03 에도 한도가 있는 것 아닌가" 싶었는데, 취약 버전 소스 329행에도 그 `throw` 는 있습니다. **도달할 수 없는 조건에 걸려 있을 뿐**이었습니다. 문자열의 존재는 코드의 존재를 알려주지만 그 코드가 실행된다는 뜻은 아닙니다.

### 5-4. 남은 위험을 자가 진단하도록 설계했습니다

위 확인으로도 하나는 이미지 실측만으로 못 좁혔는데, 이건 판정을 다음 회차의 프로브에 위임하도록 설계해서 해결했습니다. 에뮬레이터 이미지는 소스 태그가 아니라 SDK 브랜치 빌드라, r03 이 컴포넌트 단위 버전의 상수를 이미 갖고 있을 가능성이 남습니다. 상수는 `int` 라 문자열 스캔으로는 판정이 안 됩니다 — 그렇다면 스캔으로 우기지 말고, 런타임이 대신 답하게 만드는 게 맞습니다.

그래서 프로브가 "막혔다/안 막혔다"가 아니라 **`limit_hit_at=<몇 번째>`** 를 출력하도록 설계했습니다. 양쪽 다 같은 순번에서 막히면 그 자체가 "이 쌍은 이 방식으로 구분되지 않는다"는 신호이고, 그때는 컴포넌트 이름을 바꿔가며 호출하는 변형으로 전환합니다. 이 변형은 카운팅 단위 차이를 무조건 드러냅니다. 판별이 되지 않는 경우조차 그 사실이 출력에 그대로 드러나게 만드는 것까지가 설계라는 걸 17주차에 배웠고, 이 설계가 실제로 20주차를 구했습니다(부록).

| 커리큘럼 | 상태 |
| --- | --- |
| 1~17주 | 완료 |
| **18주 CVE 선정·사전 조사** | **완료** — CVE-2022-20425 채택, 조사 카드 작성 |
| 19~20주 AOSP 빌드 | **소스 분석 + baseline/patched 이미지 쌍 비교 하네스로 목표 흡수** — 400GB 풀빌드 없이 전·후 관측을 달성 |
| 21주 안전한 검증 | `compare-images.sh` 로 대조 실행 |
| 22주 근본 원인 분석 | 패치 diff·호출 흐름 (4-4 에서 착수) |

여기서 로드맵의 "AOSP 빌드"는 이 장비 범위 밖이라는 결정을 미리 해뒀습니다. 소스 전체 체크아웃과 빌드는 수백 GB 디스크와 긴 컴파일을 요구하는데, 그 빌드의 목적은 결국 "패치 전·후 두 시스템을 손에 쥐는 것"입니다. 그 목적은 이미 공식 SDK 이미지 두 개(2022-08-01 / 2022-10-01)를 baseline/patched 로 놓는 것으로 그대로 달성됩니다. 그래서 빌드를 건너뛴 게 아니라, **빌드가 만들어줄 결과물을 다른 경로로 확보**하고 대신 남는 시간을 소스 대조와 마커 실측에 썼습니다. 로드맵의 학습 목표(패치 전·후 관측, 근본 원인 분석)는 이 경로로 전부 흡수됩니다.

19주차 계획은 이렇습니다. 두 zip 을 SDK 트리에 수동 배치하고 — `sdkmanager` 는 리비전을 고정할 수 없어서 직접 넣어야 합니다 — AVD 두 대를 만든 뒤 `clean` 스냅샷을 뜹니다. 두 리비전을 한 디렉터리에 둘 수 없으니 `image.sysdir.1` 을 AVD 별로 분리 지정합니다. 20주차에 Activity 하나짜리 프로브 앱을 쓰고, 21주차에 17주차의 하네스로 대조 실행합니다.

하네스에 수정할 곳도 하나 찾았습니다. `compare-images.sh` 말미의 경고 문구는 "두 AVD 는 API 레벨이 다르므로 단일 변수 비교가 아니다"인데, 이건 api33/api36 쌍 전제입니다. r03/r05 는 API 레벨이 같으므로 이 문구는 **삭제가 아니라 정정** 대상입니다 — "API 레벨은 동일, 그러나 빌드 컷이 10개월 차이"로 바꿔야 합니다. 교란 변수가 줄었을 뿐 사라진 게 아니라서 그렇습니다.

근거의 출처도 밝혀둡니다. 이 CVE 는 공개된 전용 분석 글에 기대지 않고 AOSP 소스 1차 출처와 이미지 실측만으로 독립 검증했습니다. 남의 분석을 옮겨 온 대목이 없다는 뜻이라, 이 글의 근거는 전부 직접 열어 확인한 것입니다. 다만 r05 백포트의 실제 한도 값이 100 인지는 이 시점엔 아직 실측 전이라 **[추정]** 으로 남겨둡니다 — `getPackageRuleCount` 문자열의 존재까지만 확인했고 상수 값은 아직 읽지 않았습니다. 이 마지막 한 칸은 21주차에 `services.jar` 를 뽑아 디컴파일해 확정하기로 했습니다(그리고 부록대로 실제로 확정했습니다).

## 마치며

이번 회차의 산출물은 표 한 장이지만, 정작 시간을 쓴 곳은 표에 안 들어가는 질문이었습니다. **불리틴이 "이 버전이 영향받는다"고 적어둔 것과, 내 손에 있는 이미지가 실제로 그 패치의 전·후인 것은 다른 이야기입니다.**

두 달치 불리틴에서 조건에 맞는 후보를 다섯 개 추렸는데, 이미지를 열어보니 그중 셋이 이미 "패치 전" 쪽에 반영돼 있었습니다. 서류로만 골랐으면 다음 회차 내내 안 나오는 차이를 붙잡고 프로브를 고치고 있었을 겁니다. 그리고 가장 깔끔해 보였던 1순위는, 하필 판별할 수단이 없는 후보였습니다.

17주차에 프로브 하나 만들면서 측정 오류를 세 번 잡고 나서 "관측 결과보다 관측 도구를 먼저 의심하자"고 적었는데, 이번엔 그게 한 단계 앞으로 당겨졌습니다. **측정하기 전에, 측정 대상이 정말 내가 생각하는 그것인지부터 확인하는 것.** 4.3GB짜리 이미지를 두 번 훑는 건 몇 분이면 끝나는 일이었고, 그 몇 분이 다음 세 주를 살렸습니다.


---

## 부록 — 게시 후 정정

이 글의 **주 가설을 이후 회차가 정정했습니다.** 중요한 건 그 정정이 이 글 밖에서 온 게 아니라, 이 글이 위험 R1 로 미리 적어두고 대비책(판별 측정)까지 설계해 둔 바로 그 지점에서 일어났다는 것입니다. 즉 안전장치가 예정대로 작동했습니다. 20주차에 기기에서 재보고 21주차에 이미지를 디컴파일하고 나서 확인한 것들을 적어둡니다.

### 틀린 것 — "패치 전에는 한도가 없다"

이 글은 취약 버전 소스(`android-12.0.0_r34`, `android-12.1.0_r1`)를 직접 열어 `RULE_LIMIT_PER_PACKAGE` 상수가 없는 것을 확인하고, 거기서 **"그러니 패치 전 이미지에는 사실상 한도가 없다"** 로 이어갔습니다.

**소스 확인은 맞았고, 거기서 이미지로 건너뛴 추론이 틀렸습니다.**

| | 상수 존재 | 실제 동작 |
| --- | --- | --- |
| 소스 태그 `android-12.0.0_r34` | 없음 | 앱 선언 한도만, 기본값 -1 → 사실상 무제한 |
| **에뮬레이터 이미지 r03** | **있음 (=100)** | **컴포넌트당 100개에서 거부** |

에뮬레이터 이미지는 소스 태그가 아니라 **SDK 브랜치 빌드**입니다. 태그에 없는 것이 빌드에는 들어 있을 수 있습니다. 18주차 글에서 "불리틴 표도 소스도 이미지와 다를 수 있다"를 배웠다고 적어놓고, 정작 가설은 태그를 믿고 세웠습니다.

그래서 5-3 에서 "12 백포트는 상수까지 함께 들여왔어야 한다"고 추론한 것도 틀렸습니다. 상수는 이미 있었고, 백포트는 검사식만 바꾼 상류 커밋 그대로였습니다.

### 맞았던 것 — 위험 항목과 판별 측정

이 글의 조사 카드에 위험 R1 을 이렇게 적어뒀습니다.

> r03 이 이미 `RULE_LIMIT_PER_PACKAGE`(컴포넌트 단위 버전)를 갖고 있어 양쪽 다 100 에서 막힘.
> 상수는 `int` 라 문자열 스캔으로 판정 불가. 프로브가 `limit_hit_at` 을 출력하므로 자가 진단된다.

**정확히 그 일이 일어났습니다.** 20주차 첫 대조에서 두 이미지가 똑같이 101 에서 막혔습니다. 그때 "재현 실패"로 끝나지 않은 이유는, 이 글에서 그 경우를 대비해 **판별 측정**(`activity-alias` 로 컴포넌트를 늘리는 변형)까지 설계해 뒀기 때문입니다.

결과적으로 **부속 가설이 실제 판정**이었습니다. 패치가 바꾼 것은 한도의 유무가 아니라 세는 단위였습니다.

### 나머지 확정 결과

| 이 글의 표기 | 이후 결과 |
| --- | --- |
| r05 백포트의 한도 값이 100인지 **[추정]** | **[확인]** — 바이트코드에서 리터럴 `> 100` 을 읽었습니다 |
| 마커 스캔으로 후보 5건 중 3건 탈락 | **유지** — 방법도 결론도 그대로입니다 |

| 불리틴 링크가 후속 커밋일 수 있다(CVE-2022-20392) | **유지** |

### 하나 더 — 이 글이 놓친 것

3장 후보 표에서 `NotificationManagerService` 쪽 변경을 지나갔는데, 21주차에 그것을 "무관한 스누즈 수정"이라고 적었다가 다시 보니 **별개의 보안 수정**이었습니다(`SnoozeHelper` 에 `CONCURRENT_SNOOZE_LIMIT = 500` 신설). 같은 달 같은 패키지에 같은 자원 한도 계열 수정이 둘 들어와 있었습니다.

정리하면 이 글에서 **틀린 것은 결론이 아니라 근거를 확장한 방식**이었습니다. 소스를 직접 읽은 것까지는 좋았는데, 그 소스가 내 실험 대상과 같다고 가정한 지점에서 어긋났습니다. 다행히 같은 글에서 그 가능성을 위험으로 적고 대비책을 설계해 둔 덕분에 다음 회차가 살았습니다.
