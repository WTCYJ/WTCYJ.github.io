이 글은 24주 Android 보안 학습 로드맵의 7~8주차, 동적 분석 구간 기록입니다.

직전 구간에서는 APK를 뜯어보는 정적 분석으로 테스트 앱 `kr.wtcy.memovault`의 약점을 표로 정리했습니다. 이 글에서는 그 표의 각 행이 실제로 동작하는지를 logcat, 관찰 프록시, adb 명령을 통해 기기 위에서 하나씩 재현한 과정을 살펴보겠습니다. 재현에 성공한 것만큼이나 제가 잘못 판정했던 두 번의 실수도 함께 다루겠습니다.

## 배경 개념 - 동적 분석의 기본 요소

이번 구간에서 계속 등장하는 용어를 먼저 정리하고 가겠습니다. Android 보안을 처음 보는 분이라도 뒤의 실습을 따라올 수 있도록 짧게만 짚겠습니다.

**동적 분석**이란 앱을 실제로 실행한 상태에서 동작을 관찰하는 분석 방식을 말합니다. 코드와 설정 파일만 읽는 정적 분석과 달리, 실행 중에 실제로 어떤 값이 오가고 어떤 화면이 뜨는지를 직접 확인합니다. 정적 분석이 "이렇게 돼 있다"를 알려준다면, 동적 분석은 "그래서 실제로 이렇게 된다"를 보여줍니다.

**logcat**은 Android 시스템과 앱이 남기는 로그를 실시간으로 보여주는 도구이고, **adb**(Android Debug Bridge)는 PC에서 기기나 에뮬레이터에 명령을 보내는 도구입니다. 우리가 `adb shell am start`로 앱의 화면을 강제로 띄우거나 `adb shell cat`으로 파일을 읽어보는 것이 모두 여기에 해당합니다.

**프록시**는 앱과 서버 사이에 끼어 앉아 오가는 트래픽을 들여다보는 중계 프로그램입니다. 앱이 서버로 보내는 요청은 화면에 표시되지 않기 때문에, 어떤 값이 실제로 네트워크에 실려 나가는지 확인하려면 통신 경로 위에 관찰 지점을 두는 수밖에 없습니다. HTTPS라면 TLS를 가로채기 위해 기기에 인증서를 설치해야 하지만, 평문 HTTP라면 그 단계가 통째로 사라집니다.

**exported 컴포넌트**란 다른 앱이 인텐트로 직접 호출할 수 있도록 공개된 컴포넌트를 말합니다. 매니페스트에서 `exported="true"`로 선언된 액티비티는 설치된 아무 앱이나, 혹은 adb 명령 한 줄로도 실행할 수 있습니다. 이때 함께 전달되는 부가 데이터를 **인텐트 extra**라고 부릅니다.

**scoped storage**는 Android 10 이후 도입된 저장소 접근 제한 정책으로, 앱이 자기 몫의 디렉터리 바깥에는 마음대로 쓸 수 없게 막는 구조입니다. 뒤에서 경로 이탈을 시도할 때 이 정책이 어디까지 막아주는지가 그대로 결과로 나타납니다.

## 1. 실습 환경과 준비 - 관찰 프록시와 검증 스크립트

지난 구간에서 APK를 분석해 표를 아홉 개 만들었습니다. exported 컴포넌트가 몇 개인지, 로그에 무엇이 찍히는지, WebView 설정이 어떤지를 정리한 표입니다. 그런데 표는 "이렇게 돼 있다"까지만 말합니다.

이번 구간은 그 각 행을 **기기에서 실제로 밟아보는** 단계였습니다. 그리고 밟는 절차를 스크립트로 남겨서, 다음 구간에서 취약점을 고친 뒤 같은 것을 다시 돌릴 수 있게 만들었습니다.

앞서 설명한 것처럼 프록시는 앱과 서버 사이에 앉아 트래픽을 들여다보는 장치입니다. 로드맵에는 Burp나 ZAP을 쓰라고 적어뒀는데 둘 다 설치돼 있지 않았습니다. 설치할까 하다가 생각해보니, **이 앱은 평문 HTTP를 씁니다.** TLS 가로채기도 인증서 설치도 필요 없습니다. 경로 위에 그냥 앉으면 됩니다.

그래서 파이썬 표준 라이브러리로 관찰용 프록시를 짜서 앱과 서버 사이에 넣었습니다. 앱을 다시 빌드하기 싫어서 프록시가 앱이 원래 보던 포트(8099)를 차지하고, 실제 서버를 8097로 옮겼습니다.

결과부터 말씀드리면 심어둔 약점 10개가 전부 재현됐습니다. 다만 그 과정에서 제가 두 번 틀렸고, 그 이야기가 이 글의 절반을 차지합니다.

## 2. 재현 절차 - 인텐트 주입과 적대적 서버 응답

exported 컴포넌트를 밟아보는 절차가 이번 구간에서 제일 인상적이었던 부분입니다. exported 컴포넌트는 앞서 설명했듯 외부에서 인텐트로 직접 호출할 수 있는 컴포넌트입니다. 세 가지 확인을 이어 붙이면 하나의 흐름이 됩니다. 먼저 exported 액티비티 세 개를 외부에서 그대로 실행하고, 다음으로 인텐트 extra를 하나 더 붙여 소유권 검사를 건드리고, 마지막으로 같은 액티비티에 파일 경로를 넘겨 앱에게 자기 파일을 읽어달라고 시킵니다.

두 번째 단계는 대조군과 실험군을 나눠서 확인했습니다. 사용한 명령은 다음과 같습니다.

```bash
# 대조군 — override 없이 bob 소유 메모를 연다
adb shell am start -n kr.wtcy.memovault/.MemoDetailActivity --es memo_id 4
  → "이 메모를 볼 권한이 없습니다"

# 실험군 — extra 하나를 더 붙인다
adb shell am start -n kr.wtcy.memovault/.MemoDetailActivity \
  --es memo_id 4 --ez owner_override true
```

경로 이탈(path traversal)이란 `../`처럼 상위 디렉터리를 가리키는 문자열을 파일 이름에 섞어 넣어, 원래 의도한 디렉터리 바깥에 접근하는 기법을 말합니다. 이 앱은 서버 응답에 들어 있는 파일명을 로컬 저장 이름으로 그대로 씁니다. 서버가 장악된 상황을 흉내내려고 테스트 서버에 적대적 응답 모드를 넣었습니다.

## 3. 관측 결과 - 평문 캡처·인텐트 주입·경로 이탈

### 3-1. 평문 HTTP 캡처와 하드코딩 관리자

아래는 1절에서 만든 관찰 프록시가 남긴 실제 캡처 기록입니다.

```
[2026-08-09T09:59:16] >>> POST /login
    X-Api-Key: mv_live_7c1f9a3e42b8d05612ff8ab34c7e9d20  ** 민감
    User-Agent: Dalvik/2.1.0 (Linux; U; Android 13; sdk_gphone64_x86_64 ...)
    body: {"username":"alice","password":"alice123"}  ** 민감값 포함
[2026-08-09T09:59:16] <<< 200  {"token": "mvt_alice_0001", ...}  ** 민감값 포함

[2026-08-09T09:59:17] >>> GET /memos
    Authorization: Bearer mvt_alice_0001  ** 민감
```

비밀번호, API 키, 세션 토큰이 전부 그대로 보입니다.

앱 쪽에 하드코딩해둔 관리자 비밀번호도 이번에 눌러봤습니다. 서버에는 존재하지 않는 계정인데 로그인이 됩니다.

![메모 목록 화면입니다. 상단에 "사용자: admin"과 "관리자 메뉴" 버튼이 떠 있는데, 하단 상태줄에는 "서버 연결 실패: HTTP 401: {"error": "missing or invalid token"} (로컬 캐시 표시)"라고 적혀 있습니다](/assets/img/android-security-study/08-admin-fallback.png)

화면 위쪽은 `사용자: admin`에 **관리자 메뉴**까지 떠 있는데, 아래 상태줄은 `서버 연결 실패: HTTP 401`입니다. 서버는 이 세션을 모릅니다.

### 3-2. exported 컴포넌트와 샌드박스 경계

**첫째, exported 액티비티가 외부에서 그냥 뜹니다.**

아래는 각 액티비티를 외부에서 실행했을 때의 결과입니다.

```
MemoListActivity   -> Starting: Intent { cmp=kr.wtcy.memovault/.MemoListActivity }
MemoDetailActivity -> Starting: Intent { ... }
WebViewActivity    -> Starting: Intent { ... }
```

세 개 다 권한 거부가 없습니다.

**둘째, 인텐트 extra 하나로 소유권 검사가 무너집니다.** 앞 절의 실험군 명령을 넣은 결과가 이렇습니다.

![메모 상세 화면입니다. 제목 "비밀 메모", 작성자 bob, 본문 "이 줄이 다른 계정에서 보이면 인가 결함이다"가 표시되고 하단 상태줄에 id=4 override=true admin=false 라고 찍혀 있습니다](/assets/img/android-security-study/06-authz-bypass.png)

`override=true` 한 줄에 남의 메모가 열립니다.

**셋째, 앱에게 자기 파일을 읽어달라고 시킬 수 있습니다.** 같은 액티비티에 파일 경로를 extra로 주면, 앱이 그 파일을 읽어 서버로 올립니다. [1~4주차 글](/posts/android-security-study-week1-4/)에서 세션 파일이 그렇게 나갔습니다.

여기서 짚고 싶은 것이 있습니다. Android는 앱마다 별도의 사용자 ID를 부여해 서로의 데이터 디렉터리에 접근하지 못하도록 격리하는데, 이를 애플리케이션 샌드박스라고 부릅니다. 공격자는 `/data/data/kr.wtcy.memovault/`를 **직접 읽지 못합니다.** 이번에도 대조군으로 확인했습니다.

```
$ adb shell cat /data/data/kr.wtcy.memovault/shared_prefs/session.xml
cat: ... Permission denied
```

### 3-3. 경로 이탈 1차·2차 시도

**1차 — `../../../hostile-marker.txt`**

아래는 이때 관측된 logcat 출력입니다.

```
D MemoVault: POST /upload -> 201 {"raw_name": "../../../hostile-marker.txt", ...}
E MemoVault: java.io.FileNotFoundException:
  .../files/attachments/../../../hostile-marker.txt: open failed: EACCES (Permission denied)
```

앱은 서버가 준 이름을 의심 없이 `File()`에 넘겼습니다. **취약한 코드 경로는 확정입니다.** 그런데 플랫폼이 막았습니다. 앞서 설명한 scoped storage가 `Android/data/` 루트 쓰기를 차단합니다.

**2차 — `../hostile-marker.txt`**

상위로 한 단계만 올라가도록 줄여서 다시 시도했습니다.

```
I MemoVault: attachment cached at .../files/attachments/../hostile-marker.txt

$ ls files/
  drwxrws--- attachments
  -rw-rw----  29  hostile-marker.txt      ← attachments/ 밖
```

성공했습니다. `attachments/` 밖으로 나갔습니다.

## 4. 결과 해석 - 샌드박스는 정상, 데이터는 유출

앱이 자기 안에 박아둔 문자열 하나로 관리자 권한을 스스로 부여한 것입니다. 권한 판단을 클라이언트에 두면 이렇게 됩니다.

정적 분석에서 `usesCleartextTraffic="true"`를 플래그 하나로 봤을 때와, 캡처 파일에서 `password":"alice123"`을 볼 때의 체감은 서로 다릅니다. 같은 사실인데 후자가 훨씬 설득력 있습니다. 보고서에 무엇을 붙여야 하는지에 대한 답이기도 합니다.

**인증서 설치 단계가 없다는 점이 오히려 요점입니다.** HTTPS였다면 기기에 CA를 넣어야 하고, Android 7 이후로는 앱이 사용자 CA를 기본적으로 신뢰하지 않으니 그 자체가 방어층이 됩니다. 평문을 쓴다는 것은 그 층을 통째로 버린다는 뜻입니다.

샌드박스는 정상 작동합니다. 그런데 데이터는 나갔습니다. 경계를 뚫은 것이 아니라 **경계 안쪽에 있는 쪽에게 심부름을 시킨** 것입니다.

`exported="true"`가 위험한 이유를 문장으로는 여러 번 읽었는데, 거부 로그와 성공 화면을 나란히 놓고 보니 다르게 이해됐습니다.

경로 이탈의 정확한 결론은 **"경로 이탈은 실재하되 앱 자신의 외부 디렉터리 안으로 제한된다"**입니다. 1차만 보고 판단했으면 취약점을 놓쳤고, 2차만 보고 "임의 경로 쓰기"라고 적었으면 과대평가였습니다.

## 5. 시행착오와 정정

### 5-1. 한 번의 시도로 끝낼 뻔한 경로 이탈

1차 시도가 `EACCES`로 막혔을 때 "막혔으니 취약점이 아니다"로 끝낼 뻔했습니다.

3~4주차에 외부 저장소 노출을 과대평가했다가 심각도를 낮춘 적이 있는데, 같은 종류의 실수를 반대 방향으로 할 뻔했습니다. **경계는 한 번의 시도로 드러나지 않습니다.**

### 5-2. 검증 스크립트의 거짓 양성

이번 구간에서 제일 뜨끔했던 부분입니다. 거짓 양성(false positive)이란 실제로는 취약하지 않은데 취약하다고 잘못 판정하는 경우를 말합니다.

인가 우회를 처음에는 이렇게 판정했습니다.

```bash
if grep -q "권한이 없습니다" ui.xml; then  결과="거부됨"
else                                      결과="우회 성공"
fi
```

결과표에 **"우회 성공"**이 찍혔습니다. 그런데 화면을 직접 열어보니 이랬습니다.

![메모 상세 화면에 "메모를 찾을 수 없습니다"라는 제목과 "memo_id=4"만 표시돼 있습니다. 메모 본문도 작성자도 없습니다](/assets/img/android-security-study/07-false-positive.png)

바로 앞 단계에서 `pm clear`로 앱 데이터를 지웠고, 로컬 메모 DB가 비어서 대상 메모 자체가 없었습니다. 거부 문구가 뜨지 않은 것은 우회에 성공해서가 아니라 **검사할 대상이 없어서**였습니다.

문제는 **"거부 문구가 없으면 성공"이라는 부정 조건**이었습니다. 실패하는 경우와 애초에 실행되지 않은 경우를 구분하지 못합니다.

두 가지로 고쳤습니다. 판정을 긍정 증거로 바꿔서 bob 메모의 본문 문자열이 화면에 실제로 있어야 성공으로 치고, 대조군(override 없이 열면 거부되는지)을 붙였습니다. 둘 다 만족해야 "우회 성공"입니다.

취약점을 찾는 것보다 **찾았다고 잘못 말하지 않는 것이** 더 어렵다는 사실을 제 스크립트로 배웠습니다. 자동화한 검증은 자동으로 틀리기도 합니다.

### 5-3. 환경 때문에 시간을 쓴 함정들

기법 자체와는 별개로, 환경 때문에 시간을 쓴 것들을 남겨둡니다.

**`grep -c`는 일치가 없어도 `0`을 출력하고 종료 코드 1을 반환합니다.**

```bash
hits="$(grep -c 'pattern' file || echo 0)"
```

그래서 `|| echo 0`이 같이 실행돼 변수가 `"0\n0"`이 됐고, 결과표에 `토큰 노출 0\n0행`으로 찍혔습니다. `|| true`로 바꿔서 해결했습니다. 출력과 종료 코드가 따로 논다는 사실을 잊으면 이렇게 됩니다.

**서버를 재시작할 때마다 앱 토큰이 무효가 됩니다.** 토큰을 프로세스 메모리에 들고 있어서인데, 실험 중 설정을 바꾸느라 여러 번 재시작했고 그때마다 원인 모를 401을 디버깅했습니다. 세 번쯤 반복하고 나서야 패턴을 알아챘습니다. 절차에 "서버 재시작 후 앱 재로그인"을 넣었습니다.

**`adb backup`은 끝까지 가지 못했습니다.** 기기 화면에서 사용자가 직접 승인해야 하는데 헤드리스 에뮬레이터라 승인 UI를 누를 수 없었습니다. `dumpsys package`의 런타임 플래그로 `ALLOW_BACKUP`이 켜져 있다는 것까지만 확인하고, 실제 추출은 하지 못했다고 적었습니다. 확인하지 못한 것을 확인한 것처럼 적지 않는 것이 중요합니다.

## 마치며

세 구간째 같은 이야기를 적고 있습니다. 도구는 정직했고 제가 잘못 읽었다는 이야기입니다.

이번에는 종류가 하나 늘었습니다. 앞서는 **도구 출력을 잘못 해석**했고, 지난 구간에는 **도구가 볼 수 없는 것**이 있다는 사실을 확인했는데, 이번에는 **제가 만든 검증 도구가 틀린 답을 내놨습니다.**

세 번째가 제일 위험한 것 같습니다. 남의 도구는 의심하면서 내가 짠 스크립트는 잘 의심하지 않게 됩니다. 결과표가 마크다운 표로 예쁘게 나오면 더 그렇습니다.

그래서 대조군을 붙이는 습관을 들이기로 했습니다. "우회에 성공했다"를 주장하려면 "우회하지 않으면 실패한다"도 같이 보여야 합니다. 우리가 한 줄 더 실행하는 비용으로 거짓 양성을 거를 수 있다면, 그 한 줄은 붙일 가치가 있습니다.
