> **한 줄 결론**: 공개된 니모닉의 서명 weight 는 1, 계정 threshold 는 3 이다. 피해자는 **조회만 되고 출금은 안 되는** 지갑에 가스비를 넣게 되고, 그 TRX 는 **중앙값 57초** 만에 피의자 collector 로 쓸려 나간다. 미끼인 test USDT 는 그대로 남아 다음 피해자를 기다린다.

## 무엇이 주어졌나

ZIP 안에 `post.txt` 와 `pic1.png` 두 개뿐. 둘 다 같은 문구, 같은 Nile TRON 지갑, 같은 12단어 복구 문구를 제시한다.

| 파일 | SHA-256 |
|---|---|
| 원본 ZIP | `a1acf0fa38f4037e0c67e15af0e1fe6f09bff996c7e5b76f41aadf2d5c7db973` |
| `post.txt` | `0ab8c29348038c73b88f18eccdbbfd1e014b5c0e3da4545887d70630c5eef33f` |
| `pic1.png` | `83c43def76a11d2c78ffbebc6244ff4965281be06580848562d9a0cbeccb2f68` |

증거는 이게 전부다. 나머지는 **전부 온체인에서 가져와야 한다.**

## 1. 니모닉 → 주소 (오프라인)

BIP39/BIP32 표준 파생을 제3자 패키지 없이 구현했다. 순서는 이렇다.

1. 12단어를 NFKD 정규화
2. 빈 BIP39 passphrase 로 PBKDF2-HMAC-SHA512 2,048회 → seed
3. BIP32/secp256k1, TRON BIP44 경로 `m/44'/195'/0'/0/0`
4. **비압축** 공개키의 `x || y` 에 Keccak-256, 마지막 20바이트
5. TRON prefix `0x41` 을 붙여 Base58Check 인코딩

```
압축 공개키    : 03efd425a6de4e60ad0d5af15544070fac01744c4536e48a8774ad3ad0f28cf195
TRON hex 주소  : 4191271D44A0FF6D46A863FA01EA8D04EC6716BACF
Base58Check    : TPChqavCK3e4S6UCGGUCKnt6yeKn1XbugL
```

Keccak-256 은 SHA-3 와 패딩이 다르다(`0x01` vs `0x06`). 구현 검증용으로 잘 알려진 이더리움 테스트 벡터를 assert 로 박아 뒀다.

```python
# private key 1 -> 0x7e5f4552091a69125d5dfcb7b8c2659029395bdf
assert keccak256(pubkey_bytes(1, False)[1:])[-20:].hex() == "7e5f4552091a69125d5dfcb7b8c2659029395bdf"
```

address index 0~19 를 다 확인했지만 실제 계정·거래·권한변경이 있는 것은 index 0 하나였다.

## 2. 네트워크 확인 — 같은 주소, 다른 원장

게시물은 **Nile 테스트넷**을 명시한다. Nile 과 mainnet 은 주소 생성 규칙이 같지만 원장이 완전히 별개다. 같은 Base58 주소를 mainnet TronGrid 에서 조회하면 **계정이 활성화조차 되어 있지 않다.**

문제의 USDT 계약은 `TXYZopYRdj2D9XRtbG411XZZ3kM5VkAeBf` — Nile faucet 이 "USDT test tokens" 라고 명시하는 그 주소다. 즉 화면에 찍히는 1,944 USDT 는 **금전 가치가 없는 테스트 토큰**이고, 피해자가 뺏기는 건 가스비로 넣은 TRX 다.

## 3. 함정의 구조 — AccountPermissionUpdate

미끼 주소의 첫 권한변경 트랜잭션:

```
TXID       : e663de6fde24a64faf1548eae943bfe1933ea27d4239d8617064e64643fe62c8
거래 생성   : 2026-06-17 06:39:48 KST
블록 시각   : 2026-06-17 06:39:51 KST
결과       : SUCCESS
승인 주소   : 미끼 주소 TPChqav… 1개
```

**공개된 니모닉 키 자신이 이 권한변경을 실행했다.** 공개 전에는 단독 키였으니 가능한 일이다. 변경 후 owner 와 active(id 2) 는 둘 다 이렇게 된다.

| 키 주소 | weight | 정체 |
|---|---|---|
| `TPChqavCK3e4S6UCGGUCKnt6yeKn1XbugL` | 1 | **공개 니모닉 키** |
| `TEqVCMiYoHs5H7fhqC7zqgWuXkeZWKKDBc` | 2 | 피의자 핵심 키 · collector |
| `TS24nf8BR1afsAsqEwQ1Re9ztVFgiKYFhh` | 1 | 실제 공동서명 키 |
| `TXTdy94EqXzMx3SSEkum6qiWuxV6zk8cAF` | 1 | 등록된 예비 권한 키 |
| **threshold** | **3** | 합산 weight 3 이상이어야 승인 |

숫자가 전부다. 공개 니모닉 보유자는 weight 1 → TRX 전송도, TRC-20 호출도, **권한 복구도** 단독으로 못 한다. 피의자는 `TEq`(2) + `TS24`(1) = 3 으로 혼자 다 된다.

## 4. 실제 sweep 은 누가 서명했나

대표 sweep 트랜잭션을 `/wallet/getapprovedlist` 에 넣어 실제 서명자를 확인했다.

```bash
curl -sS -X POST -H 'Content-Type: application/json' \
  -d '{"value":"b4296ce49598558f32b9b53820a341349c7bb6f2340fdea3f0918d72abb69142"}' \
  -o /tmp/sweep_tx.json \
  'https://nile.trongrid.io/wallet/gettransactionbyid'

curl -sS -X POST -H 'Content-Type: application/json' \
  --data-binary @/tmp/sweep_tx.json \
  'https://nile.trongrid.io/wallet/getapprovedlist'
```

결과는 `TEqVC…`(weight 2) 와 `TS24nf…`(weight 1) 둘뿐. **공개 니모닉 키는 이 서명에 쓰이지 않았다.**

"누구나 아는 니모닉으로는 자산을 못 움직이고, 비공개 피의자 키 조합만 출금을 승인한다" 는 명제의 직접 증거다. 권한 테이블만 보면 "그럴 것이다" 지만, `getapprovedlist` 는 "그랬다" 를 준다.

## 5. 회계 — 지표를 섞지 않기

사건 구간을 권한변경 블록 직후(`2026-06-17 06:39:51 KST`)부터 마지막 반복 sweep(`12:31:54 KST`)까지로 **고정**했다. 이후에 새 거래가 붙어도 숫자가 안 변하게 하기 위해서다.

```
피해자성 입금  : 25건, 17개 고유 송신 주소, 174.38 TRX
미끼→collector : 26건, 전부 TEqVC… 행, 168.006 TRX
outbound 수수료: 25건×1.335 + 1건×1.334 = 34.709 TRX
권한변경 후 setup 잔액 : 30 TRX
구간 종료 잔액 : 1.665 TRX
```

회계식이 정확히 닫힌다.

```
30 + 174.38 = 168.006 + 34.709 + 1.665 = 204.38 TRX
```

그래서 지표를 이렇게 분리했다.

| 지표 | 값 |
|---|---|
| 피해 규모 (gross deposit) | **174.38 TRX** |
| 온체인 총 sweep | 168.006 TRX (최초 setup 30 TRX 포함) |
| 피해자 자금 중 collector 귀속분 | 약 138.006 TRX |
| 피해자 자금 중 수수료 소모 | 34.709 TRX |
| 사건 직후 잔류 | 1.665 TRX |

"탈취액" 을 하나의 숫자로 적으라고 하면 셋 중 무엇을 고르든 절반은 틀린다. **피해자가 잃은 돈**과 **피의자가 챙긴 돈**은 수수료만큼 다르고, sweep 총액에는 피의자 자기 돈 30 TRX 가 섞여 있다.

## 6. 자동화의 흔적

입금과 바로 다음 sweep 사이 시간차의 **중앙값이 57초**, 25건 중 24건이 60초 이내였다.

API polling 이나 자동 sweep 봇의 강한 정황이다. 다만 봇 소스코드가 온체인에 남는 건 아니므로 "자동화 추정" 으로 적었다. 타이밍 분포는 행태 증거이지 코드 증거가 아니다.

## 7. 현재 4,001.665 TRX — 함정이 하나 더

사건 구간이 끝난 뒤 `TVF2Mp9QY7FEGTnr3DBpFLobA6jguHyMvi` 에서 2,000 TRX 가 두 번 들어와 잔액이 4,000 TRX 늘었다.

이걸 피해액에 넣으면 안 된다. 이 주소는 **아주 많은 주소에 2,000 TRX·1,000 USDT 정액을 뿌리는 고거래량 distributor** 이고, Nile faucet 화면이 제시하는 금액과 정확히 같다. 피해자 입금이 아니라 faucet 이다.

여기서 한 가지가 뒤집힌다. 지금 미끼 주소에는 4,001 TRX 가 있고 staked/delegated Energy 는 없다. 그러니 **지금 출금이 안 되는 이유는 "가스 부족" 이 아니라 "threshold 미달"** 이다. 과거에 피해자 TRX 가 곧바로 쓸려 나간 것은 그와 별개의 탈취 단계다.

## 8. 탈취 메커니즘 정리

1. 피의자가 나중에 공개할 니모닉으로 미끼 주소를 만든다
2. test USDT 를 채워 큰 잔액이 있는 것처럼 보이게 한다
3. 공개 니모닉 키 하나로 `AccountPermissionUpdateContract` 를 실행
4. threshold 를 3 으로 올리고 자기 키를 weight 2·1 로 등록
5. 니모닉을 SNS 에 공개 — "USDT 를 꺼내면 차익" 이라는 욕심을 자극
6. 피해자가 지갑에 니모닉을 넣으면 **주소·잔액 조회는 정상 동작한다** (조회에는 서명이 필요 없다)
7. 피해자가 TRC-20 전송용 Energy/수수료를 마련하려 TRX 를 보낸다
8. 피해자 서명 weight 1 < threshold 3 → 전송 거부
9. 피의자 두 키는 2+1 로 유효한 다중서명 구성
10. 입금 감시 후 1분 내 TRX 를 collector 로 sweep
11. test USDT 는 그대로 남아 같은 미끼를 반복

6번이 이 사기의 심리적 핵심이다. **조회가 정상 동작한다는 게 함정을 완성한다.** 지갑 앱에 잔액이 찍히니 피해자는 "가스만 채우면 된다" 고 믿는다.

## 9. 피의자 연관 주소

**직접 연관**

| 주소 | 역할 | 근거 |
|---|---|---|
| `TPChqav…` | 미끼 지갑 | 니모닉의 표준 파생 주소, 권한변경·입금·sweep 의 중심 |
| `TEqVCMi…` | 핵심 권한 키 · collector | owner/active weight 2, 대표 sweep 실제 서명자, 26회 168.006 TRX 전액 수취 |
| `TS24nf8…` | 공동서명 키 | weight 1, 대표 sweep 실제 서명자 |
| `TE9cKBb…` | 미끼 setup 자금원 | 미끼에 130 TRX 공급, swap 으로 최초 1,944 test USDT 조성 |
| `TFz7gAX…` | 권한 키 공통 자금원 | 권한변경 27분 전 세 권한 키에 각각 25 TRX 를 **3초 간격**으로 공급 |

`TFz7` 의 3초 간격 펀딩이 결정적이다. 서로 무관한 지갑이 27분 뒤 같은 계정의 권한 키로 동시에 등록될 리 없다.

**간접 연관** (중간 신뢰도)

| 주소 | 역할 |
|---|---|
| `TXTdy94…` | 등록된 예비 권한 키. `TFz7` 의 같은 펀딩을 받았지만, 확인한 대표 sweep 의 실제 서명자는 아니라 개인키 사용은 **미확정** |
| `TNgrGUg…`, `TUkECXz…`, `TAY58TF…` | 유인자산 조성 중간 지갑. 연속 swap 경로에 사용됐으나 단독 거래만으로 동일 자연인 통제 확정 불가 |

유인자산 조성 경로: `TVF2`(faucet) → `TFz7` → `TNgr` → `TUkECX` → `TAY58` → `TE9c` → `TPCh`.

**제외한 주소**

- `TVF2Mp9…` — faucet/distributor 성 주소. 관찰된 자금원이지만 피의자 통제로 보지 않았다
- swap pool/router 계약 주소 — DEX 유동성이지 지갑이 아니다
- 피해자성 입금 17개 주소 — 피의자로 분류하지 않았고, **온체인 주소 수와 실제 사람 수가 같다고 단정할 수도 없다**

## 정리 — 이 문제에서 남는 것

**니모닉이 곧 통제권은 아니다.** TRON 의 다중서명 권한 모델에서는 키를 알아도 weight 가 threshold 에 못 미치면 아무것도 못 한다. 이 사기는 그 간극 하나로 설계돼 있다.

**조회와 서명은 다른 연산이다.** 잔액이 보인다고 움직일 수 있는 게 아닌데, 지갑 UI 는 그 차이를 보여 주지 않는다.

**사건 구간을 먼저 고정한다.** 온체인은 계속 갱신되므로 구간을 못 박지 않으면 보고서 숫자가 조회할 때마다 달라진다. "현재 잔액" 은 API 응답의 `meta.at` 시각과 함께 보존해야 한다.

**지표 이름을 정확히 쓴다.** gross deposit / 총 sweep / 피의자 귀속분 / 수수료 / 잔류는 전부 다른 숫자다. 하나로 뭉개면 회계식이 안 닫힌다.
