4부 내내 우리는 찾는 쪽이었다. AOSP 트리를 걷고(1장), 패치 계보를 추적하고(3장), 하네스로 크래시를 만들고, sibling variant를 사냥했다(17장). 그런데 크래시 하나를 손에 쥔 그 순간, 연구는 절반만 끝났다. 나머지 절반 — 그걸 벤더에게 어떻게 전달하고, 언제 세상에 공개하느냐 — 가 사실 더 어렵고, 더 자주 망가진다.

이 글은 crash를 finding으로, finding을 책임 있는 리포트로 바꾸는 마지막 공정을 정리한 기록이다. Android Security Bulletin의 게재 주기, 조율된 공개(CVD)의 임베고, CVSS를 정직하게 매기는 법, 그리고 내 wabt·libsoup 제보와 한 건의 익명 폐쇄소스 사례가 실제로 어떤 타임라인을 그렸는지를 놓는다.

> **한 줄 결론**: 좋은 리포트는 "무엇이 어떻게 왜 터지는지"를 최소 재현으로 증명하고 심각도를 벡터로 정직하게 매긴 뒤 벤더의 패치 주기에 맞춰 임베고를 지키는 것이다 — 크래시를 취약점으로, DoS를 RCE로 부풀리는 순간 이 모든 게 무너진다.

## 무엇을 다루고, 무엇을 알아야 하는가

이 장은 4부의 닫는 글이다. 앞 장들이 "발견"이었다면 여기는 "전달"이다. 세 가지 선수 개념이 밑에 깔린다. 첫째, 3장의 patch provenance — 불리틴 게재, AOSP 커밋, CVE 발급은 서로 다른 사건이라는 것. 둘째, 9장의 crash minimization — 최소 재현이 없는 리포트는 벤더가 재현조차 못 한다. 셋째, 18장의 회귀 검증 — 좋은 리포트는 패치와 함께 회귀 테스트를 제안한다. Atlas 쪽에선 심각도 산정에 완화(Atlas C37)의 유무가 들어간다는 정도만 알면 된다.

전체 구조는 하나의 파이프라인이다. 발견 → 최소화 → 심각도 산정(CVSS) → 채널 선택(벤더 트래커 / Android Security Rewards) → 임베고 협의 → 패치 → 불리틴·CVE 공개 → 회귀 반영. 이 파이프라인의 어느 칸도 건너뛰면 리포트가 무시되거나, 더 나쁘게는 무기화 창을 스스로 연다.

## 핵심 개념 — 리포트의 세 산출물과 공개 타임라인

리포트는 산문 한 편이 아니라 세 개의 산출물이다.

| 산출물 | 무엇 | 흔한 실패 |
|--|--|--|
| 재현(PoC) | 최소 입력 + 실행 절차 + sanitizer 로그 | 코퍼스 통째로 첨부, ASan 출력 없음 |
| 영향(impact) | 신뢰 경계·프리컨디션·결과를 벡터로 | "심각함"만 쓰고 벡터 없음 |
| 수정 제안(fix) | root cause 지목 + 회귀 테스트 초안 | 증상만 지목, 패치가 sibling 놓침 |

공개 타임라인은 이 산출물을 벤더의 시간축에 얹는 문제다. Google은 CVE 발급 권한을 가진 CNA이고, Android의 공개는 매월 초(대체로 첫째 주 월요일)에 Android Security Bulletin으로 묶여 나온다. `Source-confirmed` 불리틴이 게재되면 AOSP에 패치가 반영되고 CVE·심각도·SPL이 함께 공개되는데, 반영 시점의 정확한 지연은 원문 재확인이 필요하다. 즉 "패치 머지"와 "불리틴 공개"와 "CVE 발급"은 같은 날이 아니다 — 이 셋을 한 사건으로 뭉치면 임베고를 언제까지 지켜야 하는지 감을 잃는다.

임베고란 보고자가 받은 정보(패치 전 취약점 상세)를 공개 합의 시점 전까지 공개하지 않는 약속이다. Project Zero류의 데드라인 정책(대략 90일 + 유예)은 벤더가 무한정 뭉개는 걸 막는 장치인데, 정책 세부는 원문 재확인이 필요하다. `Reported` 이 절차 자체는 표준으로도 정리돼 있다 — ISO/IEC 29147(취약점 공개)과 30111(취약점 처리)이 보고자·벤더 양쪽의 역할을 규정한다. `Source-confirmed`

> **[그림 1]** 내 wabt GitHub 이슈에서 report→triage→fix 머지까지의 코멘트 타임라인과, 병합된 회귀 테스트가 첨부 PoC를 그대로 참조하는 부분을 함께 담은 캡처 — *실측 스크린샷 자리*

## 신뢰 경계와 위협 모델

공개 프로세스의 위협 모델은 코드가 아니라 **정보**다. 취약점 상세는 패치가 배포·설치되기 전까지 "누가 아느냐"가 곧 위험이다. 신뢰 경계는 세 겹으로 놓인다 — 보고자(나) → 벤더(패치 권한) → 대중(패치 소비자). 조기 공개는 이 경계를 무너뜨려 아직 패치받지 못한 사용자에게 무기화 창을 연다. 반대로 무기한 임베고는 벤더가 위험을 방치하게 둔다. CVD는 이 둘 사이의 균형점이다.

여기서 오해 하나 — "패치가 머지됐으니 이제 공개해도 된다"는 틀렸다. 오픈소스라면 머지된 diff 자체가 취약점을 드러내지만(1-day), 그 패치가 다운스트림·배포판에 반영되기 전까지 사용자는 여전히 취약하다. Android라면 AOSP 커밋과 실제 OEM 롤아웃 사이에 patch-gap(15장)이 있다. 그래서 공개 타이밍의 기준은 "머지"가 아니라 "소비자 도달"이어야 한다.

DoS를 RCE로 부풀리는 것도 결국 신뢰의 문제다. 심각도를 과장하면 첫 리포트는 통과할지 몰라도, triage에서 벤더가 벡터를 재산정하는 순간 보고자의 신뢰도가 깎인다. 다음 리포트는 더 의심받는다. 정직한 벡터가 장기적으로 이긴다.

## 분석 — 실제 제보 타임라인 네 건

내 자작 하네스·공개 프로젝트 제보 기록을 타임라인으로 놓으면 CVD의 실제 모양이 보인다.

| 대상 | 결함 | 채널 | 결과 / 타임라인 |
|--|--|--|--|
| wabt #2751 | wasm2c 파서 크래시(DoS) | GitHub 이슈(공개) | 보고→78일 만에 수정 머지, 패치는 제3자, 회귀 테스트가 내 PoC 그대로 |
| wabt #2750 | 같은 클래스 다른 표면 | GitHub 이슈(공개) | 여전히 Open, CVE/GHSA 없음 |
| libsoup Range | 정수 오버플로→assert DoS | GNOME GitLab | 제보 완료 |
| 폐쇄소스 이미지 뷰어(익명) | 무한 루프 DoS(CWE-835) | 벤더 비공개 | 보고서 완성, 제보 예정 — 벤더 통보 전이라 제품·모듈명 비공개 |

이 표에서 세 가지가 드러난다. 첫째, **오픈소스 공개 트래커는 그 자체가 공개다** — GitHub 이슈에 PoC를 붙이는 순간 임베고는 없다. 개발 도구의 오프라인 DoS라 위험이 낮아 이 선택이 합당했지만, 원격·메모리 손상급이면 비공개 채널이 먼저다. 둘째, **수정이 78일 걸렸고 패치는 내가 아닌 제3자가 썼다** — 보고자가 곧 패처는 아니다. 셋째, **병합된 회귀 테스트가 내 PoC를 그대로 참조했다** — 이게 리포트가 코드베이스에 남긴 실제 흔적이다. `Source-confirmed`

CVSS를 정직하게 매기는 예를 하나 들자. 위 표의 익명 폐쇄소스 뷰어 사례 — 파일을 열어야 발동하는 무한 루프는 가용성-only 결함이다(CWE-835). 벡터와 점수는 이렇게 재현된다.

```
CVSS:3.1/AV:L/AC:L/PR:N/UI:R/S:U/C:N/I:N/A:H
ISS     = 1 - (1-0)(1-0)(1-0.56)              = 0.56
Impact  = 6.42 × 0.56                          = 3.60   (S:U)
Exploit = 8.22 × 0.55 × 0.77 × 0.85 × 0.62     = 1.83
Base    = Roundup(3.60 + 1.83) = Roundup(5.43) = 5.5   → Medium
```

C·I가 None이고 A만 High다. 여기에 근거 없이 C:H/I:H를 얹거나 AV를 Network로 올리면 8점대 Critical이 나오지만, 그건 벡터와 현실이 어긋난 숫자다. 같은 클래스의 wabt 선례가 CVSS 3.3 LOW·DISPUTED로 처리된 것도 같은 이유다 — 오프라인 도구의 크래시는 대개 낮게, 때로 분쟁 처리된다. `Reported`

> **[그림 2]** Android Security Bulletin의 한 CVE 행 — CVE 번호·심각도·영향 컴포넌트·연결된 AOSP 패치 링크가 한 줄에 있고, 그 행이 게재된 SPL 날짜가 상단에 보이는 캡처 — *실측 스크린샷 자리*

## Root Cause — 리포트가 무시되는 진짜 이유

벤더가 리포트를 닫아버리는 근본 원인은 대개 취약점이 약해서가 아니라 **리포트가 재현·영향·수정 중 하나를 비웠기 때문**이다.

- 재현 공백: 최소화 안 된 입력, sanitizer 로그 없음 → 벤더가 재현 실패 → "정보 부족"으로 닫힘.
- 영향 공백: 벡터 없이 "critical"만 → triage가 강등 → 신뢰도 하락.
- 수정 공백: 증상만 지목하고 root cause·sibling(17장)을 안 짚음 → 패치가 표면 하나만 막고 형제 변종이 남음.

그리고 타이밍의 근본 원인이 하나 더 있다 — 보고자의 긴박함과 벤더의 패치 주기는 애초에 시간축이 다르다. 연구자는 "지금 위험"을 느끼지만 벤더는 월간 불리틴·QA·롤아웃에 묶여 있다. 이 간극을 인정하고 데드라인을 합의로 다루는 게 CVD고, 인정하지 않고 터뜨리는 게 full disclosure의 사고다.

## 방어와 회귀 검증

리포트의 최종 방어선은 산문이 아니라 **회귀 테스트**다. 18장에서 봤듯 좋은 패치는 그 버그를 영구히 막는 테스트를 남긴다. 보고자가 최소 PoC를 테스트 케이스 형태로 제안하면 그게 그대로 벤더 회귀 셋에 편입될 확률이 크게 오른다 — 내 wabt PoC가 병합 회귀 테스트가 된 게 그 증거다. `Source-confirmed`

- 최소 PoC를 "테스트 입력"으로 정리해 첨부한다(코퍼스 통째 금지, 9장).
- root cause 한 줄 + 제안 패치 방향 + sibling 표면 점검 결과(17장)를 함께 낸다.
- 심각도는 벡터로 매기고, 계산이 재현되게 벡터 문자열을 그대로 붙인다.
- 공개는 "패치 머지"가 아니라 "사용자 도달"을 기준으로, 임베고 합의 시점에 맞춘다.

이 네 개가 리포트를 "닫히는 이슈"에서 "코드베이스에 회귀 테스트로 남는 기여"로 바꾼다.

## 정리

- 크래시는 finding이 아니다. 최소 재현 + 정직한 벡터 + 수정 제안, 세 산출물이 갖춰져야 리포트다.
- 패치 머지·불리틴 게재·CVE 발급은 서로 다른 사건이다. 공개 타이밍은 "사용자 도달" 기준으로 잡는다.
- DoS를 RCE로, 크래시를 취약점으로 부풀리지 마라. 벡터와 현실이 어긋나면 신뢰를 잃는다.
- 리포트의 흔적은 회귀 테스트로 남는다 — 최소 PoC를 테스트 형태로 내라.

**점검 질문** — (1) 오픈소스 GitHub 이슈에 PoC를 붙이는 것이 왜 이미 "공개"인가? (2) 파일을 열어야 발동하는 가용성-only 크래시의 CVSS 벡터를 쓰고 점수를 재계산하라. (3) "패치가 머지됐으니 공개해도 된다"가 왜 틀릴 수 있는가?
