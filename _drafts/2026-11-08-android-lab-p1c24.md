모바일 앱 감사를 처음 자동화하면 대부분 같은 실수를 한다 — MobSF 리포트의 빨간 경보 개수를 그대로 취약점 개수로 옮겨 적는 것. 자동 스캐너는 빠르고 넓지만, 스캐너가 확정하는 건 "이 패턴이 소스 어딘가에 존재한다"까지다. 그 패턴이 **실제로 도달 가능한 경로에 있고, 어떤 조건에서 트리거되는지**는 사람이 코드를 역추적해야 판정된다. 이 경계를 흐리면 오탐이 리포트를 오염시키고, 반대로 정적 스캔이 못 보는 런타임 결함은 통째로 빠진다.

이 글은 자작/공개 교육용 취약앱(InsecureBankv2·DIVA 등)을 MobSF로 정적·동적 스캔한 뒤, 각 경보를 jadx/smali로 역추적해 도달 가능성과 트리거 조건을 검증하고, 오탐과 미탐을 분류한 기록이다.

> **한 줄 결론**: 자동 스캐너의 경보는 "취약점"이 아니라 "후보 위치"다. **도달 가능성 + 트리거 조건 + 민감한 부작용** 세 가지가 모두 확인돼야 경보는 vuln으로 승격되고, 정적 스캔이 실행 상태를 못 보는 한 런타임 전용 결함은 반드시 미탐으로 남는다.

## 무엇을 다루고, 무엇을 알아야 하는가

이 글의 범위는 MobSF 산출물의 **후처리**다. 스캔을 돌리는 법이 아니라, 나온 경보를 한 건씩 코드로 되짚어 참/거짓을 가르는 절차를 다룬다. 대상 경보는 네 부류로 좁힌다 — 하드코딩 시크릿, exported 컴포넌트, 약한 암호, 평문 통신. 이 넷이 자동 스캔 오탐의 대부분을 차지한다.

선수 지식이 셋 깔린다. 실습 4장에서 jadx로 DEX를 정적 역컴파일하는 법을, 6장에서 매니페스트의 exported·permission이 만드는 공격면을, 11장에서 mitmproxy로 실제 통신을 관측하는 법을 이미 다뤘다. 개념 쪽에서는 Atlas C42가 crash/bug/vuln/exploit을 구분하는 사다리를, C55가 위협 모델과 영향 산정을 제공한다. 이 글의 판정은 결국 "MobSF 경보가 C42 사다리의 어느 칸에 있는가"를 묻는 일이다.

전체 구조에서 이 장은 **감사 파이프라인의 검증 게이트**다. 뒤이어 25장(커스텀 규칙 작성)·26장(MASVS 커버리지 매트릭스)·27장(회귀 테스트)이 여기서 걸러진 "진짜 결함"만 입력으로 받는다. 검증 없이 넘기면 뒤 단계 전체가 오탐 위에 쌓인다.

## 핵심 개념 — 경보는 "존재"이지 "도달"이 아니다

MobSF(Mobile Security Framework)는 오픈소스 정적·동적 분석 프레임워크로, APK를 넣으면 매니페스트 분석·코드 분석·시크릿 탐지 등을 자동 수행하고 각 항목에 심각도를 매긴다. 시크릿 탐지는 정규식 기반이고, exported 판정은 매니페스트와 intent-filter 규칙에 기반한다. `Source-confirmed`(MobSF GitHub/문서)

여기서 핵심은 **각 탐지 방식이 확정할 수 있는 것의 범위**가 다르다는 점이다. 표로 정리하면:

| 경보 부류 | MobSF가 확정하는 것 | MobSF가 **확정 못 하는 것** | 사람이 검증할 축 |
|--|--|--|--|
| 하드코딩 시크릿 | 정규식에 맞는 문자열이 존재 | 그 값이 살아있는 자격증명인지, 사용되는지 | 참조·xref → 크립토/네트워크 sink 도달 |
| exported 컴포넌트 | 외부에서 실행 가능(도달성) | 도달 후 위험한 동작을 하는지 | intent 처리 → 부작용 → permission 가드 |
| 약한 암호 | ECB/MD5/정적 IV 등 API 사용 | 민감 데이터를 보호하는 경로인지 | 데이터 흐름 → 보호 대상 → 경로 도달성 |
| 평문 통신 | http URL·cleartext 허용 존재 | 그 URL이 실제로 호출되는지 | 호출부 → 전송 데이터 민감도 |

패턴이 exported·약한암호처럼 **정확히 확정되는 축**과, 시크릿·평문처럼 **존재만 확정되는 축**을 섞어 다루면 안 된다. exported는 (signature/privileged 등 보호 permission이 없을 때) 도달성이 결정론적으로 확정되므로 "도달 후 무엇을 하나"만 보면 되고 — 보호 permission으로 가드된 컴포넌트는 비특권 외부 앱이 도달할 수 없어 '도달성 참'이 아니다 — 시크릿은 "존재"가 참이어도 "미사용 더미 상수"면 무해다. `Inferred`

위협 모델 관점에서 검증의 기준선은 하나다 — **경보가 신뢰 경계를 실제로 넘느냐**. 외부 입력이 닿지 않는 dead code의 약한 암호는 공격자 관점에서 존재하지 않는 것과 같고(C55), 반대로 exported 액티비티가 인증을 우회시키면 그건 이미 exploit 후보다(C42).

> **[그림 1]** InsecureBankv2 스캔 후 MobSF 리포트의 "Manifest Analysis"·"Code Analysis"·"Secrets" 섹션에서 경보 목록과 각 심각도 배지를 펼친 화면 — *실측 스크린샷 자리*

## 실습 환경과 안전 범위

전부 **자작 취약앱 또는 공개 교육용 취약앱**으로만 진행한다. InsecureBankv2·DIVA처럼 의도적으로 취약하게 만든 오픈소스 앱이 대상이고, 제3자 앱·프로덕션 앱 스캔은 하지 않는다. MobSF는 공식 Docker 이미지로 띄우고, 동적분석은 계측 가능한 에뮬레이터(1장에서 만든 `google_apis` userdebug AVD)에 붙인다. `Source-confirmed`(MobSF Docker 배포)

PoC는 도달성 확인용 최소 개념 수준이다 — 컴포넌트를 한 번 띄워 도달하는지 보는 정도이고, 무기화·데이터 탈취·지속성은 다루지 않는다.

## 실습 절차와 관측

### 가설
- **가설 A** — MobSF가 시크릿으로 올린 값 중 상당수는 xref 추적 시 미사용 상수·더미 값이라 sink에 도달하지 않는다(오탐). `Inferred`
- **가설 B** — MobSF가 exported로 표시한 컴포넌트는 (보호 permission이 없다면) 도달성은 참이지만, 그중 일부만 도달 후 실제 위험 동작을 하고 나머지는 무해하다. `Inferred`
- **가설 C** — 런타임 인증 우회·리플렉션으로 감춘 sink는 정적 리포트에 아예 안 나타난다(미탐). `Inferred`

### 절차
1. MobSF Docker로 대상 APK를 정적 스캔하고, 네 부류 경보를 표로 덤프한다.
2. 각 경보를 jadx-gui에서 문자열/심볼로 검색해 **선언 위치와 사용처(xref)**를 찾는다.
3. exported 경보는 **보호 permission 부재를 먼저 확인**한 뒤에만 `adb`로 도달성을 본다. 단 `adb shell`(uid 2000)은 서명·특권 permission을 다수 보유해 비특권 공격 앱보다 넓게 컴포넌트를 띄울 수 있으므로, `am start` 성공이 곧 '외부 공격 앱 도달 가능'을 증명하지는 않는다. `normal` 보호수준 permission이 걸린 경우 등 엄밀 검증이 필요하면 별도 비특권 테스트 앱으로 재확인한다.
4. 시크릿·약한암호·평문은 값이 **민감 데이터를 처리하는 sink(네트워크·인증·저장)에 도달하는지** 데이터 흐름을 따라간다.
5. 동적분석을 붙여 정적으로 안 보였던 경로(리플렉션·런타임 분기·WebView 브리지)를 관측하고, 정적 리포트에 없던 결함은 **미탐**으로 기록한다.

```bash
# (1) MobSF 정적 스캔 — 공식 Docker 이미지
#     재현성을 위해 실제 감사에서는 :latest 대신 digest로 고정한다
#     (예: opensecurity/mobile-security-framework-mobsf@sha256:<digest>) — 본문 '버전 고정' 항목 참조
docker run -it --rm -p 8000:8000 \
  opensecurity/mobile-security-framework-mobsf:latest
# 브라우저 http://localhost:8000 → InsecureBankv2.apk 업로드

# (3) exported 경보 도달성 확인 (교육용 취약앱 한정, 부작용 없는 최소 확인)
#     <컴포넌트>는 매니페스트에서 exported=true·보호 permission 부재를 실제로 확인한 값으로 교체
#     (어떤 컴포넌트가 인증 우회로 이어지는지는 반드시 대상 매니페스트로 실측 — 값 단정 금지)
adb shell am start -n com.android.insecurebankv2/.<매니페스트에서 확인한 exported 컴포넌트>
#   도달 O + 인증 우회 발생  → vuln 후보 (참)
#   도달 O + 아무 부작용 없음 → 무해 (실질 오탐)
#   Permission denial 로 거부  → 도달 X (오탐)
```

시크릿·평문 경보는 실행이 아니라 **역추적**으로 검증한다. jadx-gui에서 MobSF가 보고한 문자열을 Text search로 찾고, 상수 선언 → xref → sink 순으로 따라간다. smali 레벨에서 애매하면 `apktool d`로 푼 smali에서 `const-string`과 뒤따르는 `invoke-*`를 같이 본다.

> **[그림 2]** MobSF가 하드코딩 시크릿으로 표시한 문자열을 jadx-gui의 Text search로 찾아 "Find Usage(xref)"로 사용처를 따라간 화면 — 상수 선언과 실제 호출부를 한 화면에 대조 — *실측 스크린샷 자리*

### 관측 결과

`예시 출력(교체)` — 각 경보를 검증한 뒤 판정 표로 정리한다. 아래 값은 형식 예시이며 실제 스캔 결과로 교체한다:

```
경보                         | MobSF 심각도 | 도달성 | 트리거 조건        | 판정
----------------------------|------------|-------|------------------|--------
하드코딩 "test_api_key"       | High       | 미사용 | 없음(dead const)  | 오탐
exported .PostLogin         | High       | 도달 O | 인증상태 무검사     | vuln (참)
exported .ChangePassword    | High       | 도달 O | 로그인 후에만 의미   | bug(조건부)
ECB 모드 AES                 | Warning    | 도달 O | 저장 크리덴셜 암호화  | vuln (참)
http:// 상수 URL             | High       | 미호출 | 없음(주석/미사용)   | 오탐
```

정적 리포트에는 **없었던** 결함도 동적분석에서 나온다:

```
미탐(정적 리포트에 없음)         | 발견 경로
------------------------------|------------------
리플렉션으로 호출된 SQL sink     | 동적 실행 + Frida hook
루트 탐지 우회 후 드러난 분기      | 런타임 조건 분기
WebView addJavascriptInterface | 실제 URL 로드 시 노출
```

## Root Cause — 왜 오탐과 미탐이 생기나

**오탐의 뿌리는 도달성 미추적이다.** 대부분의 정적 스캐너는 패턴 매칭에 얕은 데이터플로우를 더한 수준이라, "패턴이 소스에 존재한다"는 확정하지만 "그 패턴이 외부 입력으로 도달 가능한 경로에 있다"는 완전히 추적하지 못한다. `Inferred` 그래서 미사용 상수, dead code, 테스트 전용 값이 전부 실제 결함과 같은 배지를 달고 나온다. exported처럼 매니페스트 규칙으로 도달성이 결정론적으로 확정되는 경우조차, "도달 후 위험 동작 유무"는 코드 의미 분석이 필요해 자동 판정 밖이다.

**미탐의 뿌리는 정적분석의 근본 한계다.** 실행해야만 정해지는 것 — 런타임 상태, 외부 입력값, 리플렉션·`DexClassLoader`로 동적 로딩되는 코드(C15), 조건 분기, WebView 브리지의 실제 노출 — 은 소스를 아무리 봐도 확정되지 않는다. `Source-confirmed`(OWASP MASTG의 정적/동적 테스트 분리 근거) MASTG가 정적 테스트와 동적 테스트를 별도 절차로 두는 이유가 이것이다. 즉 미탐은 스캐너의 버그가 아니라 방법론의 경계다.

결국 자동 스캔 점수(예: MobSF의 보안 점수)는 **입력 신호**이지 결론이 아니다. 점수를 그대로 리포트에 옮기면 오탐만큼 부풀고 미탐만큼 비어 있다.

## 방어와 회귀 검증 — 검증된 경보만 남기기

- **판정 표를 산출물로 고정한다.** 모든 경보에 도달성·트리거·판정을 붙이고, 검증되지 않은 경보는 리포트로 승격하지 않는다. 이 표가 26장의 MASVS 커버리지 매트릭스와 27장 회귀 테스트의 입력이 된다.
- **오탐은 "왜 오탐인지"를 근거와 함께 기록한다.** "미사용 상수 / permission 가드로 도달 불가" 같은 억제 사유를 남겨야 다음 스캔에서 같은 판단을 반복하지 않는다. 근거 없는 억제는 진짜 결함을 지우는 사고로 이어진다.
- **미탐은 동적분석·수동 테스트로 능동적으로 메운다.** 정적 리포트가 비었다고 "없음"이 아니다. 리플렉션·런타임 분기·WebView는 실행해서 확인한 뒤에야 "관측함/못함"을 말할 수 있다.
- **버전 고정.** MobSF는 버전마다 탐지 규칙과 점수 산정 방식이 달라진다 — 감사 재현을 위해 이미지 태그(Docker digest)와 규칙 버전을 리포트에 박아 둔다. `Inferred`(정확한 버전별 규칙 차이는 원문 재확인 필요)

회귀 관점에서, 한 번 vuln으로 확정한 경보는 패치 후 다시 스캔했을 때 사라지는지, 그리고 **변종으로 되살아나지 않는지**까지 확인해야 한다. 이 고정 작업이 27장의 회귀 테스트 하네스로 이어진다.

## 정리

- MobSF 경보는 "후보 위치"다. **도달 가능성 + 트리거 조건 + 민감한 부작용**이 다 확인돼야 vuln으로 승격된다.
- 오탐의 대부분은 도달성 미추적(미사용 상수·dead code·permission 가드), 미탐의 대부분은 정적분석이 못 보는 런타임 경로(리플렉션·조건 분기·WebView)다.
- 자동 스캔 점수는 입력 신호이지 결론이 아니다. jadx/smali 역추적과 동적분석으로 각 경보를 C42 사다리에 앉힌 표만 리포트에 남긴다.

**점검 질문** — (1) exported 경보와 하드코딩 시크릿 경보에서 MobSF가 "확정하는 것"의 범위는 각각 어떻게 다른가? (2) 정적 스캔이 리플렉션으로 호출된 sink를 놓치는 것을 왜 스캐너의 버그가 아니라 방법론의 경계라 하는가? (3) 오탐을 억제할 때 반드시 함께 기록해야 하는 것은?
