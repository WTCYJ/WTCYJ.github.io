취약점을 하나 찾아 제보하고 패치가 머지되면 거기서 손을 떼기 쉽다. 그런데 실제로 야생에서 관측되는 0-day의 상당수는 완전히 새로운 버그가 아니라 **이미 패치된 버그의 변종**이거나 **불완전한 패치**의 잔여물이다. 원인은 단순하다 — 같은 실수를 한 사람은 근처 코드에서도 같은 실수를 하고, 파서는 복붙되며, 리팩터는 사본을 남긴다. 패치는 증상 한 곳을 닫을 뿐, 클래스 전체를 닫는 건 별도의 작업이다.

이 글은 이미 패치된 공개 CVE 하나를 출발점으로 삼아, 그 버그를 **패턴으로 일반화**하고 AOSP 소스 트리 전체에서 형제 변종(sibling variant)을 훑는 워크플로를 정리한 기록이다. 무기화가 아니라, "이 수정이 정말 클래스를 닫았는가"를 검증하는 방어자·연구자의 작업이다.

> **한 줄 결론**: 변종 분석은 텍스트 검색이 아니라 **패치에서 추출한 데이터플로/구조 패턴을 트리 전체에 재적용**하는 일이다. grep은 문자열이 살아남은 사본만 잡고, 이름이 바뀌었거나 리팩터된 형제는 CodeQL·Semgrep 같은 구조·데이터플로 기반 도구라야 잡힌다.

## 무엇을 다루고, 무엇을 알아야 하는가

이 글의 범위는 "패치 하나 → 클래스 전체 스윕"의 방법론이다. (1) 패치 diff를 근본 원인 수준의 패턴으로 일반화하는 법, (2) `git grep`·Semgrep·CodeQL로 트리를 훑어 후보를 뽑는 법, (3) 뽑은 후보를 진짜 변종과 오탐으로 분류하는 법. 대상은 AOSP 공개 소스와 자작 하네스뿐이고, 재현은 이미 패치된 버그에 대해서만 한다.

선수 지식이 네 조각 깔린다. AOSP 소스 트리를 받아 대상을 좁히는 법(이 파트 1장), `git log`/`blame`/`tag`로 패치 커밋을 짚어내는 계보 추적(2장), 정적 규칙과 시맨틱 패치(spatch/Coccinelle)로 코드 패턴을 기술하는 법(16장), 그리고 패치가 있어도 벤더 이미지엔 안 내려온다는 patch-gap의 감각(15장)이다. 변종 분석은 이 넷을 한 파이프라인으로 잇는다.

전체 구조에서 이 장의 위치는 명확하다. 버그를 찾고 패치를 봤으면(2·14장) → 그 실수를 규칙으로 옮기고(16장) → **이 장에서 규칙으로 트리를 훑어 형제를 캐고** → 다음 장(18장)에서 그 수정과 형제들이 회귀하지 않는지 검증한다.

## 핵심 개념 — 변종 분석이란 무엇인가

변종 분석(variant analysis)은 "발견한 버그 하나를 씨앗으로, 같은 근본 원인을 공유하는 다른 인스턴스를 체계적으로 찾는 것"이다. Project Zero가 방법론으로 널리 알리고 연말 회고에서 반복 강조해 온 개념이다. `Reported` 이들의 보고서는 관측된 인더와일드 0-day의 상당 비율이 이전에 공개·패치된 버그와 밀접히 관련된 변종/불완전 패치였다고 지적한다(정확한 연도별 비율은 원문 재확인 필요). `Reported`

변종은 네 갈래로 산다. 표로 정리하면 스윕 도구를 고를 때 기준이 된다.

| 변종 유형 | 어떻게 생기나 | grep으로 잡히나 | 필요한 도구 |
|--|--|--|--|
| 복붙 사본 | 파서·헬퍼를 그대로 복사 | 대개 잡힘 | `git grep` |
| 이름 바뀐 사본 | 리팩터로 함수/변수명 변경 | **놓침** | Semgrep(구조) |
| 같은 API 오용 | 다른 호출부가 같은 실수 반복 | 부분적 | CodeQL(데이터플로) |
| 불완전 패치 | 한 경로만 막고 형제 경로 방치 | 놓침 | CodeQL/수동 diff |

핵심은 **씨앗 패치를 "무엇이 틀렸나"의 서술로 승격**하는 데 있다. 예를 들어 "길이 검사 없이 `memcpy`로 고정 버퍼에 복사"라는 서술은, 변수명이 무엇이든·함수가 어디에 있든 성립하는 패턴이다. 이 서술을 `git grep` 정규식으로 좁게 쓰면 사본만, Semgrep 규칙으로 구조로 쓰면 리팩터된 형제까지, CodeQL 쿼리로 소스→싱크 데이터플로로 쓰면 "검증되지 않은 길이가 복사 크기에 도달하는" 경로 전체를 잡는다. `Source-confirmed`

내 경험이 이 사다리를 그대로 밟았다. wabt를 퍼징해 명령 미구현(UNIMPLEMENTED) 경로의 크래시를 찾았을 때, 같은 클래스의 형제 하나(atomic wait/notify 계열)가 트리에 그대로 남아 있었다 — 씨앗을 opcode 단위 패턴으로 일반화하니 형제가 바로 눈에 보였다. `Source-confirmed` libsoup에서도 multipart·websocket·range 세 파서는 서로의 형제 표면이었고, range 쪽의 정수 오버플로는 나머지 둘을 같은 눈으로 다시 보게 만든 씨앗이었다. `Source-confirmed`

> **[그림 1]** 이미 패치된 공개 CVE의 수정 커밋을 `git show`로 연 화면 — 추가된 길이 검사 한 줄과, 그로부터 뽑아낸 "일반화된 패턴" 메모를 나란히 캡처 — *실측 스크린샷 자리*

## 신뢰 경계와 위협 모델

변종 분석의 위협 모델은 대칭적이라 흥미롭다. **공격자와 방어자가 같은 입력(공개 패치)에서 출발한다.** 패치가 공개되는 순간 diff는 "여기 버그가 있었다"는 지도가 되고, 공격자는 그 지도로 (a) 아직 패치가 안 내려온 벤더 이미지(patch-gap, 15장)를 n-day로 치거나 (b) 같은 실수의 형제를 찾아 새 0-day를 만든다. `Reported`

그래서 이 작업의 신뢰 경계는 "제보한 그 한 곳"이 아니라 **버그가 건너온 클래스 전체**다. 한 곳만 막고 손을 떼면, 방어자는 한 인스턴스를 닫았다고 믿는데 공격자는 형제 인스턴스를 이미 들고 있다. 변종 분석은 이 비대칭을 지우는 방어 작업이다 — 공격자가 할 스윕을 먼저 해서 클래스를 통째로 닫는다.

안전 범위는 엄격히 지킨다. 대상은 AOSP 공개 소스와 자작 하네스뿐이고, 재현은 **이미 패치된** 버그에 대해서만 개념 확인 수준으로 한다. 형제 후보가 진짜 취약해 보여도, 완성된 익스플로잇을 만들지 않고 원인·재현 조건·수정안까지만 정리해 정상 채널로 넘긴다. 미패치 형제를 찾았다면 그건 제보 대상이지 게시 대상이 아니다.

## 분석 — 씨앗에서 스윕까지

### 절차

1. **씨앗 확보** — 이미 패치된 CVE의 수정 커밋을 `git log`/`git show`로 연다(계보 추적은 2장).
2. **패턴 일반화** — diff가 무엇을 추가/제거했는지 읽고, 변수·함수명에 독립인 서술로 옮긴다.
3. **좁은 스윕** — `git grep`으로 문자열이 살아남은 복붙 사본부터 건진다(빠르고 오탐 적음).
4. **구조 스윕** — Semgrep 규칙으로 리팩터된 형제를 잡는다(16장의 정적 규칙을 재사용).
5. **의미 스윕** — CodeQL 데이터플로 쿼리로 "검증 없는 값이 위험 싱크에 도달"하는 경로를 잡는다.
6. **분류** — 후보를 진짜 변종/오탐으로 나누고, 진짜만 재현·제보로 보낸다.

```bash
# 2장에서 짚은 수정 커밋을 씨앗으로 연다 (이미 패치된 공개 CVE)
git show <fix-commit> -- path/to/parser.c

# 3) 좁은 스윕: 복붙 사본 — 문자열이 살아남은 경우만 잡힌다
git grep -n "memcpy(.*, .*, .*len)" -- '*.c' '*.cpp'

# 4) 구조 스윕: 이름이 바뀌어도 잡는다 (16장의 규칙 재사용)
semgrep --config sibling.yaml frameworks/av/media
```

`sibling.yaml`은 "길이 검사 없이 고정 버퍼로 복사"라는 구조를 기술한다. 텍스트가 아니라 AST 패턴이라, 리팩터로 이름이 바뀐 형제도 같은 규칙에 걸린다.

```yaml
# sibling.yaml (개념 예시) — 상한 검사 없는 복사를 구조로 기술
rules:
  - id: unchecked-copy-into-fixed-buffer
    languages: [c, cpp]
    message: "고정 버퍼로 복사 전 길이 상한 검사 없음 — 형제 변종 후보"
    severity: WARNING
    patterns:
      - pattern: memcpy($DST, $SRC, $LEN);
      - pattern-not-inside: |
          if (<... $LEN <= $CAP ...>) { ... }
```

CodeQL은 여기서 한 단계 더 간다. 문자열/구조가 아니라 **소스(신뢰 못 할 입력)에서 싱크(복사 크기)까지 데이터플로**를 추적하므로, 중간에 함수 몇 개를 거쳐 값이 흘러도 잡는다. 실행 명령은 아래 형태다(출력은 실제 실행으로 교체).

```bash
# 먼저 빌드 환경을 잡는다 (1장) — 이 선행이 없으면 m이 PATH에 없어 --command가 실패한다
# source build/envsetup.sh && lunch <target>
codeql database create aosp-db --language=cpp --command="m -j8 libstagefright"
codeql database analyze aosp-db sibling.ql --format=csv --output=hits.csv
```

`예시 출력(가상 경로·실측 아님·검증되지 않음)`:

```
# 아래는 형식만 보여주는 가상 경로·가상 라인이다. 실제 파일/라인이 아니며,
# 여기 나온 위치가 취약하다는 뜻이 결코 아니다 — 후보는 반드시 수동 검증한다.

# git grep — 복붙 사본 (문자열 생존)
path/to/extractorA.cpp:NNN:  memcpy(dst, src, hdr.len);
path/to/decoderB.cpp:NNN:  memcpy(state->buf, in, blk.len);

# semgrep — 리팩터된 형제 2건 추가로 검출 (이름 바뀜)
path/to/frame_decoder.cpp:NNN unchecked-copy-into-fixed-buffer
```

미디어 프레임워크가 좋은 예다. 추출기(extractor)들은 컨테이너만 다를 뿐 "헤더에서 길이를 읽어 버퍼로 복사"하는 골격을 공유한다 — 스테이지프라이트 계열에서 한 파서의 결함이 형제 파서들로 번진 이유가 이 공유 골격이다. `Reported` 그래서 한 추출기의 패치는 다른 추출기들을 다시 보라는 신호로 읽어야 한다.

> **[그림 2]** `git grep`과 Semgrep을 같은 씨앗 패턴으로 돌려, 트리 여러 경로에 흩어진 형제 후보가 나열된 결과를 캡처 — grep은 놓치고 Semgrep이 추가로 잡은 리팩터 사본에 표시 — *실측 스크린샷 자리*

## Root Cause — 왜 변종이 남는가

변종이 남는 건 우연이 아니라 소프트웨어 제작 방식의 구조적 산물이다. 첫째, **코드 재사용**. 파서·직렬화·경계 검사 로직은 복붙되거나 얇게 감싸 재사용되고, 원본의 결함은 사본에 그대로 승계된다. 둘째, **국소적 패치 습관**. 제보는 증상 한 곳을 지목하고, 수정자는 "그 줄"만 고친다 — 근본 원인이 공유 함수에 있으면 형제 호출부는 방치된다(불완전 패치). `Inferred` 셋째, **리팩터의 사본화**. 함수 분리·복제 과정에서 취약한 골격이 이름만 바꿔 여러 벌 생긴다.

여기에 도구의 한계가 겹친다. 사람이 diff를 보고 "이 버그 하나 고쳤다"로 인지를 닫으면, 클래스 관점이 사라진다. grep은 문자열이 살아남은 사본만 보여줘서, "몇 건 없네"라는 잘못된 안심을 준다. 근본 원인은 **패치를 인스턴스가 아니라 클래스로 다루지 않은 것**이고, 변종 분석은 바로 그 인지의 갭을 도구로 메운다.

## 방어와 회귀 검증

변종 분석의 결과물은 "형제 목록"이 아니라 **재사용 가능한 규칙**이어야 한다. 씨앗에서 뽑은 Semgrep/CodeQL 쿼리를 저장소 CI에 걸어 두면, 다음에 같은 골격이 새로 들어올 때 자동으로 걸린다 — 한 번의 스윕이 상시 회귀 검사로 승격된다. 이게 16장의 정적 규칙과 이 장이 맞물리는 지점이다.

- **씨앗 → 규칙 → CI**: 찾은 형제만 고치지 말고, 그 패턴을 쿼리로 남겨 클래스가 다시 열리는 걸 막는다.
- **패치 완전성 확인**: 수정 커밋이 근본 원인(공유 함수)을 고쳤는지, 아니면 한 경로만 막았는지 diff로 확인한다. 후자면 형제 경로가 곧 변종이다.
- **회귀 시드 보존**: 형제를 재현한 최소 입력을 코퍼스/회귀셋에 넣어, 다음 장(18장)의 회귀 검증이 클래스 전체를 커버하게 한다.

**흔한 실패와 처리.** `git grep`만 돌리고 "변종 없음" 선언 → 리팩터된 형제를 놓친 것. 최소한 구조(Semgrep) 스윕까지 간다. Semgrep 규칙이 너무 넓어 오탐 폭발 → `pattern-not-inside`로 이미 검사된 경로를 빼서 좁힌다. CodeQL이 빌드에 물려 안 돎 → 데이터베이스는 실제 컴파일을 캡처하므로, 대상 모듈만 빌드되게 `--command`를 좁힌다.

## 정리

- 변종 분석은 텍스트 검색이 아니라 **패치를 클래스 패턴으로 일반화해 트리 전체에 재적용**하는 일이다. grep=사본, Semgrep=구조 형제, CodeQL=데이터플로 형제.
- 공격자와 방어자는 같은 공개 패치에서 출발한다 — 형제를 먼저 훑어 클래스를 닫는 것이 방어다.
- 안전 범위는 이미 패치된 공개 CVE·AOSP 소스·자작 하네스뿐. 미패치 형제는 게시가 아니라 제보 대상이다.
- 스윕의 산출물은 목록이 아니라 CI에 남는 규칙이어야 클래스가 다시 열리지 않는다.
