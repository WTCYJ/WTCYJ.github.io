앞 장(증상/트리거/폴트사이트/근본원인 구분)에서 우리는 네 층을 갈랐다. 그런데 실제로 "근본 원인을 적어라"고 하면 대부분 트리거를 다시 쓴다 — "길이 0x41짜리 입력을 보내면 죽는다" 같은 문장. 이건 **하나의 목격 사례**지 근본 원인이 아니다. 근본 원인은 *어떤 성질이 왜 깨졌는가*이고, 그 성질을 한 문장으로 못 적으면 아직 원인을 못 찾은 것이다.

그 "성질"을 형식화한 것이 **보안 불변식(security invariant)**이다. 이 글은 RCA의 산출물을 반증 가능한 불변식 한 문장으로 적는 법을 정리한 기록이다. 불변식을 제대로 쓰면 그 뒤 파트 전체 — 패치 검증, variant analysis, 회귀 방어 — 가 기계적으로 이어진다.

> **한 줄 결론**: 근본 원인은 "어떤 보안 불변식이, 어느 신뢰 경계에서, 왜 깨졌는가"로 적는다. 반증 가능한 한 문장으로 옮길 수 없으면 그건 근본 원인이 아니라 트리거다.

## 무엇을 다루고, 무엇을 알아야 하는가

이 글은 RCA 결과를 **불변식으로 형식화하는 방법**을 다룬다. 불변식의 정의와 유형, 좋은 불변식이 갖춰야 할 조건, 그리고 불변식이 어떻게 패치 검증·variant analysis·회귀 방어로 연결되는지까지다. 무기화는 다루지 않는다 — 프리미티브의 존재를 불변식으로 서술하는 데서 멈춘다.

선수 지식은 세 가지다. 첫째, 앞 장의 4층 구분(증상·트리거·폴트사이트·근본원인)을 전제로 한다. 둘째, 결함 클래스별 대표 증상 — OOB, UAF, integer overflow, TOCTOU, Parcel mismatch — 의 이름 정도는 알아야 표의 각 행이 읽힌다. 셋째, 사전조건/사후조건/불변식이라는 계약(contract) 개념이 밑에 깔린다. 이는 Hoare 논리와 design-by-contract에서 온 오래된 형식이다. `Reported`

전체 구조에서 이 장은 **RCA의 출력 형식을 정하는 자리**다. 이후 장들(call graph·data-flow, 최소 재현, crash/exploitability 구분)이 전부 "깨진 불변식"을 중심으로 서술된다. 특히 10장(Parcel mismatch)·11장(integer)·12장(OOB)·13장(UAF)·14장(race)은 아래 유형표의 한 행씩을 확대한 것이다.

## 핵심 개념 — 불변식, 계약, 그리고 "보안" 불변식

불변식(invariant)은 **관측 구간 전체에서 항상 참이어야 하는 성질** P다. 루프 불변식, 자료구조 불변식, 클래스 불변식이 다 같은 뜻이다. 계약 개념과 나란히 놓으면 경계가 분명해진다. `Reported`

- **사전조건(precondition)**: 함수 진입 시 성립해야 하는 것 — 호출자의 책임.
- **사후조건(postcondition)**: 반환 시 보장되는 것 — 피호출자의 약속.
- **불변식(invariant)**: 지정한 구간 내내 성립 — 진입·중간·반환 모두.

여기에 "보안"이 붙으면 결정적 제약이 하나 추가된다. **보안 불변식은 신뢰 경계를 가로지르는 데이터/제어에 대해 항상 성립해야 하는 안전·인가 속성**이다. 내부에서만 만들어지고 공격자가 절대 못 건드리는 인덱스에 대한 `0 ≤ i < len`은 그냥 정확성 불변식이지 *보안* 불변식이 아니다. 같은 술어라도 `i`가 신뢰 경계를 넘어온 입력에서 유도될 때 비로소 보안 불변식이 된다. 이 구분을 놓치는 게 첫 번째 흔한 실수다.

결함 클래스는 대부분 "어떤 보안 불변식이 깨졌나"로 1:1 대응된다.

| 유형 | 불변식(항상 참이어야) | 위반 시 결함 클래스 |
|--|--|--|
| 메모리 안전(공간) | 모든 접근에서 `0 ≤ idx < len` | OOB read/write |
| 객체 수명(시간) | free 이후 그 포인터로 접근 없음 | UAF |
| 산술 | size 계산이 오버플로하지 않는다(또는 오버플로 시 실패) | integer overflow → 짧은 할당 |
| 타입/상태 | 태그가 실제 활성 union 멤버와 일치 | type confusion |
| 인가 | 특권 동작 **전에** 호출자 UID/권한을 검증 | Binder 권한 우회 |
| 시간적(temporal) | 검사(check)와 사용(use) 사이 대상이 불변 | TOCTOU/race |
| 직렬화 | Parcel write 순서 == read 순서·타입 | Parcel read/write mismatch |

> **[그림 1]** 자작 결함 앱의 폴트 사이트 소스에, 깨지는 보안 불변식을 주석으로 명시해 둔 화면(불변식 문장 + 경계 + 액터) — *실측 스크린샷 자리*

## 신뢰 경계와 위협 모델

보안 불변식은 **신뢰 경계 없이는 의미가 없다.** 그래서 잘 쓴 불변식은 성질만이 아니라 그 성질이 지키는 경계와, 그 경계에서 입력을 통제하는 액터를 함께 명시한다. 세 요소를 한 문장에 담는다.

1. **성질(property)** — 무엇이 항상 참이어야 하는가. (`claimed ≤ len - 4`)
2. **경계(boundary)** — 어디를 넘어온 데이터에 대해서인가. (Binder Parcel / Intent extra / 파일 / 네트워크)
3. **액터(actor)** — 누가 그 입력을 통제할 수 있는가. (임의 앱, 원격 상대, 로컬 파일 제공자)

Android에서 가장 흔한 경계는 Binder다. 임의 앱이 Parcel에 임의 바이트를 실어 특권 서비스로 보낸다. 그래서 인가 불변식("특권 동작 전 호출자 검증")과 직렬화 불변식("write 순서 == read 순서")이 유독 자주 깨진다. 위협 모델을 "호출자는 신뢰되지 않는다"로 못 박고 불변식을 그 전제 위에 쓴다. 경계를 안 적은 불변식은 "코드가 안전해야 한다" 수준의 공허한 문장으로 미끄러진다.

## 분석 — 좋은 불변식의 조건

좋은 보안 불변식은 아래 다섯 조건을 만족한다. 이건 체크리스트로 써도 된다.

1. **반증 가능(falsifiable)** — 구체적 상태를 넣으면 참/거짓이 판정된다. "파서는 안전해야 한다"는 반증 불가라 불변식이 아니다.
2. **국소적으로 체크 가능(locally checkable)** — 폴트 사이트에서 판정되는 술어여야 한다. 전역 상태 전체를 봐야 알 수 있으면 검증 도구도 사람도 못 쓴다.
3. **최소(minimal)** — 그 결함 클래스에 필요한 만큼만. 과하게 강하면 정상 입력도 거짓 위반으로 잡힌다.
4. **경계에 고정(boundary-anchored)** — 위에서 말한 경계·액터가 붙어 있다.
5. **기계 검증 가능하면 더 좋다** — `assert`, 새니타이저, 또는 ACSL 같은 명세로 옮길 수 있으면 자동 오라클이 생긴다.

나쁜 불변식과 좋은 불변식을 나란히 두면 차이가 선명하다.

| 나쁨(반증 불가·경계 없음) | 좋음(반증 가능·경계 고정) |
|--|--|
| "TLV 파서는 안전해야 한다" | "Parcel에서 온 `claimed`에 대해 `parseTLV`의 모든 `buf[i]` 접근에서 `i < len`" |
| "권한을 잘 확인한다" | "`setFoo()`는 본문 실행 전에 호출자가 `PERM_X`를 보유함을 `enforceCallingPermission`으로 검증한다" |
| "정수 계산이 맞다" | "`alloc(n * sz)`에서 `n * sz`가 `SIZE_MAX`를 넘지 않는다(넘으면 실패 반환)" |

여기서 핵심 도구가 **새니타이저 = 메모리 안전 불변식의 런타임 오라클**이라는 관점이다. AddressSanitizer는 "OOB·UAF 없음"이라는 공간·시간 불변식을 실행 중에 강제하고, 위반하면 리포트가 깨진 불변식의 종류(`heap-buffer-overflow`, `use-after-free`)를 이름으로 찍어 준다. `Source-confirmed` 커널 측 KASAN도 같은 역할을 한다. `Source-confirmed` 즉 "불변식을 손으로 쓰는 일"과 "새니타이저를 돌리는 일"은 동전의 양면이다 — 새니타이저 리포트의 제목이 곧 깨진 불변식 유형이다.

다만 **모든 불변식에 새니타이저가 있는 건 아니다.** 인가 불변식과 TOCTOU 불변식은 자동 오라클이 없어, 손으로 `assert`나 명시적 검증을 심어야 판정된다. 손으로 불변식을 쓰는 훈련이 필요한 이유가 여기 있다.

```c
// 보안 불변식 I1: parseTLV 진입 후 모든 buf[i] 접근에서 i < len 이어야 한다.
//   경계: Binder Parcel 로 들어온 신뢰되지 않는 바이트열
//   액터: 임의 앱(호출자)
uint32_t claimed = read_u32(buf);      // 공격자 통제 값
// assert(claimed <= len - 4);         // I1 을 명시했다면 여기서 거짓 판정
memcpy(dst, buf + 4, claimed);         // I1 위반 지점: len-4 검증 없이 claimed 사용
```

위 코드는 원리 이해용 최소 개념(프리미티브 존재까지)이다. 실행하면 새니타이저가 I1 위반을 잡는다.

> **[그림 2]** 같은 자작 결함을 ASan(또는 KASAN)으로 실행해, 리포트 첫 줄이 깨진 불변식 유형(`heap-buffer-overflow READ` — `buf` 상한을 넘어선 소스 읽기)과 폴트 사이트를 지목한 화면 — *실측 스크린샷 자리*

`예시 출력(교체)` — ASan 리포트에서 깨진 불변식 유형이 제목으로 나온다:

```
==12345==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x60b0...
READ of size 512 at 0x60b0... thread T0
    #0 0x... in memcpy
    #1 0x... in parseTLV tlv.c:42
0x60b0... is located 0 bytes to the right of 128-byte region (buf, len=128)
```

## Root Cause — 왜 이렇게 되는가

근본 원인 문장은 두 부분으로 쓴다. **(1) 깨진 불변식 + (2) 그 불변식이 보장되지 않은 이유**. 위 예시라면: "폴트 사이트 `parseTLV`에서 불변식 I1(`claimed ≤ len-4`)이 깨진다. I1이 보장되지 않는 이유는, `claimed`를 신뢰 경계(Parcel)에서 읽은 뒤 `memcpy` 전까지 어떤 경로에서도 상한을 검증하지 않기 때문이다."

이렇게 적어야 하는 이유는 셋이다.

- **트리거와 근본 원인이 분리된다.** 트리거는 I1을 깨뜨리는 *하나의* 입력(예: `claimed=0x200`)이고, 근본 원인은 *모든* 입력에 대해 I1을 보장하지 못하는 **누락된 성질**이다. 트리거는 목격자, 불변식은 일반 성질이다. 이 둘을 혼동하는 게 RCA에서 가장 흔한 오류다.
- **반증 가능하다.** "I1이 성립하는가?"는 임의 입력·상태로 판정된다. 산문 서술("입력 검증이 부족")은 판정할 수 없다.
- **다음 단계가 자동으로 열린다.** 불변식이 있으면 "패치가 I1을 모든 경로에서 복원했는가?"와 "코드베이스의 다른 어디서 I1이 깨지는가?"를 곧바로 물을 수 있다.

반대로, 근본 원인을 트리거로 적으면("길이 큰 입력이 크래시를 낸다") 패치는 그 한 입력만 막고 끝난다. 형제 경로는 그대로 열려 있고, 이게 뒤에서 볼 불완전 패치(17장)의 씨앗이다.

## 방어와 회귀 검증 — 불변식으로 패치를 검증한다

불변식은 발견 도구가 아니라 **검증 도구**로 값이 더 크다.

- **패치 정확성 = 불변식이 모든 경로에서 복원되는가.** 리포트된 경로 하나만 막으면 형제 경로는 여전히 불변식을 깬다. "이 패치가 I1을 *어느 진입 경로에서든* 복원하는가"를 물어야 한다. 못 하면 불완전 패치다(17장). `Reported`
- **Variant analysis.** 근본 원인을 불변식으로 형식화하면, "같은 불변식을 깨는 다른 사이트"를 grep·코드쿼리로 찾을 수 있다. Google Project Zero는 하나의 근본 원인마다 이 variant 탐색을 표준 절차로 문서화한다. `Source-confirmed` 불변식 없이 트리거만 있으면 이 검색을 할 술어 자체가 없다.
- **회귀 방어(regression).** 불변식을 `assert`나 테스트로 코드에 박아 두면, 나중 리팩터가 불변식을 다시 깰 때 CI가 잡는다. regression으로 되살아난 취약점(18장)을 막는 사실상 유일한 기계적 수단이다.
- **부정 대조(negative control).** 패치 전 빌드에서 불변식 체크가 **실패**(취약)하고, 패치 후 **성공**하는 걸 둘 다 확인해야 "이 패치가 진짜 이 불변식을 복원했다"가 증거로 선다. 한쪽만 보면 우연 일치를 배제 못 한다.

한 가지 못 박아 둘 것 — `assert(claimed <= len-4)` 한 줄은 불변식 그 자체가 아니라 불변식의 **런타임 체커**다. 릴리스 빌드에서 `NDEBUG`로 꺼지면 체크는 사라지고 불변식은 문서로만 남는다. 불변식(설계 성질)과 그 체커(assert)와 그 오라클(새니타이저)을 구분해야 한다.

## 정리

- 근본 원인은 "어떤 보안 불변식이 · 어느 경계에서 · 왜 깨졌는가"로 적는다. 반증 가능한 한 문장이 안 나오면 트리거를 근본 원인으로 착각한 것이다.
- 보안 불변식에는 성질·경계·액터 세 요소가 다 있어야 한다. 경계 없는 불변식은 그냥 정확성 술어다.
- 새니타이저(ASan/KASAN) 리포트의 제목이 곧 깨진 메모리 안전 불변식 유형이다. 단, 인가·TOCTOU 불변식은 자동 오라클이 없어 손으로 써야 한다.
- 불변식이 있어야 패치 검증(모든 경로 복원)·variant analysis·회귀 방어가 기계적으로 이어진다.

**점검 질문** — (1) 방금 재현한 자작 결함의 근본 원인을 성질·경계·액터가 든 한 문장으로 적어 보라. (2) `assert` 한 줄과 "불변식"은 어떻게 다른가? (3) 근본 원인을 트리거로 적으면 뒤의 어떤 단계가 무너지는가?
